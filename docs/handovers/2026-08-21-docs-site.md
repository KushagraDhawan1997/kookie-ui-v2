## What you asked for, and what is there

You wanted the docs to be a guideline document in the register of Apple's HIG — the system's
argument and its taxonomy, not a props catalogue — built entirely out of KookieUI, on correct
headless infrastructure, with the builder woven in. That is what is on the branch.

**Twenty-two chapters, about 19,000 words**, at `apps/docs`:

- **Getting started** — Installation, Theming, Your first screen
- **Philosophy** — Why Kookie exists, The kinds of things, Why these rules hold
- **Foundations** — Colour, Typography, Space and layout, Size, Radius, Materials, Depth,
  Motion, States and interaction, Responsiveness
- **Patterns** — Composition, Forms, Modality, Navigation, Feedback
- **Components** — the existing 31 reference pages, rebuilt

Plus search (⌘K), the whole site inside `Shell`, and the workbench (builder, preview, matrix)
promoted into the navigation instead of being three links in a header.

**Almost none of the content is new thinking.** It is `THESIS.md` and `DECISIONS.md` re-voiced
for someone who has not been in the room — descriptive turned normative. Where I could not find
a decision in the spec, I did not invent one; I recorded it as a gap instead (see below).

## The one thing to look at first

`/philosophy/the-kinds-of-things` is the chapter that did not exist anywhere before. It states
the ontology in one breath: grounds, surfaces, controls, marks, rows, instruments, type, layout,
and the frame. It is the piece your message was actually describing — "we have Card, Surface
with meaning, not interchangeable" — and every other chapter now cites its vocabulary instead of
re-deriving it.

It also carries the near-twin tests (Tabs vs segmented control, Dialog vs alert, Menu vs Select,
Card vs Surface) as functional dissociation rather than appearance, which is THESIS §3 applied
to the components rather than argued in the abstract.

If the taxonomy in that chapter is wrong anywhere, it is wrong everywhere downstream, so it is
worth your read before the rest.

## Infrastructure: what I took and what I refused

You said you would use correct headless infrastructure if it exists. Applying your own Base UI
test — adopt things that are *hard*, settled, behavioural, and invisible until we paint them —
split the field cleanly.

**Taken:**

- **`@mdx-js/mdx` via `@next/mdx`** — the compiler only. Every markdown element maps to a Kookie
  component in `mdx-components.tsx`. A `##` is a `Heading` on the §15 ladder, a fence is the same
  `CodeBlock` the component pages use, a rule is a `Separator`.
- **Shiki** for syntax highlighting, with **a theme generated from the ten tones**. Every token
  colour resolves through `--{tone}-ink`, so the code samples inherit the solved contrast
  targets and follow a re-judged palette. Bold is dropped (we refuse it), italic kept.
- **`remark-gfm`** — one plugin, purely so markdown tables exist.

**Refused, with reasons:**

- **`fumadocs-core`.** It is a real headless docs core and the closest thing to "Base UI for
  docs". What it abstracts is a nav tree from a directory, a table of contents and prev/next —
  a weekend of code we fully understand. Base UI is worth its dependency because we could not
  write it; this is a bundle of easy things.
- **`content-collections`** and frontmatter. Chapter order has to be authored, so a registry
  exists either way — frontmatter beside it is a second home for the same fields. Metadata lives
  in `chapters.ts` where `tsc` checks it. Four dependencies deleted.
- **Pagefind.** The better tool for a big site; it needs a post-build crawl and somewhere to
  serve an index. For fifty pages whose content we already hold as data, search is eighty lines
  of our own. Recorded as replaceable.
- **Twoslash.** It would add type hovers, not correctness — the examples are real `.tsx` files
  in the app's own program, so `tsc` already checks every one.

## The parts you will probably want to argue with

**1. Examples are real files now.** The 31 inline specimens moved out of `registry.tsx` into
`apps/docs/examples/<slug>.tsx`. Each file is imported and rendered, and the same file is read
off disk and shown as source — one file, two consumptions, nothing to keep in step. Side effect:
the registry became pure data, so it is `registry.ts` now and its law imports the values instead
of regexing the source.

I refused building examples on the builder's serializer, even though the round-trip law makes it
tempting: a builder document cannot express a handler, controlled state or an import, so a docs
system built on it could never show a form that submits.

**2. The API tables are generated from the types.** `scripts/generate-api.ts` reads the package's
own source and writes `api.generated.ts`, protected by a drift law on exactly the `tokens.css`
pattern. Only the props the package *declares* are shown — expanding the full type gives 324
names for `FlexProps`. The *agreement* law uses the checker's full answer, because a prop can be
real and absent from the declared list.

**3. Search indexes the refusals.** Typing "margin" finds Button, Flex and Text — because the
answer to "why can't I set a margin" is a refusal, not a feature. That is the search this site
should be good at.

**4. The composition chapter renders the reviewer's real rules.** It narrates the house style in
prose, then prints the actual `RULES` array the builder walks over a live document. A rule added
to the linter appears on the guideline page the same day, and the sentence you read is the
sentence the finding prints. This is the builder integration I think is worth more than a link.

**5. The navigation tree is a placeholder, as you said.** `nav-disclosure.tsx` is one collapsible
group over `ShellNavGroup`, written as one part with two props so that when the Kookie tree
ships the migration is deleting the file. It is explicitly *not* a general tree — no arbitrary
nesting, no roving focus, no `role="tree"` — because that is the API the package should own.

## What the writing found in the system

This is the part worth your attention beyond the site itself. Writing chapters against the code
turned up real defects, in the pattern this repo keeps repeating (/preview forced the composition
rules; the builder forced `componentAxes`).

**47 exported props had no JSDoc at all** — and they were the system's most central ones:
`size`, `tone`, `emphasis`, `weight`, and the floating components' controlled-state trios.
Undocumented precisely because everyone assumes they are obvious, while `bordered`, `loading` and
`leading` beside them all carried careful comments. All 47 are now written, with `size` written
nine different times because it joins nine different things.

**Then the law that caught them was itself too narrow.** It walked registry roots only, hiding 64
more undocumented props on the compound parts (`MenuItem`, `SelectItem`, every Dialog part,
`TabsList.size`). A law narrower than the rule it enforces is a law that cannot fail wearing a
quieter disguise. Widened, and the parts are documented.

**Doc–code drift in `DECISIONS.md`, in seven sections.** Each was verified against the code
before being amended:

- **§7 documents a `Theme accentColor` prop that has never existed**, with a worked nested-Theme
  example presenting it as the sanctioned path for a sectioned multi-accent app. Accent is
  hue-authored in config and baked by the generator — one app-wide identity. This is the biggest
  one, because §7 is what a chapter author is told to write from.
- **§8**'s disabled remap names pre-2026-08-19 values (`neutral-a3` / `neutral-6`); the code went
  per-mode and the border is an alpha step.
- **§6**'s radius palette is the pre-lab-port set and contradicts its own later prose.
- **§10 and §5** name shadow rows 3 and 2; the code emits row 4 and an authored literal, and the
  law asserts row 4.
- **§3** lists `Container` and `Spacer` as shipped (neither exists) and gives `Stack` a
  `direction` and `wrap` it does not have. `gridArea` is a real prop with no spec home.
- **§4**'s gap bullet names `--space-N`; the token is `--control-gap-N`.
- **§11**'s defaults table is stale on Tabs ("active tab takes accent" — false of the tab),
  Segmented Control (three ways), Select trigger, and describes `material` as a per-component
  opt-in in two places.

Two more turned up while those were being fixed: **§9's axis table** carried the same two
falsehoods (`accentColor`, and `material` as a per-component prop), and **§10's shadow anatomy**
still described two layers with a growing ambient offset, where the lab-depth adoption made it
contact–drop–blast, which is what the law asserts.

**`LOG.md` had an entry with a heading and no body** (2026-08-04, the tone set widening) — and
it turned out the body was not lost, it was *displaced*: four headingless paragraphs sitting
under a neighbouring entry are verbatim its content. Moved back under its heading, with nothing
reconstructed. Two further orphaned bodies in the same region are reported and deliberately left
alone: their headings were never written, and supplying them would be inventing history.

## Open, and left for you

None of these are defects in what shipped; they are decisions I did not think were mine.

1. **`DialogOpenChangeDetails`** is named by the public `DialogProps` signature but is not
   exported, so a consumer cannot type their own handler's second argument.
2. **`TextField` stamps `data-bordered` and `SelectTrigger` does not**, while both wear
   `kui-field`. Two members of one family disagreeing about an attribute.
3. **The package is not on npm.** The installation chapter says so plainly and gives the
   workspace route, because an install command that fails is a worse first page than an honest
   one. When it publishes, one paragraph changes.
4. **Three prose primitives are unshipped** — a list, an inline `Link`, a static table. §11 has
   planned `Link` since the defaults table was written. Each is drawn in `prose.css` from tokens
   and is small enough to delete the day the component lands.
5. **Nothing on the site has had an eye pass.** Every value is a token, so nothing needs new
   numbers — but the vertical rhythm of a chapter, the table of contents column, and the code
   block's ground in dark mode are all v0 by the same rule everything else in this system is.

### About CI in this container

`pnpm run ci` reports **one** failure, and it is an environment artifact rather than a
regression: `motion.browser.test.tsx > a button's travels, and it travels in whole pixels`.
This container ships Chromium build 1194 while the installed Playwright wants 1234, so the
browser project cannot launch at all until the binary is bridged by hand — which is why the
suite silently reported "10 passed (41)" at first, this repo's own favourite failure mode. I
bridged it, then reproduced the failure **with every one of my changes stashed**, and a second
session reproduced it independently. The law asserts that Chrome resolves `outline-offset` to
whole pixels; the substituted build returns 5.96875.

Everything else is green and was run after all changes landed:

- package node laws: 478/478
- package browser laws: 1539/1540 (the one above)
- docs laws: 447/447
- lint and `tsc`: clean in both packages
- `pnpm run measure`: 30988 gzipped, unchanged — nothing in this batch touched shipped CSS

The other browser law that failed on a full local run, `nothing jumps on the frame the flight
ends`, is a `watchesFrames` law: the class this repo deliberately excludes from CI because its
subject is wall time. Its own comment records it reporting ordinary flight travel as a release
jump on a stalled runner.
