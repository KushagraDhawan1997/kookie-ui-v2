## What the branch contains

You asked for a guideline document in the register of Apple's HIG, built from KookieUI, on
correct headless infrastructure, with the builder included.

**21 chapters, about 17,000 words**, in `apps/docs`:

- **Getting started** — Installation, Theming, Your first screen
- **Philosophy** — Why Kookie exists, The kinds of things, Why these rules hold
- **Foundations** — Colour, Typography, Space and layout, Size, Radius, Materials, Depth,

- **Patterns** — Composition, Forms, Modality, Navigation, Feedback
- **Components** — the 31 reference pages, rebuilt

The site also has search, a `Shell` frame, and the workbench in the navigation.

The chapters state decisions that already existed. `THESIS.md` and `DECISIONS.md` hold those
decisions. The chapters state them for a reader who did not make them. Where a decision was
missing from the specification, I recorded a gap. I did not invent a rule.

**The language follows ASD-STE100 Simplified Technical English.** The first draft did not. I
rewrote every chapter after you reported the fault. `content/AUTHORING.md` now holds the
language rules, so later chapters follow them.

**The chapters state rules, not history.** The first draft re-voiced `DECISIONS.md` and
`LOG.md`, and both of those are records of reversals, so the reversals came across. About 1,300
words told a reader about ladders and props that were removed before anyone could use them. All
of it is cut. A reason stays only where it changes what a reader types: "there is no per-card
shadow prop" stays, "the ladder was removed after the first review" goes. `AUTHORING.md` states
the rule in four parts, so later chapters follow it.

**Each chapter now builds something.** 26 of the 70 code fences were four lines or shorter, and
eight were one `<Theme>` prop. Every chapter now carries at least one fence of 8 to 15 lines that
composes a real screen: an editor toolbar over a canvas, a failed-invoice card, a create-project
form, an import panel, a shell with real navigation. I pasted every fence into one temporary
`.tsx` and compiled it before shipping.

## Read this chapter first

`/philosophy/the-kinds-of-things` did not exist before. It states the taxonomy: grounds,
surfaces, controls, marks, rows, instruments, type, layout and the frame.

It also separates the pairs that look the same: Tabs and the segmented control, Dialog and
alert dialog, Menu and Select, Card and Surface. It separates them by what each one does, not
by how each one looks.

Every other chapter uses that vocabulary. If the taxonomy is wrong, every chapter after it is
wrong.

## The infrastructure

You said to use correct headless infrastructure if it exists. I applied your Base UI test:
take a dependency when the problem is hard, settled, behavioural, and invisible until we paint
it.

**Taken:**

- **`@mdx-js/mdx`, through `@next/mdx`.** The compiler only. `mdx-components.tsx` maps every
  markdown element to a package component. A `##` becomes a `Heading`. A fence becomes the
  same `CodeBlock` that the component pages use.
- **Shiki**, with a theme generated from the ten tone families. Each token colour reads
  `--{tone}-ink`. The code samples therefore use the solved contrast values and follow a
  re-tuned palette. The theme drops bold and keeps italic, because the package refuses bold.
- **`remark-gfm`.** One plugin. Markdown tables need it.

**Refused:**

- **`fumadocs-core`.** It is a real headless documentation core. It provides a navigation tree,
  a table of contents and previous/next links. Each of those is a small amount of code that we
  understand. Base UI earns its place because we could not write it. This does not.
- **`content-collections` and frontmatter.** Chapter order must be authored, so a registry
  exists in either case. Frontmatter would be a second place to store the same fields. The
  metadata lives in `chapters.ts`, where `tsc` checks it.
- **Pagefind.** It is the better tool for a large site. It needs a crawl after the build and a
  place to serve an index. This site has about fifty pages, and we already hold the content as
  data. Search is 80 lines. It can be replaced later.
- **Twoslash.** It adds type hovers, not correctness. The examples are real `.tsx` files in the
  app, so `tsc` already checks every one.

## Decisions you may want to change

**1. The examples are real files.** The 31 inline specimens moved from `registry.tsx` to
`apps/docs/examples/<slug>.tsx`. The page imports each file and renders it. The page also reads
the same file and shows the source. One file, two uses, so the sample cannot differ from the
render.

I refused to build examples from builder documents. A builder document cannot express a
handler, controlled state or an import. A documentation system built on it could not show a
form that submits.

**2. A script generates the props tables from the types.** `scripts/generate-api.ts` reads the
package source and writes `api.generated.ts`. A test regenerates and compares, as the tokens
drift test does. The table shows only the props that the package declares. The agreement test
uses the type checker's full answer, because a prop can be real and absent from the declared
list.

**3. Search indexes the refusals.** Type "margin" and you find Button, Flex and Text. The
answer to "why can I not set a margin" is a refusal, not a feature.

**4. The composition chapter renders the reviewer's real rules.** It states the house style in
prose, then prints the `RULES` array that the builder runs. A rule added to the linter appears
on the page the same day.

**5. The navigation tree is a placeholder.** `nav-disclosure.tsx` is one collapsible group over
`ShellNavGroup`. It takes a label and children, so the Kookie tree can replace it by deletion.
It is not a general tree. It has no nested levels, no roving focus and no `role="tree"`.

## What the writing found in the package

Writing the chapters against the code found real defects.

**111 exported props had no JSDoc comment.** The missing ones were the most-used props:
`size`, `tone`, `emphasis`, `weight`, and the controlled-state props of the floating
components. Less-used props next to them had careful comments. All 111 now have comments.
`size` needed nine different comments, because it joins nine different scales.

**The test that found the first 47 was too narrow.** It walked registry roots only. It missed
64 props on the compound parts, including `TabsList.size`. A test narrower than the rule it
enforces cannot fail. I widened it.

**`DECISIONS.md` was wrong in nine sections.** I verified each one against the code before
amending it.

- **§7 documented a `Theme accentColor` prop that has never existed.** It also showed a worked
  example that used the prop for a multi-accent app. The colour config holds the accent as a
  hue and a vividness, and the generator bakes it. An app has one accent. §9 repeated the same
  error.
- **§8** named the pre-2026-08-19 disabled values.
- **§6** showed the pre-lab-port radius palette. It also disagreed with its own later text.
- **§10 and §5** named shadow rows 3 and 2. The code emits row 4 and a written literal.
- **§10** described a two-layer shadow. The code emits three layers.
- **§3** listed `Container` and `Spacer` as shipped. Neither exists. It also gave `Stack` a
  `direction` and a `wrap` that `Stack` does not have. `gridArea` was missing.
- **§4** named `--space-N` for the control gap. The token is `--control-gap-N`.
- **§11** was wrong about Tabs, the segmented control, the select trigger, and material.

**A LOG entry had a heading and no body.** The body was not lost. Four paragraphs under a
neighbouring entry are that body. I moved them back and reconstructed nothing. Two more
orphaned bodies remain in the same area. Their headings were never written, so I left them and
report them here.

## Open items

None of these is a defect in what shipped.

1. **`ShellScroll` lets its content's width escape the pane.** Base UI's ScrollArea sets
   `min-width: fit-content` on its content wrapper, as an inline style. That is correct for the
   element that scrolls. The demand then passes outward through every ancestor. A code block
   sets `white-space: pre`, so its scroller refuses to shrink below the longest line, and the
   page grows.

   Measured at a 700px window: the page content computed 784px inside a 685px pane. Every
   chapter with code ran past the right edge on a phone. The reading column's own
   `max-inline-size` did not prevent this. A maximum stops acting as a maximum when an ancestor
   sizes itself by `fit-content`.

   I fixed it in the app, in `prose.css`, scoped to the page scroller. Code blocks still scroll
   sideways inside their own wells. This is the second app to meet the same behaviour on the
   same component. `globals.css` already carries the builder's version on the block axis. The
   package should probably decide this, not each app.

2. **`DialogOpenChangeDetails`** appears in the public `DialogProps` signature. The package
   does not export it, so a consumer cannot type the second argument of a handler.

3. **`TextField` sets `data-bordered` and `SelectTrigger` does not.** Both wear `kui-field`.

4. **The package is not on npm.** The installation chapter states this and gives the workspace
   route. One paragraph changes when the package publishes.

5. **`SegmentedControl` gives a controlled consumer `unknown`.** It inherits Base UI's
   RadioGroup value type, so `onValueChange` receives `unknown` and the caller has to cast. The
   chapter shows the cast, because the version without it does not compile. A typed wrapper would
   fix it in the package.

6. **Nothing checks the props inside a code fence.** `AUTHORING.md` requires every prop, token
   and component name in a fence to exist. The chapter tests check the tokens, and check that
   each fence tokenizes. They do not check the rest. Extraction alone will not close this: a
   fence is often a fragment, a wrong/right pair with duplicate identifiers, or a reference to a
   symbol the chapter never defines. I compiled the fences by hand this time.

7. **Three prose components do not exist:** a list, an inline `Link`, and a static table. §11
   has planned `Link` since the defaults table was written. `prose.css` draws all three from
   public tokens. Delete each rule when the component ships.

8. **Nobody has reviewed the visual result.** Every value is a token, so no new numbers are
   needed. The chapter rhythm, the table of contents column and the code block in dark mode are
   all first versions.

## How to run it

```bash
pnpm install
pnpm run build
cd apps/docs && pnpm run dev
```

Open `/`, then `/philosophy/the-kinds-of-things`, then `/foundations/color`. The code theme is
clearest on that page. Then open `/patterns/composition` and scroll to the end for the live
rule list. Press ⌘K on any page.

`pnpm run ci` reports one failure. It is an environment fault, not a regression:
`motion.browser.test.tsx > a button's travels, and it travels in whole pixels`.
