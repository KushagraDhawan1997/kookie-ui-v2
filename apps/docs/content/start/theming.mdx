A `Theme` sets eight values for your whole app: appearance, density, radius, contrast, pointer,
depth, material, and size. Every component inside the theme reads those values. All eight are
optional, and the defaults suit an app that has not made any decisions yet.

## The eight settings

```tsx
<Theme
  appearance="inherit" // inherit | light | dark
  density="default" // compact | default | comfortable
  radius="full" // none | small | medium | large | full
  contrast="normal" // normal | high
  pointer="auto" // fine | coarse | auto
  depth="elevated" // flat | elevated
  material="solid" // solid | thin | regular | thick
  size="2" // 1 | 2 | 3 | 4
>
  {children}
</Theme>
```

### Appearance

`appearance` accepts `light`, `dark`, or `inherit`. Use `inherit` at the root, so that the theme
takes the mode from `<html>`, where the script in the [Installation](/start/installation)
chapter writes it.

### Density

`density` accepts `compact`, `default`, or `comfortable`, and it changes the space between
elements without making the elements smaller. A compact theme selects smaller gaps from the same
set of spacing values, while text keeps its size and corners keep their shape.

### Radius

`radius` accepts `none`, `small`, `medium`, `large`, or `full`. The theme calculates a different
corner for each category of component from that single value, which keeps a button, a card, and
a menu row in proportion at every setting.

### Contrast

`contrast` accepts `normal` or `high`. You can select `high` yourself, or leave the default,
because a person who raises the contrast in their operating system receives high contrast
automatically.

### Pointer

`pointer` accepts `fine`, `coarse`, or `auto`, and it tells the theme whether people use a mouse
or a touch screen. `auto` follows the device. Set it yourself to check the touch sizes on your
laptop.

### Depth

`depth` accepts `flat` or `elevated`, and it determines whether surfaces cast shadows. Set it
once for the whole app, because no component accepts a shadow prop.

### Material

`material` accepts `solid`, `thin`, `regular`, or `thick`, and it describes what your app is
made of. One value covers every panel, because every panel in an app is made of the same
material.

### Size

`size` accepts `1`, `2`, `3`, or `4`, and it sets the default size for controls and surfaces. At
`3`, every button, field, card, menu, and dialog without its own size moves up one step. The
setting is a default rather than a limit, so a `size` on a component always wins. A `Field` or a
`Composer` sets the size of the controls inside it, which lets you size those controls as one
object.

The setting leaves text alone, because `Text` and `Heading` use their own scale of nine steps,
and one number cannot carry the same meaning on both scales. The
[Composition](/patterns/composition) chapter shows how to rank your text. `Code`, `Kbd`, `Badge`,
and `Chip` take the size of the line they sit in, so the setting does not reach them either,
whereas `Avatar` follows it in the way a control does.

## Nest a Theme to change one region

A Theme inside a Theme changes only the settings it names and inherits the rest.

```tsx
<Theme density="comfortable">
  <Page />
  {/* A dense region inside a roomy app. Nothing else changes. */}
  <Theme density="compact">
    <DataTable />
  </Theme>
</Theme>
```

Use a nested Theme when one region must behave differently, such as:

- a dark hero on a light page
- a compact inspector panel in a comfortable app
- a glass panel over a photograph

Nesting also keeps menus and dialogs correct, because each floating layer applies the theme
again inside itself, so a menu opened from a dark section is dark as well.

Nesting does not change responsive behaviour. Wrap a component in `<Box container>` to make it
respond to the width of its container rather than the width of the window.

## The accent colour

Kookie generates the accent from two numbers in the colour config rather than from a prop. Set
them in `packages/ui/src/tokens/color-config.ts`:

```ts
// A violet brand.
const accent = { hue: 265, vividness: 1 } as const;
```

- **`hue`** is an angle in degrees on the OKLCH colour wheel, from 0 to 360.
- **`vividness`** is the fraction of the available chroma that the family takes at each
  lightness, from 0 to 1. At 1 the family takes as much colour as the gamut holds. Below 0.18 a
  scale can no longer carry prominence through saturation, so the solid fill resolves to the
  darkest step instead of the coloured one, which is how a grey brand works.

Then run the generator, which rewrites `src/tokens/tokens.css`:

```bash
pnpm --filter @kookie-ui/react run tokens
```

From those two numbers the generator calculates twelve steps and twelve transparent steps, in
light mode and dark mode, at normal and high contrast, along with every role that the
[Colour](/foundations/color) chapter lists: the tints, the fills, the border, the three text
colours and the readable label on a solid fill. Your neutral greys derive their hue from the
accent, so the greys lean towards your brand.

A prop could only accept a hex value, which gives the generator a single colour. A hex value
cannot say which fill the button takes under the pointer, which border reads against the page,
or which text colour clears the contrast floor in dark mode. The generator solves each of those
from the hue, and it checks the result against the contrast floors.

The generator runs when the package builds, so changing the accent means building Kookie from
source. An installed copy carries the generated stylesheet.

Therefore an app has one accent, and you cannot give one section a different brand colour.

## Read the theme in JavaScript

Components receive the settings through CSS, so most code never reads them. Two hooks cover the
cases that CSS cannot handle.

```tsx
import { useMaterial, useWindowClass } from "@kookie-ui/react";

// Your own panel, made of whatever the app is made of.
function Pane({ children }: { children: React.ReactNode }) {
  return (
    <div className="kui-surface" data-material={useMaterial()}>
      {children}
    </div>
  );
}

// Which navigation shape to show.
function Nav() {
  const windowClass = useWindowClass(); // "narrow" | "regular" | "wide" | null
  return windowClass === "narrow" ? <BottomTabs /> : <Sidebar />;
}
```

`useWindowClass` returns `null` on the server and until the first paint, because the server
cannot measure a window, and a guess would make React report that the server and the browser
disagree. Write the answer in CSS if you need it before the first paint, using
`windowClassQueries`, which the package exports with the same breakpoints.

## Why depth starts elevated and material starts solid

**`depth` starts at `elevated`** because most apps have a light source, which makes a flat app a
deliberate choice that you set yourself.

**`material` starts at `solid`**, which lets no light through a panel. Glass appears only when
the theme is glass and something behind the panel can bend, so a control in the normal page flow
stays solid.
