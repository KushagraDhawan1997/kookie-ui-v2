A theme is not a colour scheme. It is the set of app-level identities that every component
resolves against. You state them one time at the root, and everything inside inherits them.

There are seven axes. All of them are optional, and each default is the correct answer for an app
that has not decided yet. That inversion is deliberate. Overriding an axis requires knowing
something the library does not know.

## The seven axes

```tsx
<Theme
  appearance="inherit"   // inherit | light | dark
  density="default"      // compact | default | comfortable
  radius="full"          // none | small | medium | large | full
  contrast="normal"      // normal | high
  pointer="auto"         // fine | coarse | auto
  depth="elevated"       // flat | elevated
  material="solid"       // solid | thin | regular | thick
>
  {children}
</Theme>
```

**`appearance`** is light or dark. Use `inherit` at the root. `inherit` tells the theme to stamp
no appearance of its own and to read the mode from `<html>`, where the pre-paint script wrote it.
That is the whole dark-mode design. See [Installation](/start/installation).

**`density`** re-picks which step of the space palette each semantic distance uses. It scales
nothing. A compact theme is not a smaller theme. Its gaps sit lower on the same ladder. Type does
not move with density, and no corner moves with it.

**`radius`** is the corner identity for the whole app. Each component's corner derives from it in
bands, so a control, a Card and a menu row stay in proportion at every level.

**`contrast`** is an accessibility preference, and it is the conformance surface. It also answers
the platform signal, so a visitor who asked the operating system for more contrast gets it with
no prop set.

**`pointer`** is what is touching the screen. `auto` follows the platform. Pinning it forces
the whole coarse world: geometry, targets and the handheld type band together. Pin it to judge a
phone's sizing on a desktop.

**`depth`** says whether light exists in this app. Surfaces either sit above the page and cast
a shadow, or everything sits in one plane. This is an app-level statement, never a per-Card prop.

**`material`** is what the app is made of. One value covers the whole scope, because every
pane in one app is made of the same thing.

## A nested theme re-scopes

A nested `Theme` overrides the axes it names and inherits the rest.

```tsx
<Theme density="comfortable">
  <Page />
  {/* A dense region inside a comfortable app. Everything else is unchanged. */}
  <Theme density="compact">
    <DataTable />
  </Theme>
</Theme>
```

Use nesting to make a region behave differently. A dark hero inside a light page, a compact
inspector inside a comfortable app, and a glass panel over a photograph are the sanctioned cases.

Nesting is also what makes portals correct. Every floating layer re-applies the theme inside its
portal, so a menu opened from a dark section opens dark.

A nested theme does not create a query container. Layout measurement is the job of
`<Box container>`, and you opt into it where something inside wants measuring.

## The accent is set in config

There is no `accentColor` prop. This is the most common expectation the system does not meet.

The colour config authors the accent as a hue and a vividness. The generator solves the whole
family from those two numbers: every step, every role, both appearances and all contrast targets.
A prop could only pass a hex value, and a hex value is what the generator exists to avoid.

An app therefore has one accent. A differently branded region inside one app is not expressible
today.

## Read the theme in JavaScript only where you must

Most code needs no hook. Components read the axes through CSS inheritance, which is why no
JavaScript runs at interaction time. Two hooks exist for the cases that CSS cannot cover.

```tsx
import { useMaterial, useWindowClass } from "@kookie-ui/react";

// A pane of your own, made of whatever the app is made of.
function Pane({ children }: { children: React.ReactNode }) {
  return <div className="kui-surface" data-material={useMaterial()}>{children}</div>;
}

// Which interface shape to show. Returns null on the server.
function Nav() {
  const windowClass = useWindowClass(); // "narrow" | "regular" | "wide" | null
  return windowClass === "narrow" ? <BottomTabs /> : <Sidebar />;
}
```

`useWindowClass` returns `null` on the server and through the first paint. The server cannot
measure the window, and a hook that guessed would produce a hydration mismatch. Express the
answer in CSS when you need it before paint. The library exports the boundary queries as
`windowClassQueries`.

## The defaults and their reasons

The resting theme is light appearance, default density, `full` radius, normal contrast, automatic
pointer, elevated depth and solid material. Two of those need a reason.

`depth` defaults to `elevated`, because most apps have light in them. A flat world is the
deliberate exception rather than the neutral starting point. This is a judgment.

`material` defaults to `solid`. Solid is a material. It is the level where light stops passing
through, not the absence of a material. Glass takes two steps, and both are required. The theme
must be made of glass, and something must sit behind the pane for the pane to bend it. A control
in ordinary flow resolves `solid` and costs nothing.
