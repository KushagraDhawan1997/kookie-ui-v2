This chapter builds one settings panel: a title, two groups of controls, and two buttons. By
the end you will have written no colour, no pixel value and no breakpoint.

## Choose the containers before the components

In this system the container sets the distance between its children, so the first decision is
which container owns which relationship.

```tsx
import { Card, Heading, Stack, Text } from "@kookie-ui/react";

export function Settings() {
  return (
    <Card size="4">
      <Stack gap="6">
        <Stack gap="2">
          <Heading size="6">Notifications</Heading>
          <Text emphasis="medium">Choose what reaches you, and how.</Text>
        </Stack>
        {/* the groups go here */}
      </Stack>
    </Card>
  );
}
```

Notice the two Stacks use different gaps. The outer one, at 6, separates whole sections. The
inner one, at 2, ties the heading to the sentence underneath it.

Keep related things closer together than unrelated things. Your eye groups by distance before
it reads a word, so a screen that uses the same gap everywhere looks like one undifferentiated
list. This is a measured effect, not a preference.

There is no margin anywhere in that code. No component sets its own outer spacing, so every
distance on the screen comes from a container you can see.

## Put a checkbox beside its label

```tsx
import { Checkbox, Flex, Stack, Switch, Text } from "@kookie-ui/react";

function Group() {
  return (
    <Stack gap="4">
      <Flex align="center" gap="3">
        <Switch id="email" defaultChecked />
        <Text render={<label htmlFor="email" />}>Email me about releases</Text>
      </Flex>
      <Flex align="center" gap="3">
        <Checkbox id="digest" />
        <Text render={<label htmlFor="digest" />}>Weekly digest instead of every release</Text>
      </Flex>
    </Stack>
  );
}
```

No checkbox or switch takes a `label` prop. A label is text, and `Text` already handles every
size, weight and colour that text needs. Putting a `label` prop on a checkbox would mean
building a second, smaller text system inside it.

`render={<label htmlFor="…" />}` swaps the element without changing the component. You keep
the text size and colour, and the browser gets a real `<label>`, so clicking the words toggles
the control.

## Rank the two buttons

```tsx
import { Button, Flex } from "@kookie-ui/react";

function Actions() {
  return (
    <Flex gap="3" justify="flex-end">
      <Button emphasis="quiet" bordered>Cancel</Button>
      <Button tone="accent" emphasis="loud">Save changes</Button>
    </Flex>
  );
}
```

Two different props are doing two different jobs. `emphasis` is how loud the button is.
`tone` is what it means. Keeping them apart is why you never see a value like
`secondary-outline-destructive` here. That kind of value answers three questions at once, and
you cannot change one answer without changing the others.

Nothing defaults to loud and accent, so a second loud button on this screen is something you
have to type on purpose. That is how one screen ends up with one obvious action.

## What you never had to write

That screen is about thirty lines, and none of it mentions any of the following.

- **No colours.** You picked a tone and a loudness, and the theme worked out the value. It
  follows dark mode, it responds to the high-contrast setting, and it survives you changing
  your accent later.
- **No pixel sizes.** `size` is a step. One number set the height, the padding, the corner, the
  icon and the label size together.
- **No breakpoints.** Targets get bigger on a touch screen and text gets bigger on a phone.
  Layouts respond to the space they are given rather than the width of the window.
- **No hover, focus or press styles.** CSS handles every state, so nothing runs in JavaScript
  when someone points at a control.
- **No accessibility wiring beyond `htmlFor`.** The roles, the keyboard behaviour and the
  announcements come with the components.
