An AI coding agent learns this library the same way you do, from the types and from these pages.
Most libraries it has seen have a `variant` prop, a `color` prop and a margin prop on every
component, and this one has none of them. So an agent will reach for those props at first. The
tools on this page help it learn the library's own API, so you spend less time fixing its code.

You don't need any of these tools to build with the library. They're all generated from the same
source as the [component pages](/components), so they always agree with them.

## Start with the type checker

TypeScript is the first tool, and it's already running. When an agent writes a prop the library
doesn't have, the error names that prop and says what to use instead. For `variant`, the message
reads: *KookieUI has no `variant`. Use `tone` for what a thing means and `emphasis` for how loud
it is — so a quiet destructive button is expressible.*

Every missing prop has its own message. `asChild` points to `render`, and `highContrast` points
to `<Theme contrast="high">`. Most agents run `tsc` while they work, so they usually fix the code
from the message before you see it.

The type declarations also carry the documentation. Every exported component has its
description in its `.d.ts` file, which your editor and your agent read from `node_modules`, so
an agent can look up what a component does without going online.

## Lint what the type checker can't see

Three mistakes compile without an error:

- **A `data-tone` attribute:** TypeScript doesn't check attribute names that contain a hyphen.
- **A utility class, or a raw colour or length in `style`:** Both are valid types.
- **A prop inside a spread:** TypeScript checks attributes you write out, but not the contents
  of a spread.

The package includes an ESLint plugin that catches all three. A plugin can't include a parser,
so in a TypeScript project, add your TypeScript parser in its own entry:

```js title="eslint.config.mjs"
import tseslint from "typescript-eslint";
import kookie from "@kushagradhawan/kookie-ui-react/eslint-plugin";

export default [
  { files: ["**/*.tsx"], languageOptions: { parser: tseslint.parser } },
  ...kookie.configs.recommended,
];
```

A JavaScript project doesn't need the parser entry, because the plugin turns on JSX parsing for
`.js`, `.jsx`, `.mjs` and `.cjs` files itself.

The recommended config turns on three rules:

- **`no-refused-attribute` (error):** Reports a `data-` attribute that sets a theme setting
  directly, such as `data-tone`, because it brings back a prop the library left out.
- **`no-refused-prop` (error):** Reports a `color` prop. TypeScript can't catch this one with a
  helpful message, because React's own types already declare `color`. The rule also reports
  missing props inside a spread, when the spread object is written inline or as a `const` in the
  same file.
- **`no-escape-abuse` (warning):** Reports a class that looks like a utility class, such as
  `p-4`, `gap-3` or `min-w-[20rem]`. It also reports a raw colour in `style`, or a raw length on
  a property that already has a prop, such as `padding`.

Every message says what to write instead.

The plugin ignores single-word classes, such as `flex` and `grid`, because they might be your
own class names. It also ignores your other class names, and `style` values for properties that
have no prop. `style` is the right place for CSS the library doesn't cover, such as the height of
a `ScrollArea`.

## Give your agent the rules

Agents read an instructions file at the root of your repository, such as `AGENTS.md`,
`CLAUDE.md`, a Cursor rule in `.cursor/rules/` or `.github/copilot-instructions.md`. The package
includes a command that adds its rules to that file:

```bash
npx @kushagradhawan/kookie-ui-react init
```

By default, the command only prints what it would change and writes nothing. When you're happy
with the plan, run it again with the write flag:

```bash
npx @kushagradhawan/kookie-ui-react init --write
```

The command updates whichever of those files already exist. If you have none, it creates
`AGENTS.md`, which most coding agents read. It only creates the Cursor rule if your repository
already has a `.cursor/rules/` folder.

The command adds one block between start and end markers. The block lists:

- every export
- each theme setting and its values
- the props the library leaves out, and what to use instead

When you run the command again, it replaces that block instead of adding a second one. Run it
after each upgrade, and the rules will match the version you installed.

## Let your agent look things up

Every page on this site also has a Markdown version. To get it, add `.md` to the end of the path,
or request the page with the `Accept: text/markdown` header. The Markdown version of a component
page includes:

- the props it leaves out, and what to use instead
- its props and their allowed values
- its examples

`/llms.txt` lists every page with a one-line description, and `/llms-full.txt` contains the whole
site in one file. An agent that can fetch a URL needs nothing else.

If your agent supports the Model Context Protocol (MCP), you can give it the Kookie MCP server
instead:

```json title=".mcp.json"
{
  "mcpServers": {
    "kookie-ui": {
      "command": "npx",
      "args": ["-y", "@kookie-ui/mcp"]
    }
  }
}
```

The server has four tools:

- **`list_components`:** Lists every component with a one-line description, grouped the same way
  as this site.
- **`get_component`:** Returns the page for one component.
- **`get_tokens`:** Finds design tokens by name and returns their values.
- **`check_usage`:** Checks a piece of JSX and reports every missing prop, `data-` attribute,
  utility class and raw value, with what to write instead.

`check_usage` is the most useful of the four, because it tells your agent whether code follows
the library's rules before that code reaches your repository.

Like `@kushagradhawan/kookie-ui-react`, the `@kookie-ui/mcp` package isn't on npm yet, so the `npx` commands on
this page work once both packages are published.

### Use the tools in the browser

The same four tools are also available on every page of this site. Add `?webmcp=1` to the URL,
and the page registers them through the WebMCP API, so a browser agent that supports it can use
them while it reads. Without that parameter, the page loads nothing extra.

In the browser, each tool name starts with `kookie_`, such as `kookie_check_usage`, because a
page shares its tool names with every other script on it. Otherwise, the tools are the same.

## What your agent still needs to learn

These tools tell your agent which props exist and which don't. They don't tell it what a good
screen looks like. A screen can use every component correctly and still be wrong, for example
when it has:

- two loud buttons
- the same gap between every kind of element
- a heading at the wrong size

Once your agent stops writing props that don't exist, these are the mistakes you'll see most.
The [Composition](/patterns/composition) chapter explains how to avoid them, and it works as a
checklist when you review an agent's code. The [builder](/builder) checks a screen against the
same rules while you build it.

Here's what correct output looks like:

```tsx
import { Button, Card, Flex, Heading, Text } from "@kushagradhawan/kookie-ui-react";

export function Invite() {
  return (
    <Card size="3">
      <Flex direction="column" gap="5">
        <Heading size="6">Invite your team</Heading>
        <Text emphasis="medium">Everyone you add can see this project.</Text>
        <Flex gap="3" justify="flex-end">
          <Button emphasis="quiet">Not now</Button>
          <Button tone="accent" emphasis="loud">Send invites</Button>
        </Flex>
      </Flex>
    </Card>
  );
}
```

- **One loud button:** "Send invites" is the only main action on the screen.
- **No colours:** The theme calculates every colour from `tone` and `emphasis`.
- **No margins:** Each `Flex` sets the space between its children.
