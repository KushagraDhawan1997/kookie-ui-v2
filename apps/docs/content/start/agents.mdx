An AI coding agent learns this library the way you do, from the types and from these pages, and
it makes the same mistakes. Most libraries it has read carry a `variant` prop, a `color` prop and
a margin prop on every component, while this library carries none of them. The tools on this page
let an agent learn that from the package and the site, so you spend less time correcting its
output.

None of these tools is required for building with the library, and all of them generate from the
same source as the reference pages, so no tool can disagree with `/components`.

## Start with the compiler

The first tool is the type checker, and you cannot skip it. An agent that writes a refused prop
receives an error naming that prop and telling it what to write instead. For a `variant` prop the
message reads: *KookieUI has no variant. Use `tone` for what a thing means and `emphasis` for how
loud it is.*

Every refused prop carries its own message, so a margin prop on a button points to `Box` and a
`color` prop points to `tone`. Most agents run `tsc` while they work, which means they repair the
code from the message and you see the correct version rather than the mistake.

The package's type declarations also carry the documentation, because every exported component
keeps its description in its `.d.ts` file, which your editor and your agent read from
`node_modules`. The one-line answer to "what is this" therefore needs no network.

## Lint what the compiler cannot see

Three mistakes compile without an error:

- **A `data-tone` attribute**, because TypeScript does not check attribute names with a hyphen.
- **A utility class, or a raw pixel value in `style`**, because both carry correct types.
- **A prop inside a spread**, because TypeScript checks a written attribute and not a spread.

The package ships an ESLint plugin that catches all three.

The plugin includes no parser, since a plugin cannot, so place it after your TypeScript parser
entry:

```js title="eslint.config.mjs"
import tseslint from "typescript-eslint";
import kookie from "@kushagradhawan/kookie-ui-react/eslint-plugin";

export default [
  { files: ["**/*.tsx"], languageOptions: { parser: tseslint.parser } },
  ...kookie.configs.recommended,
];
```

A JavaScript project needs no parser entry, because the plugin sets the JSX flag itself for
`.js`, `.jsx`, `.mjs` and `.cjs` files.

The plugin ships three rules:

- **`no-refused-attribute`** is an error that reports a `data-` attribute naming a theme setting,
  because such an attribute restores a prop the type refused.
- **`no-refused-prop`** is an error that reports `color`, the one refusal the type cannot express,
  since React's own attributes declare `color` and the props type must accept it. The rule also
  reports every refused prop inside a spread.
- **`no-escape-abuse`** is a warning that reports a class resembling a utility, such as `p-4`,
  `gap-3` or `min-w-[20rem]`, along with a raw length in `style` for a property that has a prop.

Every message names the prop to use, and tells you what to write instead when the component
refuses that prop as well.

The plugin ignores a class of one word, such as `flex` and `grid`, which may be your own names or
a utility framework's. It ignores your own class names as well, along with `style` values for
properties that have no prop, because `style` is the documented route for CSS the library does
not cover.

## Give the agent the rules

Agents read an instructions file at the root of your repository, such as `AGENTS.md`,
`CLAUDE.md` or `.cursor/rules`, and the package can write its own section of that file:

```bash
npx @kushagradhawan/kookie-ui-react init
```

The command shows the changes it would make and writes nothing by default. Run it again with the
write flag to apply them:

```bash
npx @kushagradhawan/kookie-ui-react init --write
```

The command adds one block with start and end markers. The block contains:

- the list of exports
- each theme setting and its values
- the refusals

Running the command again replaces that block rather than adding a second one, and because the
package generates it, the block always matches the version you installed.

The same facts reach Claude Code through a skill named `kookie-ui` in this repository, which
loads when an agent starts to write UI.

## Let the agent look things up

Every page on this site also has a plain-text version, which you reach by adding `.md` to the
path or by sending `Accept: text/markdown`. The markdown page carries:

- the refusals of the component
- its props and each permitted value
- its examples

`/llms.txt` lists every page with a one-line description, while `/llms-full.txt` holds the whole
site in one file. An agent that can fetch a URL needs nothing else.

If an agent supports the Model Context Protocol, it can use the server instead:

```json title=".mcp.json"
{
  "mcpServers": {
    "kookie-ui": {
      "command": "npx",
      "args": ["-y", "@kookie-ui/mcp"]
    }
  }
}
```

The server has four tools:

- **`list_components`** returns the names and a one-line description for each, grouped the way
  this site groups them.
- **`get_component`** returns the page for one component.
- **`get_tokens`** finds design tokens by name and returns their values.
- **`check_usage`** takes a piece of JSX and reports every refused prop, refused attribute,
  utility class and raw value, telling you what to write instead in each case.

`check_usage` is the most useful of the four, because it tells you whether code sits inside the
system before that code reaches your repository.

The same four tools run in the browser on every page of this site once you add `?webmcp=1` to the
URL, which registers them with the WebMCP API so that a browser agent supporting the proposal can
use them while it reads. Without the flag the page loads nothing extra.

The browser names start with `kookie_`, such as `kookie_check_usage`, because a page shares its
namespace with every other script on the document. Nothing else differs.

## What an agent still has to know

The tools report what exists and what is refused, and they say nothing about what a good screen
looks like. The [Composition](/patterns/composition) chapter holds those rules, and it works as
the checklist when you review an agent's output. `check_usage` checks a snippet you paste, while
the builder at `/builder` applies the composition rules as you work, against a document you build
or open there rather than against pasted JSX.

A screen can hold only correct components and still be wrong, for example through:

- two loud buttons
- one spacing value for all kinds of gap
- a heading at the wrong step

When the refused props stop, you will see these mistakes most often. For this reason, this
site is a guideline, and not only a reference.

```tsx
import { Box, Button, Card, Flex, Heading, Text } from "@kushagradhawan/kookie-ui-react";

export function Invite() {
  return (
    <Card size="3">
      <Flex direction="column" gap="5">
        <Heading size="6">Invite your team</Heading>
        <Text emphasis="medium">Everyone you add can see this project.</Text>
        <Flex gap="3" justify="end">
          <Button emphasis="quiet">Not now</Button>
          <Button tone="accent" emphasis="loud">Send invites</Button>
        </Flex>
      </Flex>
    </Card>
  );
}
```

Correct output looks like that example:

- **One loud action** on the screen.
- **The theme sets every colour.**
- **The layout sets every distance**, rather than the components inside it.
