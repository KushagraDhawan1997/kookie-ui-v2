An AI coding agent learns this library as you do, from the types and from these pages. It
also makes the same mistakes. Most libraries that it has read have a `variant` prop, a `color`
prop and a margin prop on each component. This library has none of them. The tools on this
page let an agent learn this from the package and the site. Then you don't have to correct its
output.

You don't need these tools to build with the library. Each tool is optional. Each tool comes
from the same source as the reference pages. Thus no tool can disagree with `/components`.

## Start with the compiler

The first tool is the type checker, and you cannot skip it. If an agent writes a prop that the
library refuses, the error names the prop. The error also tells the agent what to write
instead. For a `variant` prop, the message is: *KookieUI has no variant. Use `tone` for what a
thing means and `emphasis` for how loud it is.*

Each refused prop has its own message. A margin prop on a button points to `Box`. A `color`
prop points to `tone`. Most agents run `tsc` while they work. Such an agent fixes the code from
the message, and you see the correct code, not the mistake.

The type declarations in the package also contain the documentation. Each exported component
has its description in its `.d.ts` file. Your editor and your agent read that file from
`node_modules`. Thus the one-line answer to "what is this" needs no network.

## Lint what the compiler cannot see

Three mistakes compile with no errors:

- A `data-tone` attribute. TypeScript does not check attribute names with a hyphen.
- A utility class, or a raw pixel value in `style`. Both have correct types.
- A prop inside a spread. TypeScript checks a written attribute, but not a spread.

The package ships an ESLint plugin for these three mistakes.

The plugin has no parser, because a plugin cannot include a parser. Put the plugin after your
TypeScript parser entry:

```js title="eslint.config.mjs"
import tseslint from "typescript-eslint";
import kookie from "@kookie-ui/react/eslint-plugin";

export default [
  { files: ["**/*.tsx"], languageOptions: { parser: tseslint.parser } },
  ...kookie.configs.recommended,
];
```

A JavaScript project needs no parser entry. For `.js`, `.jsx`, `.mjs` and `.cjs` files, the
plugin sets the JSX flag itself.

The plugin has three rules:

- `no-refused-attribute` is an error. It reports a `data-` attribute that names a theme
  setting. Such an attribute adds back a prop that the type refused.
- `no-refused-prop` is an error. It reports `color`, the one refusal that the type cannot
  show. React's own attributes declare `color`, so the props type must accept it. The rule
  also reports each refused prop inside a spread.
- `no-escape-abuse` is a warning. It reports a class that looks like a utility, such as `p-4`,
  `gap-3` or `min-w-[20rem]`. It also reports a raw length in `style` for a property that
  has a prop.

Each message tells you which prop to use. If the component also refuses that prop, the message
tells you what to write instead.

The plugin ignores a class of one word. For example, `flex` and `grid` can be your own class
names, or the names from a utility framework. The plugin also ignores your own class names. It
ignores `style` values for properties that have no prop. For CSS that the library has no prop
for, `style` is the documented method.

## Give the agent the rules

Agents read an instructions file at the root of your repository, such as `AGENTS.md`,
`CLAUDE.md` or `.cursor/rules`. The package can write its section of that file:

```bash
npx @kookie-ui/react init
```

By default, the command shows the changes that it would make, and it writes nothing. To make
the changes, run it again with the write flag:

```bash
npx @kookie-ui/react init --write
```

The command adds one block with start and end markers. The block contains:

- the list of exports
- each theme setting and its values
- the refusals

If you run the command again, it replaces the block. It does not add a second block. The
package generates the block, so the block always matches the version that you installed.

If you use Claude Code, the same facts are in a skill named `kookie-ui` in this repository.
The skill loads when an agent starts to write UI.

## Let the agent look things up

Each page on this site also has a plain-text version. To get it, add `.md` to the path. You
can also send the request with `Accept: text/markdown`. The markdown page contains:

- the refusals of the component
- its props and each permitted value
- its examples

`/llms.txt` lists each page with a description of one line. `/llms-full.txt` contains the
whole site in one file. If an agent can fetch a URL, it needs nothing else.

If an agent supports the Model Context Protocol, it can use the server instead:

```json title=".mcp.json"
{
  "mcpServers": {
    "kookie-ui": {
      "command": "npx",
      "args": ["-y", "@kookie-ui/mcp"]
    }
  }
}
```

The server has four tools:

- `list_components` returns the names and a description of one line for each. It groups them
  as this site groups them.
- `get_component` returns the page for one component.
- `get_tokens` finds design tokens by name and returns their values.
- `check_usage` takes a piece of JSX. It reports each refused prop, refused attribute, utility
  class and raw value. For each problem, it tells you what to write instead.

`check_usage` is the most useful tool. It tells you if code is inside the system before the
code gets to your repository.

The same four tools are also available in the browser on each page of this site. Add
`?webmcp=1` to the URL. The page then registers the tools with the WebMCP API. A browser agent
that supports the proposal can then use them while it reads. Without that flag, the page loads
nothing more.

In the browser, the tool names start with `kookie_`, for example `kookie_check_usage`. The
reason is that a page shares its namespace with all other scripts on the document. There are
no other differences.

## What an agent still has to know

The tools tell an agent what exists and what is refused. They do not tell it what a good
screen looks like. The [Composition](/patterns/composition) chapter contains those rules. Use it
as the checklist when you review the output of an agent. `check_usage` checks a snippet that
you paste. The builder at `/builder` applies the composition rules while you work. It checks a
document that you build or open there, not pasted JSX.

A screen can contain only correct components and still be wrong. For example:

- two loud buttons
- one spacing value for all kinds of gap
- a heading at the wrong step

When the refused props stop, you will see these mistakes most often. For this reason, this
site is a guideline, and not only a reference.

```tsx
import { Box, Button, Card, Flex, Heading, Text } from "@kookie-ui/react";

export function Invite() {
  return (
    <Card size="3">
      <Flex direction="column" gap="5">
        <Heading size="6">Invite your team</Heading>
        <Text emphasis="medium">Everyone you add can see this project.</Text>
        <Flex gap="3" justify="end">
          <Button emphasis="quiet">Not now</Button>
          <Button tone="accent" emphasis="loud">Send invites</Button>
        </Flex>
      </Flex>
    </Card>
  );
}
```

The correct output looks like this example:

- It has one loud action.
- The theme sets each colour.
- The layout sets the distances. The components inside it do not.
