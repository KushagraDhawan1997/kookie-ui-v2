Kookie components keep a screen consistent: every distance comes from a spacing step, every
colour from a tone, and every size from a size step. Consistency isn't the same as quality,
though. You can still put nine components on one screen at nine different sizes, and nothing in
the components will stop you.

This page covers the rules for putting components together on a screen. The
[builder](/builder) checks most of them for you while you work.

## One obvious action per screen

Give each screen one loud control, and make it the action the screen exists for. Set it with
`tone="accent"` and `emphasis="loud"`, and leave every other control at medium or quiet.

When two controls are loud, neither one stands out, and a person can't tell which is the main
action. This is a judgment, based on the figure-and-ground principle: something only stands out
when the things around it are quiet.

```tsx
// Wrong. Two loud controls compete for attention.
<Flex gap="3">
  <Button tone="accent" emphasis="loud">Save</Button>
  <Button tone="accent" emphasis="loud">Publish</Button>
</Flex>

// Right. The main action is clear, and the second one is still easy to find.
<Flex gap="3">
  <Button emphasis="medium">Save draft</Button>
  <Button tone="accent" emphasis="loud">Publish</Button>
</Flex>
```

`Button` defaults to medium, so a loud button is almost always one you asked for. The two
exceptions are `AlertDialogAction` and the send button in a `Composer`, which default to loud
because each is the only action in its component.

Count loud controls across the whole screen, not inside the nearest card. A dialog counts as a
screen of its own, because it covers the page, so its loud button doesn't compete with anything
underneath. Two tab panels never compete either, because only one is visible at a time.

## Let space do the grouping

Put related things closer together than unrelated things. People group items by distance before
they read a word, and distance does this more reliably than a border, a fill or a dividing line.
Set the spacing first, and you'll usually find you don't need the other three.

Make the gap inside a group at least two steps smaller than the gap around it. When a screen uses
the same gap from top to bottom, it shows no structure at all.

```tsx
<Stack gap="6">
  <Stack gap="2">
    <Heading size="6">Notifications</Heading>
    <Text emphasis="medium">Choose what reaches you, and how.</Text>
  </Stack>
  <Stack gap="2">
    <Heading size="6">Billing</Heading>
    <Text emphasis="medium">Cards, invoices and the plan you are on.</Text>
  </Stack>
</Stack>
```

The two-step rule compares the inside of a group with the space around it. Two levels that both
separate groups can sit one step apart: a section at gap 6 can hold groups at gap 5.

## Five type sizes and one floor

Spacing, colour and control sizes all follow the theme, but text size doesn't. `size` on `Text`
and `Heading` accepts any step, so only a written rule keeps a screen consistent. Use these five:

- **Size 8** for the page title.
- **Size 7** for a section title.
- **Size 6** for a card or dialog title.
- **Size 3** for body text.
- **Size 2** for labels and small print.

Don't use size 1 on a real screen. At 12 pixels it's only suitable for text that almost nobody
needs to read. When something is less important, keep it at size 2 or 3 and use the muted or
faint colour instead, with `emphasis="medium"` or `emphasis="quiet"`.

To show that one piece of text ranks above another, move at least two steps. A size 4 title over
size 3 body text looks like an accident rather than a hierarchy.

## Use a tone for what it means

Choose a tone because of what it means, not because a screen looks too grey.

```tsx
// Wrong. Green because green looks pleasant.
<Text tone="green">Storage used</Text>

// Right. A status message in the tone that means success.
<Text tone="success">Backup completed</Text>
```

`success`, `warning`, `info` and `destructive` carry meanings. `blue`, `green`, `orange` and
`amber` are for colour as data, such as a chart series, a project label or a category.

Keep to three tones or fewer on one surface. Three tones read like a legend, but four or more
start to look like a palette. And never let colour carry the whole message: write the words too.

## Same job, same size

Controls that do the same job on one surface should be the same size. A size 3 button beside a
size 2 button looks like two different kinds of control, and a person will look for a reason that
isn't there.

Match controls to the surface that holds them, too. A size 3 dialog should hold size 3 fields and
size 3 buttons. A `Field` passes its `size` to the control inside it, but a `Dialog` or a `Card`
doesn't, so set the size on the controls yourself. A control two steps smaller than its container
looks like a mistake.

## Write the real words

Build a layout with real content. If the content doesn't exist yet, write text of the same shape
and length. Placeholder text hides the problems you most need to see:

- a heading that wraps onto three lines on a phone
- a name that is longer than its column
- a button label that breaks the rhythm of a row

The same goes for helper text. Keep a line if it changes what a person does next, and delete it
if it only repeats the label.

## Run the reviewer

Before you ship a screen, run the reviewer in the builder. Each finding points at the part of
your screen that breaks a rule, quotes the rule, and offers a fix when one is safe to apply.
Every template in the builder passes all of the rules, so a template is a good place to start.

The reviewer can't tell you whether a screen is good. It only tells you when a screen breaks a
rule this system has already decided.
