An interface has four things to tell you about work that it does. It tells you that the work
started, how much is done, how the work ended, and what went wrong. Each of these has one
correct answer. The usual mistake is to choose the wrong answer, not to give it a bad style.

## Four things to say

| what you say | when | the answer |
|---|---|---|
| Busy | The work started, and you cannot say how long it will take | `Spinner`, or `loading` on the button that started it |
| Progress | You know the fraction that is done | `Progress` with a `value` |
| Outcome | The work is finished | Words where the action was, in the tone that names the result |
| Error | The work failed, or the input was wrong | The invalid state of the control, and a sentence |

Outcome is the only row that has no component. The last section tells you what to build
instead.

## A busy button keeps its label

Set `loading` on a `Button`. The button replaces its leading icon with a spinner. The spinner
uses the same box, so nothing moves. The label stays. A button that stops saying what it does
is worse than a button that changes width.

```tsx
<Button emphasis="loud" loading={saving}>Save changes</Button>
```

A loading button keeps focus and its position in the tab order. It announces that it is busy,
and a person cannot activate it again. The spinner inside it is hidden from screen readers
intentionally, because the button already gives that information.

Use a standalone `Spinner` for an area that has nothing to show yet. It gets its colour from
the text around it. It gets its size from the icon size of the element that contains it. So you
do not give it a colour or a size.

## Progress when you know the fraction

`Progress` is a track with a fill in it. If you give it a number, it shows a fraction. If you
give it `value={null}`, it shows a moving sweep. The prop is required. So you must say "I do not
know how much is done". You cannot get that result because you forgot the prop.

`Progress` has no `size`, and this is intentional. The nearest scale sets the size of a track as
a fraction of a slider handle. A bar has no handle. The container of the bar sets its width. So
the `Box` that contains the row decides.

The three answers go together in one panel. The button tells you that the work started. The bar
tells you how much is done. The words tell you how the work ended.

```tsx
<Card size="3">
  <Stack gap="4">
    <Heading size="6">Import files</Heading>

    {done ? (
      <Text size="3" tone="success">Imported 24 files.</Text>
    ) : (
      <Stack gap="2">
        <Progress value={uploading ? uploaded : null} aria-label="Importing files" />
        <Text size="2" emphasis="medium">{uploaded} of 24 files</Text>
      </Stack>
    )}

    <Flex justify="flex-end">
      <Button emphasis="loud" loading={uploading} onClick={start}>Import</Button>
    </Flex>
  </Stack>
</Card>
```

The outcome replaces the bar in the same position. It does not appear in a different part of
the screen.

Give each bar a name. If a bar has no accessible name and no heading connected to it, it gives
a number that nobody can understand. Use a real fraction when you have one. A moving sweep only
tells you that something is in progress.

## Reduced motion

A spinner and a progress bar with no value keep moving. Their movement does not show a change
of state. It shows that the work continues. A person can ask their operating system for reduced
motion. Then these two move more slowly, but they do not stop, because a stopped spinner looks
finished.

Use the same rule in everything that you build. A shimmer, a pulsing dot and a moving bar all
give their message with movement, so they continue to move. A hover colour, a panel that opens
and a focus ring that appears are responses to a change, and Kookie shows them at once.

## Use a status tone for what it means

Four tone names carry a meaning: `success`, `warning`, `info` and `destructive`. Four other tone
names are colour as data: `blue`, `green`, `orange` and `amber`. Use the second set when the
colour is the data. Examples are a chart series, a project label and a category.

Currently, `success` and `green` show the same colour. They are still two separate families,
because you must be able to change each meaning independently. Do not write `green` when you
mean success. It looks correct now. It becomes wrong when the value of either family changes.

```tsx
// The tone people reach for
<Text size="2" tone="green">Deployed</Text>

// The one that means it
<Text size="2" tone="success">Deployed</Text>
```

Use a small number of data tones. Four or more data tones on one surface look like a palette,
not a set of meanings. Three look like a legend.

## Colour is never the whole message

Colour alone is not sufficient (WCAG 1.4.1). So each status that the system paints is only half
of a message. The system supplies the border, the focus ring and the text colour. You write the
sentence.

A red field with nothing next to it does not obey this rule. A green dot with no label does not
obey it. A chart that shows its keys only with colour does not obey it. These three examples are
worst for people who cannot see the colour.

In an error, tell the person what to do next. Colour cannot give that information.

## Use a Notice for something that stays true

Use `Notice` for a condition that is true now. Nobody caused the condition. The notice stays
while the condition stays. It takes space in the layout and never floats. So it cannot cover
the thing that it tells you about. Its resting colour is neutral. The tone tells you the kind of
message, not how loud to make it.

```tsx
<Notice
  tone="warning"
  action={<Button size="2">Add a card</Button>}
  onDismiss={() => setSeen(true)}
>
  Your trial ends in three days.
</Notice>
```

`action` holds one control that fixes the condition. `onDismiss` adds a close control that only
acknowledges the condition. A fix and an acknowledgement are different jobs, so they are
different props. `onDismiss` is a callback with no state of its own. A component cannot
remember a dismissal after the page reloads, so your app must remember it.

## There is no toast

`Toast` is refused and will not ship. If something needs attention, it must get attention
before it runs. If something does not need attention, it does not need a report after it runs.

People build a toast for two cases, and both cases belong in a different place. Undo belongs in
an undo stack, on a control that people can find later. A copy confirmation belongs on the
button that did the copy.

Do not build a replacement. A `Card` pinned to a corner does not get the live region that makes
the announcement. It also does not get the close behaviour that people expect.

`Callout` and `Banner` are the names that other libraries use for `Notice`. The name "Banner"
describes a position, and no component here sets its own position.

## Where to put an outcome

Put the result where the action was:

- **Inline.** Put a `Text` in the matching tone next to the control or under it. Write its verb
  in the past tense. After a button that said "Publish", write "Published", not "Success".
- **With a heading.** Use a `Card` that holds a `Heading` and a `Text`. Put the tone on the
  words. Do not give the card a colour. Surfaces take no tone. If you add a colour with `style`,
  you write a fixed colour into the app, and the app can no longer change its theme.
- **A decision.** Use an `AlertDialog` when the person must answer before anything else can
  happen.
