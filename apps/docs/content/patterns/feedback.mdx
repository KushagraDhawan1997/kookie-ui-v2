An interface says four things about work it is doing. It says that the work started, how far the
work has got, how the work ended, and what went wrong. Each one has a single answer here. The
common failure is the wrong answer, not an ugly one.

## Four things to say

| what you say | when | the answer |
|---|---|---|
| Busy | The work started and you cannot say how long | `Spinner`, or `loading` on the `Button` that started it |
| Progress | You know the fraction | `Progress` with a `value` |
| Outcome | The work finished | Words where the action was, in the tone that names the result |
| Error | The work failed, or the input was wrong | The invalid state of the control, plus a sentence |

Outcome is the one row with no component yet. The last section of this chapter says what to
build instead.

## Busy keeps the label

Set `loading` on a `Button`. The button swaps its leading slot for a `Spinner`. The slot reuses
the box of the glyph, so nothing shifts. The label stays. A button that stops saying what it does
is worse than a button that changes width.

```tsx
<Button emphasis="loud" loading={saving}>Save changes</Button>
```

A loading button keeps its focus and its place in the tab order. It announces `aria-busy`. It
refuses activation. The `Spinner` inside it is hidden from assistive technology on purpose,
because the button already carries the state.

Use a standalone `Spinner` for a region that has nothing else to show yet. It fills with
`currentColor` and it takes the icon box of the thing it sits in, so it needs neither a colour
nor a size of its own.

## Progress when you know the fraction

`Progress` is a track with a fill in it. A number reports the fraction. `value={null}` sweeps as an
indeterminate bar. The type requires the prop, so you have to say "I do not know how far
along this is" instead of arriving there by forgetting one.

`Progress` has no `size`, and the absence is a decision. The ladder it could have used sizes a
track as a fraction of a slider's thumb, and a bar has no thumb. Its extent comes from the
container, so the `Box` that owns the row decides how wide the bar is.

The three answers compose into one panel. The button says the work started, the bar says how far
it has got, and the words say how it ended.

```tsx
<Card size="3">
  <Stack gap="4">
    <Heading size="6">Import files</Heading>

    {done ? (
      <Text size="3" tone="success">Imported 24 files.</Text>
    ) : (
      <Stack gap="2">
        <Progress value={uploading ? uploaded : null} aria-label="Importing files" />
        <Text size="2" emphasis="medium">{uploaded} of 24 files</Text>
      </Stack>
    )}

    <Flex justify="flex-end">
      <Button emphasis="loud" loading={uploading} onClick={start}>Import</Button>
    </Flex>
  </Stack>
</Card>
```

The outcome replaces the bar in the place the bar was. It does not arrive somewhere else on the
screen.

Name every bar. A bar with no accessible name and no heading wired to it reports a number that
nobody can read. Use the determinate form wherever the fraction exists. This is a judgment.
An indeterminate sweep says only that something is happening.

## Motion that is the message

Everything else in this system stops moving under `prefers-reduced-motion`. A spinner and an
indeterminate bar are the exception. Their movement is not a response to a state change. Their
movement is the message. Stopping them would remove the only thing they tell you, so they slow
down instead.

Carry that distinction into anything you compose. A skeleton shimmer, a pulsing dot and a
sweeping bar all carry their message by moving. A hover fill, a panel opening and a ring landing
respond to a state change, so they stop.

## Use a status tone for its meaning

Four names carry meaning: `success`, `warning`, `info` and `destructive`. Four more are colour as
data: `blue`, `green`, `orange` and `amber`. Use the second set for a chart series, a project
label or a category, where the colour is the information.

`success` and `green` render the same colour today and remain two separately generated families.
A meaning has to stay independently correctable. Do not write `green` when you mean success. It
looks right today and it is wrong on the day either name is re-judged.

```tsx
// The tone people reach for
<Text size="2" tone="green">Deployed</Text>

// The composed answer
<Text size="2" tone="success">Deployed</Text>
```

Keep the count down. Four data tones or more on one surface read as a palette rather than as a
meaning. Three tones read as a legend, such as a status set or a three-series key.

## Colour is never the whole message

Colour alone is not enough (WCAG 1.4.1). Every status this system paints is half a
message. The border, the ring and the text colour are the half the system paints. You write the
sentence.

A red field with nothing beside it fails this rule. A green dot with no label fails it. A chart
keyed by hue alone fails it. All three fail worst for the people who cannot see the colour.

Write what to do next in an error. A colour could never carry that instruction.

## Use a Notice for a condition that stays true

`Notice` is the component for a condition that is true right now. The person did not cause it,
and it lasts while the condition lasts. It takes layout space and never floats, so it cannot
cover the content it is telling you about. It rests neutral, because the tone is the category
and not the volume.

```tsx
<Notice
  tone="warning"
  action={<Button size="2">Add a card</Button>}
  onDismiss={() => setSeen(true)}
>
  Your trial ends in three days.
</Notice>
```

`action` holds one control that resolves the condition. `onDismiss` adds a dismissal that
only acknowledges it. Those are two different verbs. `onDismiss` is a callback with no internal
state, because a component cannot remember a dismissal across a reload. Your app has to.

## There is no toast

`Toast` is refused, and it will not ship. An action that deserves attention gets that attention
before it runs. An action that does not deserve attention does not need a report afterwards.

The two cases people build a toast for both go somewhere else. Undo belongs in an undo stack, on
a control the person can find later. A copy confirmation belongs on the button that copied.

Do not build a substitute. A `Card` at a fixed position gets neither the live region that makes
the announcement nor the dismissal behaviour people expect from a toast.

`Callout` and `Banner` are dead names for `Notice`. Banner names a position, and no component in
this system owns its own position.

## Where to put an outcome

Put the result where the action was.

- **Inline.** Use a `Text` in the matching tone beside or under the control. Move the tense of
  the verb with it. A button that said "Publish" is followed by the word "Published", not by
  "Success".
- **With a heading.** Compose a `Card` that holds a `Heading` and a `Text`. Put the tone on the
  words. Do not tint the card. The surface family takes no tone, and using `style` to fake one
  writes a fixed colour into an app that then cannot change theme.
- **A decision.** Use an `AlertDialog` when the moment needs an answer before anything else
  happens.
