An interface has four things to say about work it is doing: that it started, how far it has
got, how it ended, and what went wrong. Each has one right answer here. The usual failure is
picking the wrong one rather than making an ugly one.

## Four things to say

| what you say | when | the answer |
|---|---|---|
| Busy | It started and you cannot say how long | `Spinner`, or `loading` on the button that started it |
| Progress | You know the fraction | `Progress` with a `value` |
| Outcome | It finished | Words where the action was, in the tone that names the result |
| Error | It failed, or the input was wrong | The control's invalid state, plus a sentence |

Outcome is the one row with no component. The last section below says what to build instead.

## A busy button keeps its label

Set `loading` on a `Button`. It swaps its leading icon for a spinner, reusing the same box so
nothing shifts, and the label stays. A button that stops saying what it does is worse than one
that changes width.

```tsx
<Button emphasis="loud" loading={saving}>Save changes</Button>
```

A loading button keeps focus and its place in the tab order, announces that it is busy, and
refuses to be activated again. The spinner inside it is hidden from screen readers on purpose,
because the button is already saying it.

Use a standalone `Spinner` for a region with nothing to show yet. It takes its colour from the
text around it and the icon size of whatever it sits in, so it needs neither a colour nor a
size from you.

## Progress when you know the fraction

`Progress` is a track with a fill in it. Give it a number and it shows a fraction; give it
`value={null}` and it sweeps instead. The prop is required, so you have to say "I do not know
how far along this is" rather than arriving there by forgetting.

`Progress` has no `size`, and that absence is a decision. The nearest scale sizes a track as a
fraction of a slider's handle, and a bar has no handle. Its width comes from whatever contains
it, so the Box that owns the row decides.

All three answers compose into one panel: the button says it started, the bar says how far, and
the words say how it ended.

```tsx
<Card size="3">
  <Stack gap="4">
    <Heading size="6">Import files</Heading>

    {done ? (
      <Text size="3" tone="success">Imported 24 files.</Text>
    ) : (
      <Stack gap="2">
        <Progress value={uploading ? uploaded : null} aria-label="Importing files" />
        <Text size="2" emphasis="medium">{uploaded} of 24 files</Text>
      </Stack>
    )}

    <Flex justify="flex-end">
      <Button emphasis="loud" loading={uploading} onClick={start}>Import</Button>
    </Flex>
  </Stack>
</Card>
```

The outcome replaces the bar in the same place, rather than appearing somewhere else on the
screen.

Give every bar a name. A bar with no accessible name and no heading wired to it reports a
number nobody can read. Use a real fraction wherever you have one, because a sweeping bar only
says that something is happening. That is a judgment.

## When the movement is the message

Everything else here stops moving when someone asks their operating system for reduced motion.
A spinner and a sweeping progress bar are the exception, because their movement is not a
response to a state change. The movement *is* the message, so stopping them would remove the
only thing they were saying, and they slow down instead.

Carry that distinction into anything you build. A shimmer, a pulsing dot and a sweeping bar all
say what they say by moving. A hover colour, a panel opening and a focus ring landing are all
responses to a change, so they stop.

## Use a status tone for what it means

Four names carry meaning: `success`, `warning`, `info` and `destructive`. Four more are colour
as data: `blue`, `green`, `orange` and `amber`. Use the second set for a chart series, a
project label or a category, where the colour itself is the information.

`success` and `green` render the same colour today and are still two separate families, because
a meaning has to stay correctable on its own. Do not write `green` when you mean success. It
looks right today and goes wrong the day either name is re-judged.

```tsx
// The tone people reach for
<Text size="2" tone="green">Deployed</Text>

// The one that means it
<Text size="2" tone="success">Deployed</Text>
```

Keep the count low. Four or more data tones on one surface read as a palette rather than a set
of meanings. Three reads as a legend.

## Colour is never the whole message

Colour on its own is not enough (WCAG 1.4.1), so every status the system paints is only half a
message. The border, the ring and the text colour are the system's half. You write the
sentence.

A red field with nothing beside it fails this. A green dot with no label fails it. A chart
keyed only by hue fails it. All three fail worst for exactly the people who cannot see the
colour.

In an error, write what to do next. A colour could never carry that.

## Use a Notice for something that stays true

`Notice` is for a condition that is true right now. Nobody caused it, and it lasts as long as
the condition does. It takes up layout space and never floats, so it cannot cover the thing it
is telling you about. It rests neutral, because the tone says what kind of thing it is rather
than how loudly to say it.

```tsx
<Notice
  tone="warning"
  action={<Button size="2">Add a card</Button>}
  onDismiss={() => setSeen(true)}
>
  Your trial ends in three days.
</Notice>
```

`action` holds one control that fixes the condition. `onDismiss` adds a dismissal that only
acknowledges it. Those are two different verbs. `onDismiss` is a callback with no state of its
own, because a component cannot remember a dismissal across a page reload. Your app has to.

## There is no toast

`Toast` is refused and will not ship. Anything that deserves attention should get it *before*
it runs, and anything that does not deserve attention does not need a report afterwards.

The two cases people build a toast for both belong somewhere else. Undo belongs in an undo
stack, on a control people can find later. A copy confirmation belongs on the button that
copied.

Do not build a substitute either. A Card pinned to a corner gets neither the live region that
makes the announcement nor the dismissal behaviour people expect.

`Callout` and `Banner` are dead names for `Notice`. Banner names a position, and nothing here
owns its own position.

## Where to put an outcome

Put the result where the action was.

- **Inline.** A `Text` in the matching tone beside or under the control, with the verb moved into
  the past. A button that said "Publish" is followed by "Published", not by "Success".
- **With a heading.** A Card holding a `Heading` and a `Text`, with the tone on the words. Do not
  tint the card: surfaces take no tone, and faking one with `style` writes a fixed colour into an
  app that can then no longer change theme.
- **A decision.** An `AlertDialog`, when the moment needs an answer before anything else can
  happen.
