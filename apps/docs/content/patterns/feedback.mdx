An interface has four things to say about work it's doing: that it started, how far it has
got, how it ended, and what went wrong. Each has one right answer. The usual mistake is
picking the wrong answer, not styling it badly.

## Four things to say

| what you say | when | the answer |
|---|---|---|
| Busy | It started and you can't say how long | `Spinner`, or `loading` on the button that started it |
| Progress | You know the fraction | `Progress` with a `value` |
| Outcome | It finished | Words where the action was, in the tone that names the result |
| Error | It failed, or the input was wrong | The control's invalid state, plus a sentence |

Outcome is the one row with no component. The last section says what to build instead.

## A busy button keeps its label

Set `loading` on a `Button`. It swaps its leading icon for a spinner, reusing the same box so
nothing shifts, and the label stays. A button that stops saying what it does is worse than one
that changes width.

```tsx
<Button emphasis="loud" loading={saving}>Save changes</Button>
```

A loading button keeps focus and its place in the tab order, announces that it's busy, and
can't be activated again. The spinner inside it is hidden from screen readers on purpose,
because the button is already saying it.

Use a standalone `Spinner` for a region with nothing to show yet. It takes its colour from the
text around it and the icon size of whatever it sits in, so it needs neither a colour nor a size
from you.

## Progress when you know the fraction

`Progress` is a track with a fill in it. Give it a number and it shows a fraction. Give it
`value={null}` and it sweeps instead. The prop is required, so you have to say "I don't know
how far along this is" rather than arrive there by forgetting.

`Progress` has no `size`, and that absence is a decision. The nearest scale sizes a track as a
fraction of a slider's handle, and a bar has no handle. Its width comes from whatever contains
it, so the Box that owns the row decides.

All three answers compose into one panel: the button says it started, the bar says how far, and
the words say how it ended.

```tsx
<Card size="3">
  <Stack gap="4">
    <Heading size="6">Import files</Heading>

    {done ? (
      <Text size="3" tone="success">Imported 24 files.</Text>
    ) : (
      <Stack gap="2">
        <Progress value={uploading ? uploaded : null} aria-label="Importing files" />
        <Text size="2" emphasis="medium">{uploaded} of 24 files</Text>
      </Stack>
    )}

    <Flex justify="flex-end">
      <Button emphasis="loud" loading={uploading} onClick={start}>Import</Button>
    </Flex>
  </Stack>
</Card>
```

Notice the outcome replaces the bar exactly where the bar was, rather than appearing somewhere
else on the screen.

Give every bar a name. A bar with no accessible name and no heading wired to it reports a number
nobody can read. And use a real fraction wherever you have one. A sweeping bar only says
that something is happening.

## Reduced motion

Everything else here stops moving when someone asks their operating system for reduced motion. A
spinner and a sweeping progress bar are the exception. Their movement doesn't report a state
change. It reports that work is still happening. A stopped spinner looks finished, so they
slow down instead.

Carry that distinction into anything you build. A shimmer, a pulsing dot, and a sweeping bar
all carry their message by moving. A hover colour, a panel opening, and a focus ring landing
are all responses to a change, so they stop.

## Use a status tone for what it means

Four names carry meaning: `success`, `warning`, `info`, and `destructive`. Four more are
colour as data: `blue`, `green`, `orange`, and `amber`. Use the second set when the colour is the
data: a chart series, a project label, a category.

`success` and `green` render the same colour today and are still two separate families,
because you have to be able to correct each meaning on its own. Don't write `green` when you
mean success. It looks right today and goes wrong when either family's value changes.

```tsx
// The tone people reach for
<Text size="2" tone="green">Deployed</Text>

// The one that means it
<Text size="2" tone="success">Deployed</Text>
```

Keep the count down. Four or more data tones on one surface look like a palette rather than
a set of meanings. Three look like a legend.

## Colour is never the whole message

Colour on its own isn't enough (WCAG 1.4.1), so every status the system paints is only half
a message. The border, the ring, and the text colour are the system's half. You write the
sentence.

A red field with nothing beside it fails this, and so do a green dot with no label and a chart
keyed only by hue. All three fail hardest for the people who can't see the colour.

In an error, write what to do next. Colour can't carry that.

## Use a Notice for something that stays true

`Notice` is for a condition that is true right now. Nobody caused it, and it lasts as long as the
condition does. It takes up layout space and never floats, so it can't cover the thing it's
telling you about. It rests neutral, because the tone says what kind of thing it is rather than
how loudly to say it.

```tsx
<Notice
  tone="warning"
  action={<Button size="2">Add a card</Button>}
  onDismiss={() => setSeen(true)}
>
  Your trial ends in three days.
</Notice>
```

`action` holds one control that fixes the condition. `onDismiss` adds a dismissal that only
acknowledges it. Fixing and acknowledging are different jobs, so they're different props.
`onDismiss` is a callback with no state of its own, because a component can't remember a
dismissal across a page reload. Your app has to.

## There is no toast

`Toast` is refused and won't ship. Anything that deserves attention should get it *before*
it runs, and anything that doesn't deserve attention doesn't need a report afterwards.

The two cases people build a toast for both belong somewhere else. Undo belongs in an undo
stack, on a control people can find later. A copy confirmation belongs on the button that
copied.

Don't build a substitute either. A Card pinned to a corner gets neither the live region that
makes the announcement nor the dismissal behaviour people expect.

`Callout` and `Banner` are other libraries' names for `Notice`. Banner names a position, and
no component here owns its own position.

## Where to put an outcome

Put the result where the action was.

- **Inline.** A `Text` in the matching tone beside or under the control, with the verb moved into
  the past. A button that said "Publish" is followed by "Published", not by "Success".
- **With a heading.** A Card holding a `Heading` and a `Text`, with the tone on the words.
  Don't tint the card: surfaces take no tone, and faking one with `style` writes a fixed
  colour into an app that can no longer change theme.
- **A decision.** An `AlertDialog`, when the moment needs an answer before anything else can
  happen.
