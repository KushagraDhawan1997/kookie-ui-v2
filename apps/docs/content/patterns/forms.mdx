A form is a set of labelled values and one action that commits them. This system refuses three
decisions inside that set. Fields do not rank, marks carry no label, and validity is not a prop.
You write the words, the order and the grouping.

## The label is a sibling

A label is prose. `Text` renders prose, and `Text` already resolves every ink role, step and
weight that prose needs. No control in this package takes a `label` prop. A `label` prop would
put a second type system inside a checkbox.

Because the label is a sibling, something has to hold the two together. `Field` is that
something. It supplies the name, the description and the error, and it wires all three to the
control, so you state the words and never the plumbing.

```tsx
<Field>
  <FieldLabel>Work email</FieldLabel>
  <TextField type="email" />
  <FieldDescription>We use this for receipts.</FieldDescription>
</Field>
```

The order is fixed: label, control, description, error. The label sits on the control it names,
and everything about that control sits underneath it.

Write the association yourself only outside a `Field`. Point `htmlFor` at an `id`, or wrap the
control in a `<label>`. Do not rely on proximity.

A `placeholder` is not a label. It disappears when the person types. It renders in the muted ink
role. A placeholder shows real information. It is not the name of the field.

A mark sits beside its label instead of containing it. The row sets the distance between them.
`FieldItem` is that row. Use one for each option in a checkbox group or a radio group. A label
inside an item names the mark beside it, and a description inside an item explains that option
alone.

```tsx
<Field>
  <FieldLabel>Delivery speed</FieldLabel>
  <RadioGroup defaultValue="standard">
    <Stack gap="4">
      <FieldItem>
        <Radio value="standard" />
        <FieldLabel>Standard</FieldLabel>
        <FieldDescription>Three to five business days.</FieldDescription>
      </FieldItem>
      <FieldItem>
        <Radio value="express" />
        <FieldLabel>Express</FieldLabel>
        <FieldDescription>Next business day before noon.</FieldDescription>
      </FieldItem>
    </Stack>
  </RadioGroup>
</Field>
```

## Fields do not rank

`TextField` and `TextArea` take no `emphasis` and no `tone`. The family decides this, and the
absence is not an oversight. Loudness ranks one action against the actions beside it. Every
field is equally there to be filled in, so a form where one field is louder than the next says
nothing.

Show importance in the label, in the order of the form, and in what you leave out. Mark a
required field with `required` on the control. Repeat it in the label in a long form. Only the
action row at the end ranks.

## One action commits the form

Use one loud button on each screen. Give it to the action the form is for. Set every other
button to medium or quiet.

```tsx
<Card size="3">
  <Stack gap="6">
    <Stack gap="2">
      <Heading size="6">New project</Heading>
      <Text size="3" emphasis="medium">Anyone in the workspace can open it.</Text>
    </Stack>

    <Stack gap="5">
      <Field>
        <FieldLabel>Project name</FieldLabel>
        <TextField required />
      </Field>
      <Field>
        <FieldItem>
          <Checkbox />
          <FieldLabel>Keep it private for now</FieldLabel>
        </FieldItem>
      </Field>
    </Stack>

    <Flex justify="flex-end" gap="3">
      <Button>Cancel</Button>
      <Button emphasis="loud">Create project</Button>
    </Flex>
  </Stack>
</Card>
```

Three gaps carry the structure: 3 from a label to its field, 5 between the rows of the form, and
6 between the title, the form and the actions. Only the action row ranks.

Put the actions at the end of the form. Align them to the end edge. A single action with nothing
beside it may take the full width instead. That is a balance decision, and it is a judgment.

Write what the button does. Write "Create project", not "Submit". Keep the same name through the
whole flow.

## Group with space

Put related rows closer together than unrelated rows. The house intervals are gap 3 from a label
to its field, gap 5 between groups, and gap 6 between sections.

Set the gap inside a group at least two steps below the gap around the group. A form where every
gap is the same number reads as one undifferentiated column.

Do not add a `Separator` or a `Card` to do work that the space already does. Enclosure and space
both group, and using both shows the grouping twice. Add a rule only where space cannot group.
A long settings list is the case: the groups already sit at the section interval and something
still has to divide them.

## Validity is a state

There is no `invalid` prop, because nothing chooses to look invalid. The system reads
`aria-invalid`. It also reads Base UI's `data-invalid`, which a control gets for free inside a
`Field`.

```tsx
<TextField
  id="email"
  type="email"
  aria-invalid={emailError ? true : undefined}
/>
```

A checked mark is a resting appearance. An invalid mark is a state. The state wins, so a checked
`Checkbox` that is also invalid looks invalid. The stylesheet enforces this with specificity, not by
which file loads last. The disabled state outranks both.

The border and the ring are the system's half of an error. The message is yours. Colour alone is not
enough (WCAG 1.4.1), so a red field with no words beside it is a composition defect.

## Use TextArea for a paragraph

Use `TextArea` when the value is prose that the person reads back. A description, a note and an
address are the cases. Its box carries the same inset on all four sides. `rows` sets the
starting height in lines of text.

There is no `cols`. Width belongs to the layout that owns the row. The `cols` attribute counts
characters, it predates CSS, and it collides with CSS.

A composer is not a large `TextArea`. A box that needs a toolbar, attachments, a send button and
a growth rule is its own component. Nobody has designed that anatomy. Building it out of a
`TextArea` adds parts to a field.

## Helper text must change a decision

Write helper text that carries what the label cannot. A consequence, a scope, a constraint and
the reason a control is disabled are the cases. Delete a line that repeats the control the reader
can already read.

```tsx
// Filler. The label above already said this.
<Text size="2" emphasis="medium">Enter your work email address.</Text>

// Decision-relevant. A scope the label cannot carry.
<Text size="2" emphasis="medium">Receipts and billing notices go here.</Text>
```

Set helper text at size 2 in the muted ink role, the same step as the label. A helper line two
steps under the controls beside it reads as a mistake.

Do not use size 1 on a composed screen. The muted ink role and the faint ink role say "this
matters less" at a readable size.
