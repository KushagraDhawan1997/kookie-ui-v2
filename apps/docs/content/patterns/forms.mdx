A form is a set of labelled values and one action that saves them. This system takes three
decisions out of your hands: fields do not rank against each other, checkboxes do not carry
their own labels, and validity is not a prop. Everything else — the words, the order, the
grouping — is yours.

## The label is a separate element

A label is prose, and `Text` already handles every size, weight and colour prose needs. So no
control here takes a `label` prop. Adding one would mean building a second, smaller text system
inside a checkbox.

Because the label is a sibling, something has to tie the two together, and that is what `Field`
does. It supplies the name, the description and the error message, and wires all three to the
control, so you write the words and never the plumbing.

```tsx
<Field>
  <FieldLabel>Work email</FieldLabel>
  <TextField type="email" />
  <FieldDescription>We use this for receipts.</FieldDescription>
</Field>
```

The order is fixed: label, control, description, error. The label sits on the control it names,
and everything about that control gathers underneath it.

You only write the association yourself outside a Field: point `htmlFor` at an `id`, or wrap the
control in a `<label>`. Do not rely on things being near each other.

**A placeholder is not a label.** It disappears the moment somebody types, and it is grey. Use
it for a real example of the value, not for the name of the field.

A checkbox or radio sits beside its label rather than containing it, and the row between them
sets the distance. `FieldItem` is that row — use one per option.

```tsx
<Field>
  <FieldLabel>Delivery speed</FieldLabel>
  <RadioGroup defaultValue="standard">
    <Stack gap="4">
      <FieldItem>
        <Radio value="standard" />
        <FieldLabel>Standard</FieldLabel>
        <FieldDescription>Three to five business days.</FieldDescription>
      </FieldItem>
      <FieldItem>
        <Radio value="express" />
        <FieldLabel>Express</FieldLabel>
        <FieldDescription>Next business day before noon.</FieldDescription>
      </FieldItem>
    </Stack>
  </RadioGroup>
</Field>
```

A label inside an item names the control beside it, and a description inside an item explains
that one option.

## Fields do not rank

`TextField` and `TextArea` take no `emphasis` and no `tone`, and that absence is deliberate.
Loudness ranks one action against another, and every field is equally there to be filled in. A
form where one field shouts louder than the next is telling you nothing.

Show importance in the label, in the order of the form, and in what you leave out. Mark a
required field with `required` on the control, and repeat that in the label if the form is long.
Only the buttons at the end rank against each other.

## One button saves the form

Use one loud button per screen, and give it to the thing the form is for. Everything else is
medium or quiet.

```tsx
<Card size="3">
  <Stack gap="6">
    <Stack gap="2">
      <Heading size="6">New project</Heading>
      <Text size="3" emphasis="medium">Anyone in the workspace can open it.</Text>
    </Stack>

    <Stack gap="5">
      <Field>
        <FieldLabel>Project name</FieldLabel>
        <TextField required />
      </Field>
      <Field>
        <FieldItem>
          <Checkbox />
          <FieldLabel>Keep it private for now</FieldLabel>
        </FieldItem>
      </Field>
    </Stack>

    <Flex justify="flex-end" gap="3">
      <Button>Cancel</Button>
      <Button emphasis="loud">Create project</Button>
    </Flex>
  </Stack>
</Card>
```

Three gaps carry the structure there: 3 from a label to its field, 5 between rows of the form,
and 6 between the title, the form and the buttons.

Put the buttons at the end and align them to the end edge. A single button with nothing beside
it can go full width instead — that is a balance decision, and a judgment.

Write what the button does. "Create project", not "Submit". Then keep that word through the rest
of the flow.

## Group with space

Put related rows closer together than unrelated ones. The house intervals are gap 3 from a label
to its field, gap 5 between groups, and gap 6 between sections.

Keep the gap inside a group at least two steps below the gap around it. A form where every gap
is the same number reads as one undifferentiated column.

Do not add a Separator or a Card to do work the spacing has already done. A container groups and
so does distance; using both says it twice. Add a line only where distance genuinely cannot do
it — a long settings list is the real case, where the groups are already at the section interval
and something still has to divide them.

## Validity is a state, not a prop

There is no `invalid` prop, because nothing chooses to *look* invalid. The system reads
`aria-invalid`, and Base UI's `data-invalid`, which a control gets free inside a Field.

```tsx
<TextField
  id="email"
  type="email"
  aria-invalid={emailError ? true : undefined}
/>
```

A ticked checkbox is a resting appearance; being invalid is a state, and the state wins. So a
ticked checkbox that is also invalid looks invalid. Disabled beats both.

The border and the ring are the system's half of an error message. The words are yours. Colour
on its own is not enough (WCAG 1.4.1), so a red field with no text beside it is a composition
problem rather than a missing feature.

## Use TextArea for a paragraph

Reach for `TextArea` when the value is prose somebody will read back: a description, a note, an
address. Its padding is the same on all four sides, and `rows` sets how many lines tall it
starts.

There is no `cols`. Width belongs to the layout that owns the row. The `cols` attribute counts
characters, predates CSS, and fights with it.

A message composer is not a big TextArea. A box that needs a toolbar, attachments, a send button
and a growth rule is its own component, and building it out of a TextArea means bolting parts
onto a field.

## Helper text has to change a decision

Write helper text that carries what the label cannot: a consequence, a limit, a scope, or the
reason a control is disabled. Delete any line that restates what you can already see.

```tsx
// Filler. The label above already said this.
<Text size="2" emphasis="medium">Enter your work email address.</Text>

// Useful. A scope the label cannot carry.
<Text size="2" emphasis="medium">Receipts and billing notices go here.</Text>
```

Set helper text at size 2 in the muted colour — the same size as the label. A helper line two
steps smaller than everything around it reads as a mistake.

Do not drop to size 1 for it. The muted and faint colours already say "this matters less" at a
size people can read.
