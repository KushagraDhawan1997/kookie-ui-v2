Kookie has five ways to put something in front of a person. You can change it inline, open a
`Menu`, open a `Popover`, open a `Dialog`, or show an `AlertDialog`. Each one interrupts more
than the one before it. Use the one that interrupts least and still does the job.

## The five levels

This list starts with the level that interrupts least:

- **Inline.** Change the thing where it is. Examples are an error under the field that caused
  it, a switch that takes effect immediately, and a row that expands. Nothing covers anything,
  and nobody loses their place.
- **A menu.** Use `Menu` for a short list of actions. Use `Select` for a list of values. A menu
  covers a small rectangle. It closes on Escape, on a press outside it, or when you choose an
  item. Everything under it stays readable.
- **A popover.** `Popover` covers a small rectangle, like a menu. It holds the content that you
  put in it: a filter form, a date picker or a short piece of detail. **The page stays live.**
  Nothing dims, focus is not trapped, and you can continue to work around it. A small form goes
  in a popover, not in a dialog.
- **A dialog.** `Dialog` dims the whole app and traps focus. Use it for work that needs space
  away from the page.
- **An alert.** `AlertDialog` covers the app in the same way. A person cannot leave it without
  an answer.

`Tooltip` is not on this list. It interrupts nothing, and it cannot contain anything of its
own. It repeats the name that a control already announces. It shows only to a pointer that
rests on the control. Information that shows only in a tooltip never gets to a keyboard user or
a touch user.

`Sheet` belongs on this list, but it has not shipped yet. Until it ships, use a `Dialog`. Keep
any temporary replacement that you build in one file. Then you have one place to change when
`Sheet` ships.

## Choosing between a popover and a dialog

Both cover a part of the screen, and both hold content that you wrote. The question is not how
much content you have. The question is whether the rest of the app must continue to work.

A popover lets the app continue to work. The page behind it is live. You can read the row that
opened it, scroll, or click somewhere else to close it. Use a popover when the panel is about
something on the page. Examples are filters over a list, a picker next to the field that it
fills, and detail about the item that you pressed.

A dialog stops the app. It dims everything and traps focus. This is correct when the panel is
the task and the page behind it is only context. Use a dialog when a person loses work if they
leave halfway. Also use it when the content needs more space than a panel next to a trigger
can have.

Sometimes you put a small form in a dialog only because you know the dialog component. In that
case, use a popover.

## Choosing between a dialog and an alert

The two panels look almost the same. They are two different things.

A dialog holds your work. You opened it. It contains a form, a picker or a document. You can
leave it the same way that you came in.

An alert stops you with a question. It possibly has no trigger. Something opened it because a
decision must happen before anything else can happen.

One rule separates them: **if a panel needs any control other than its two buttons, it is a
Dialog.** A type-to-confirm field, a checkbox or a form of any size makes it a dialog. With
these controls, the panel holds work and not a choice.

## An alert owns its own content

The contents of an alert are fixed. It has a title, a description, a cancel button and an
action button, in that order. The component sets the layout.

```tsx
<AlertDialog>
  <AlertDialogTrigger render={<Button tone="destructive" emphasis="quiet">Delete</Button>} />
  <AlertDialogContent>
    <AlertDialogTitle>Delete this project?</AlertDialogTitle>
    <AlertDialogDescription>
      Its documents and their history go with it. This cannot be undone.
    </AlertDialogDescription>
    <AlertDialogCancel>Keep it</AlertDialogCancel>
    <AlertDialogAction tone="destructive">Delete project</AlertDialogAction>
  </AlertDialogContent>
</AlertDialog>
```

On an alert, `size` sets everything. It sets the box, the corner, the padding, both text sizes
and both buttons. The system made all of that content, so the system sets its size.

On a `Dialog`, `size` sets the box. It also sets the two parts that the system owns:
`DialogTitle` and `DialogDescription`. It never changes the content that you wrote. The system
does not set the size of text that it does not own.

Write the cancel button first. That order decides focus. The cancel button is first in reading
order and at the start of the row. It also moves correctly for a right-to-left language, with
no extra work. It gets focus because it is the first item in the tab order. So the document
order selects the safe answer for you.

## Why a dialog casts no shadow

The dialog panel does not cast a shadow. A floating element must show what it covers. A dialog
shows this when it darkens the whole window. A shadow under the panel would give the same
information again.

The panel keeps the usual card appearance for the current depth setting. It is raised in a
raised theme, and flat in a flat theme.

Under high contrast, and for a person who asks for reduced transparency, the dark background
changes in one way. It gets more colour and no blur.

## Focus and getting out

Both panels trap focus while they are open. When they close, they return focus to where it came
from. So keyboard focus never goes out of the layer, and it always has a place to go after it
closes.

Neither panel takes a prop for initial focus. The content of the panel decides where focus
goes. For the same reason, the alert puts the cancel button first in its tab order.

A dialog closes on Escape, on a press outside it, and on any `DialogClose` that you add. An
alert closes on Escape and on its two buttons only. **An alert does not close on a press
outside it.** A click by accident must not answer a question about a deletion.

Escape still closes an alert. For a keyboard user, Escape is a different way to cancel. Without
Escape, a keyboard user can leave the panel only if they choose one of the answers.

There is no close button in the corner. This is for the same reason that `Card` has no header
slot: it is layout, not wiring. `DialogClose` puts a real button where your layout needs one. A
screen reader user on a touch device needs that button to leave a trapped panel.

## Name the consequence

Write what will happen. "Delete project" is better than "OK". If the safe answer has a name,
"Keep it" is better than "Cancel". The description gives the consequence and its scope in as
few words as possible.

Put the tone on the action button. Never put it on the panel. The alert stays neutral, and the
destructive action is the only red item in it.

An alert holds exactly one action button. So a loud button is the correct default there. The
fixed parts of the alert apply the rule of one loud action for you. Nobody has to remember it.

## Anything that covers must show its edge

An element that covers part of the screen must show where it ends. In a raised theme, a menu
casts a shadow. In a flat theme, it draws a thin line, because a flat theme draws every edge
with a line. A dialog shows its edge with the dark background.

You do not make this decision in your code. No component takes a shadow prop. If you know the
rule, you do not have to look for one.
