A responsive interface adapts to the person using the screen, which is a different job from a
layout that reflows until nothing overflows.

A phone differs from a desktop in four ways:

- **Targets** are bigger.
- **The pointer** is a thumb.
- **Hover** does not exist.
- **The reachable part** of the screen is the bottom.

Three separate mechanisms answer three separate questions, and the usual mistake is reaching for
the wrong one.

## Reflowing isn't the goal

A missed tap costs almost nothing on a website, so nothing corrects the mistake, which is how
"responsive" changed meaning. It once meant adapting to the person holding the device, and it now
usually means reflowing with no sideways scrollbar.

A layout can pass that test and still place a 24-pixel target under a thumb, inside a menu that
opens only on hover.

The real change between a desktop and a phone is how people interact. A dialog becomes a sheet,
targets grow, and a sidebar stops standing beside the content and opens only when you ask for it.

These are facts about people rather than matters of taste, which makes them defaults you can turn
off rather than options you must turn on.

## Three questions, three mechanisms

- **How much room does this component have?** Container sizes answer this by measuring the
  nearest container you marked.
- **What is touching this?** The pointer setting answers this by following the input device.
- **Which interface should this app show?** Window size classes answer this by measuring the
  window.

These are three different mechanisms rather than one mechanism under three names. Room and
navigation agree on a phone, and they diverge the moment somebody drags a window to half of a
display.

### Container sizes: how much room is there?

A responsive value measures the nearest container you marked rather than the window, which keeps
a component correct wherever you put it. One Flex stacks in a narrow drawer and spreads out in a
main column with no extra code.

```tsx
<Box container>
  <Flex direction={{ initial: "column", md: "row" }} gap="4">
    <TextField placeholder="Search" />
    <Button>Filter</Button>
  </Flex>
</Box>
```

You mark containers yourself, because measurement has a cost: a box that can be measured no
longer sizes itself around its contents. Mark only boxes that already receive a width from your
layout:

- a sidebar with a fixed width
- a column that grows
- a grid cell

Leave every other box unmarked, because a `container` Box that must fit its contents comes out
zero pixels wide, and a development build warns you when that happens.

A value falls back to the root Theme when no marked container sits near the component, and the
root Theme behaves like the window, so a responsive value always resolves.

The three sizes carry names rather than numbers: `sm` at 30rem, `md` at 48rem and `lg` at 64rem.
Apple and Google both use a small set of named classes rather than one breakpoint per
property.

### The pointer setting: what is touching this?

`fine` and `coarse` are two complete sets of measurements, in the way that light and dark are two
complete sets of colours. The components, the size numbers and the rules stay the same, and only
the values change.

This is not a mobile mode and it never measures width. A touchscreen laptop used with a trackpad
reports `fine`, while a tablet with its keyboard removed reports `coarse`, and both answers are
correct.

Two minimum sizes apply, and they are not equally strict:

- **24 pixels is fixed.** WCAG 2.2 sets this minimum at Level AA, and no combination of size,
  density and pointer falls below it.
- **44 pixels is a default you can turn off.** Normal density at size 2 on a touch screen gives
  exactly 44, which is both the Level AAA figure and the Apple figure.

Going below 44 takes a deliberate step, which makes a smaller control a choice rather than an
accident.

A touch screen changes these values:

- control heights
- side padding
- icon size
- the gap between an icon and its label
- control corners
- reading text

It leaves spacing alone, so gaps and gutters stay where they are, because a phone needs more
content per inch rather than less.

```tsx
// `auto` follows the device. Setting it yourself is also how you check
// touch sizing without leaving your desk.
<Theme pointer="coarse">{app}</Theme>
```

### Window size classes: which interface should this be?

A window class selects the shape of your navigation, which is a bottom bar, a narrow rail or a
full sidebar. Decide that shape once, at the top level, from the window, rather than per
container or per component.

`narrow` covers 48rem and below, `wide` covers 75rem and above, and `regular` covers everything
between, so two numbers produce three classes and correcting one threshold can never open a gap
or an overlap. A boundary belongs to the smaller class, which makes a window at exactly 48rem
narrow.

Three classes rather than four, because navigation has three shapes. Material carries a fourth
and a fifth because it has no container queries, and "at this width, add an inspector" is a
question about room that container sizes already answer inside the panel.

The window class reaches neither your colours nor your spacing. Type carries its own rule for
width, geometry comes from the pointer setting, and the generated CSS never mentions a window
class.

## Classes describe room, never hardware

A class reports how much room there is and never names a device, because people run apps in
windows and a device name would lie. An app on half of a 5K display reports `regular` with no
tablet anywhere.

Read the pointer setting to learn about the device, and the window class to learn about the
room.

## Type answers two questions of its own

Type carries two rules, because it answers two different questions:

- **Reading sizes go up** on a touch screen, because you hold a phone close to your face.
- **Display sizes go down** on a narrow window, because a short line has no room for a big
  heading.

The two questions take different answers. Apple publishes one Dynamic Type table for iPhone and
iPad, with body text at 17pt on both, so the reading question does not separate a phone from a
tablet, whereas line length separates a narrow window from a wide one on every device.

Each rule moves only the sizes it must, so both can apply on a phone without conflicting.

## The hook returns null on the server

`useWindowClass()` returns `"narrow" | "regular" | "wide"`, and it returns `null` on the server
and in the browser until the first paint.

The server cannot measure a window and no script changes that, while the first React render must
match the HTML the server sent, so the `null` branch paints first.

Write anything that must be correct before the first paint in CSS. Ship both navigations in the
HTML and let the exported boundary queries choose which one shows, which costs no flash and needs
no script. Use the hook for decisions after mount, such as which component to mount.

```tsx
import { useWindowClass, windowClassQueries } from "@kookie-ui/react";

// windowClassQueries.narrow is "(max-width: 48rem)". Use it in CSS for the first paint.

function Chrome({ children }: { children: React.ReactNode }) {
  const windowClass = useWindowClass(); // null, then "narrow" | "regular" | "wide"

  return (
    <Shell>
      <ShellHeader>
        <ShellTrigger target="sidebar" render={<Button emphasis="quiet" />}>Menu</ShellTrigger>
      </ShellHeader>
      <ShellSidebar>{/* both navigations ship in the HTML */}</ShellSidebar>
      <ShellContent>
        <ShellScroll>{children}</ShellScroll>
      </ShellContent>
    </Shell>
  );
}
```

`Shell` sets the state of an untouched panel in CSS at the narrow boundary, which makes the
frame correct before the hook returns a value.
