A responsive interface adapts to the person who uses the screen. This is a different job from
a layout that reflows until nothing overflows.

A phone is different from a desktop in four ways:

- The targets are bigger.
- The pointer is a thumb.
- Hover does not exist.
- The part of the screen that you can reach is the bottom.

Three separate mechanisms answer three separate questions. The usual mistake is to use the
wrong mechanism.

## Reflowing isn't the goal

On a website, a missed tap costs almost nothing, so nothing corrects the mistake. For this
reason, "responsive" changed its meaning. It once meant "adapt to the person who holds this
device". Now it often means "reflow with no sideways scrollbar".

A layout can pass that test and still put a 24-pixel target under a thumb. That target can be
inside a menu that only opens on hover.

Between a desktop and a phone, the real change is how people interact. A dialog becomes a
sheet. Targets become bigger. A sidebar no longer stays next to the content. It opens only
when you ask for it.

These are facts about people, not matters of taste. So they are defaults that you can turn
off, not options that you must turn on.

## Three questions, three mechanisms

- **How much room does this component have?** Container sizes answer this. They measure the
  nearest container that you marked.
- **What is touching this?** The pointer setting answers this. It follows the input device.
- **Which interface should this app show?** Window size classes answer this. They measure the
  window.

These are three different mechanisms, not one mechanism with three names. On a phone, room and
navigation give the same answer. When a person drags a window to half of a display, the two
answers become different.

### Container sizes: how much room is there?

A responsive value measures the nearest container that you marked. It never measures the
window. So a component is correct wherever you put it. The same Flex stacks in a narrow drawer
and spreads out in a main column, with no extra code.

```tsx
<Box container>
  <Flex direction={{ initial: "column", md: "row" }} gap="4">
    <TextField placeholder="Search" />
    <Button>Filter</Button>
  </Flex>
</Box>
```

You must mark containers, because measurement has a cost. A box that can be measured no longer
sizes itself around its contents. Mark only boxes that already get a width from your layout:

- a sidebar with a fixed width
- a column that grows
- a grid cell

Do not mark other boxes. If a `container` Box must fit its contents, its width becomes zero
pixels. A development build shows a warning when this occurs.

If no container near the component is marked, the value uses the root Theme. The root Theme
behaves like the window. So a responsive value always has a result.

There are three sizes, and they have names, not numbers: `sm` at 30rem, `md` at 48rem and `lg`
at 64rem. Apple and Google both use a small set of named classes, not one breakpoint for each
property.

### The pointer setting: what is touching this?

`fine` and `coarse` are two complete sets of measurements. In the same way, light and dark are
two complete sets of colours. The components, the size numbers and the rules stay the same.
Only the values change.

This is not a mobile mode, and it never measures width. A touchscreen laptop that you use with
a trackpad reports `fine`. A tablet with its keyboard removed reports `coarse`. Both results
are correct.

Two minimum sizes apply, and they are not equally strict:

- **24 pixels is fixed.** WCAG 2.2 sets this minimum at Level AA. No combination of size,
  density and pointer goes below it.
- **44 pixels is a default that you can turn off.** On a touch screen, normal density at size 2
  gives exactly 44. This is the Level AAA figure, and it is also the Apple figure.

To make a control smaller than 44, you must do it on purpose. So a smaller control is a choice,
not an accident.

A touch screen changes these values:

- control heights
- side padding
- icon size
- the gap between an icon and its label
- control corners
- reading text

It does *not* change spacing. Gaps and gutters stay the same, because a phone needs more
content in each inch, not less.

```tsx
// `auto` follows the device. Setting it yourself is also how you check
// touch sizing without leaving your desk.
<Theme pointer="coarse">{app}</Theme>
```

### Window size classes: which interface should this be?

A window class selects the shape of your navigation. The shape is a bottom bar, a narrow rail
or a full sidebar. Decide the shape one time, at the top level, from the window. Do not decide
it for each container or for each component.

`narrow` is 48rem and less. `wide` is 75rem and more. `regular` is all widths between the two.
Two numbers give three classes. So if you correct one threshold, it cannot cause a gap or an
overlap. A boundary belongs to the smaller class, so a window at exactly 48rem is narrow.

There are three classes, not four, because navigation has three shapes. Material has a fourth
and a fifth class because it has no container queries. "At this width, add an inspector" is a
question about room. Container sizes already answer that question inside the panel.

The window class does not change your colours or your spacing. Type has its own rule for width.
Geometry comes from the pointer setting. The generated CSS never refers to a window class.

## Classes describe room, never hardware

A class tells you how much room there is. It never names a device. People run apps in windows,
so a device name would be wrong. An app on half of a 5K display reports `regular`, and no
tablet is present.

Use the pointer setting to learn about the device. Use the window class to learn about the room.

## Type answers two questions of its own

Type has two rules, because it answers two different questions:

- Reading sizes go **up** on a touch screen, because you hold a phone close to your face.
- Display sizes go **down** on a narrow window, because a short line has no room for a big
  heading.

These two questions do not have the same answer. Apple has one Dynamic Type table for iPhone
and iPad, and body text is 17pt on both. So the reading question does not separate a phone from
a tablet. Line length *does* separate a narrow window from a wide window, on all devices.

Each rule changes only the sizes that it needs. So both rules can apply on a phone, and they
do not conflict.

## The hook returns null on the server

`useWindowClass()` returns `"narrow" | "regular" | "wide"`. On the server, it returns `null`. In
the browser, it also returns `null` until the first paint.

The server cannot measure a window, and no script can change that. The first React render must
match the HTML from the server, so the `null` branch paints first.

If something must be correct before the first paint, write it in CSS. Put both navigations in
the HTML. Then let the exported boundary queries select the navigation that shows. This gives
no flash and needs no script. Use the hook for decisions after mount, for example which
component to mount.

```tsx
import { useWindowClass, windowClassQueries } from "@kookie-ui/react";

// windowClassQueries.narrow is "(max-width: 48rem)". Use it in CSS for the first paint.

function Chrome({ children }: { children: React.ReactNode }) {
  const windowClass = useWindowClass(); // null, then "narrow" | "regular" | "wide"

  return (
    <Shell>
      <ShellHeader>
        <ShellTrigger target="sidebar" render={<Button emphasis="quiet" />}>Menu</ShellTrigger>
      </ShellHeader>
      <ShellSidebar>{/* both navigations ship in the HTML */}</ShellSidebar>
      <ShellContent>
        <ShellScroll>{children}</ShellScroll>
      </ShellContent>
    </Shell>
  );
}
```

`Shell` sets the state of an untouched panel in CSS at the narrow boundary. So the frame is
correct before the hook returns a value.
