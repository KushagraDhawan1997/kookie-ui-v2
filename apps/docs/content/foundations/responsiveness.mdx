A responsive interface adapts to the person using it, not only to the width of the screen. A
layout that reflows until nothing overflows can still put a small target under a thumb, or hide a
control behind a hover that a phone can't do.

A phone differs from a desktop in four ways that matter for an interface:

- **Targets** need to be larger, because a finger is less precise than a pointer.
- **Hover** doesn't exist.
- **Room** is limited, so navigation needs a different shape.
- **Reading distance** is shorter, because you hold a phone close to your face.

KookieUI handles these with three separate mechanisms, each answering a different question. Most
responsive mistakes come from using the wrong one.

## Three questions, three mechanisms

- **How much room does this component have?** Container sizes answer this by measuring the
  nearest container you've marked.
- **What is the person pointing with?** The `pointer` setting answers this by following the input
  device.
- **Which interface should the app show?** Window classes answer this by measuring the window.

On a phone held upright, all three give the same kind of answer. They separate as soon as
somebody uses a touchscreen laptop, or drags a desktop window to half the width of the display.

## Container sizes

A responsive value measures the nearest container you've marked, not the window. This keeps a
component correct wherever you put it, so one `Flex` can stack in a narrow drawer and sit in a
row in a wide column without extra code.

```tsx
<Box container>
  <Flex direction={{ initial: "column", md: "row" }} gap="4">
    <TextField placeholder="Search" />
    <Button>Filter</Button>
  </Flex>
</Box>
```

There are three sizes: `sm` from 30rem, `md` from 48rem and `lg` from 64rem. Each applies once the
container is at least that wide, on top of the `initial` value. The sizes have names rather than
pixel values, and there are only three, which follows the small sets of size classes that Apple
and Google use.

Mark a container with the `container` prop on a `Box`, `Flex`, `Stack` or `Grid`. A marked box can
no longer size itself around its contents, so mark only boxes that already get their width from
the layout:

- a sidebar with a fixed width
- a column that grows to fill the space
- a grid cell.

If you mark a box that has to fit its contents, it comes out zero pixels wide, and a development
build warns you. When no marked container sits above a component, its responsive values measure
the root `Theme`, which is as wide as the window, so a responsive value always resolves.

## The pointer setting

The `pointer` setting on a `Theme` has two main values, `fine` for a mouse or trackpad and
`coarse` for a finger. Each has its own complete set of measurements, in the same way that light
and dark mode have their own colours. Your components and props stay the same, and only the
values change.

The default, `auto`, follows the device's main input and never measures width. A touchscreen
laptop used with its trackpad reports `fine`, and a tablet with its keyboard removed reports
`coarse`. Both answers are correct.

Two tap sizes apply, and they aren't equally strict:

- **24 pixels is a fixed minimum.** WCAG 2.2 sets it at Level AA, and no combination of size,
  density and pointer goes below it.
- **44 pixels is the default on touch screens.** A size 2 control at default density on a touch
  screen is exactly 44 pixels tall, which is the WCAG Level AAA figure and Apple's figure.

A touch control only goes below 44 pixels when you choose size 1 or compact density, so a smaller
control is always your decision.

On a touch screen, these values change:

- control heights
- side padding
- icon size
- the gap between an icon and its label
- control corners
- body text size.

The spacing between components stays the same, so gaps and page gutters don't grow on a phone.

```tsx
// "auto" follows the device. Set "coarse" yourself to check touch sizes on a laptop.
<Theme pointer="coarse">{app}</Theme>
```

## Window classes

A window class tells you which shape your navigation should take: a bottom tab bar, a narrow
rail or a full sidebar. Decide this once, at the top of your app, from the size of the window.
Don't decide it separately in each container or component.

There are three classes. `narrow` covers windows up to 48rem wide, `wide` covers 75rem and wider,
and `regular` covers everything in between. A window exactly on a boundary belongs to the smaller
class, so a window 48rem wide is `narrow`. Because two numbers define all three classes,
adjusting one of them can never leave a gap or an overlap.

There are three classes because navigation has three shapes. A question such as "add an inspector
when there's enough room" is about the room inside a panel, and container sizes already answer
it.

The class names describe room, never hardware. People run apps in windows, so a device name
would often be wrong: an app on half of a large desktop display is `regular` with no tablet
involved. Use the pointer setting to learn about the device, and the window class to learn about
the room.

Window classes don't change colours, spacing or sizes, and the generated CSS never refers to
them. They only help you choose which components to render.

## Text on phones and narrow windows

Text size changes in two situations, for two different reasons:

- **Body text gets larger on a touch screen**, because you hold a phone close to your face.
- **Large headings get smaller in a narrow window**, because a short line has no room for them.

Each rule changes only the text sizes it needs to, so both can apply on a phone without
conflicting. The first follows the pointer setting rather than the width, because the reading
distance is the same on a phone and a tablet. Apple publishes one Dynamic Type table for iPhone
and iPad, with body text at 17 points on both.

## Render the right navigation before the first paint

`useWindowClass()` returns `"narrow"`, `"regular"` or `"wide"`. On the server, and in the browser
until after the first paint, it returns `null`.

The server can't measure the window, and React's first render in the browser must match the HTML
that the server sent. So the first paint always uses the `null` result, whatever the real window
size is.

Anything that must be correct on the first paint belongs in CSS. Put both navigations in the
HTML, and use the queries in `windowClassQueries` in your stylesheet to show the right one. That
way there's no flash and no script. Use the hook only for decisions that can wait until after the
page has mounted.

```tsx
import { Button, ShellTrigger, useWindowClass, windowClassQueries } from "@kookie-ui/react";

// For CSS: windowClassQueries.narrow is "(max-width: 48rem)".

function InspectorToggle() {
  const windowClass = useWindowClass();

  // Before the page mounts, the window class is unknown. Show nothing rather than guess.
  if (windowClass !== "narrow") return null;

  return (
    <ShellTrigger target="inspector" render={<Button emphasis="quiet" />}>
      Details
    </ShellTrigger>
  );
}
```

`Shell` handles its own panes in CSS. In a narrow window, a sidebar you haven't opened or closed
yourself starts closed and opens over the content, so the frame is correct before the hook
returns a value.
