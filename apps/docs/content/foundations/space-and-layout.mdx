Every distance on a KookieUI screen belongs to a container, never to the thing inside it. Four
components do the placing, one scale supplies the distances, and one theme setting shifts that
scale for the whole app.

## Components do not set their own outer spacing

The distance between two things is the `gap` on whatever contains them. No control takes a
margin prop, and none ever will.

The reason is that a margin describes a relationship rather than a property of a thing. How far
a button should sit below the field above it depends on what that neighbour is, how dense your
theme is, and what the group is doing, and the button can see none of those from the inside. A
component that ships its own margin has answered a question it could not ask, which is why
every layout built on top of it starts by cancelling that margin.

When you do need a one-off distance, wrap it. A wrapper is visible in the file; a margin buried
inside a control is not.

```tsx
// Does not compile. A control has no margin prop.
<Button mt="4">Save</Button>

// The distance belongs to the container.
<Stack gap="4">
  <TextField placeholder="Project name" />
  <Button>Save</Button>
</Stack>

// A one-off distance is a wrapper you can see.
<Box mt="6">
  <Button>Save</Button>
</Box>
```

## Box does the work

`Box` takes the full set of props: spacing, width and height, a few structural keywords, and
the props a flex or grid child needs. `Flex`, `Grid` and `Stack` are Box with a fixed display
and a shorter list. None of the three adds any CSS.

The shorter list is the point. Plain CSS lets you put any property on any element and quietly
ignores the ones that do not apply. Here, `columns` on a `Flex` does not compile.

Use `Stack` when things go down the page. Use `Flex` when direction or alignment is the
decision. Use `Grid` when the arrangement is two-dimensional. Use `Box` when you need something
the narrower components will not accept. Anything outside the prop list is one `style` away,
and your `style` is applied last, so it wins.

```tsx
<Stack gap="4">
  <Flex align="center" justify="space-between" gap="3">
    <Heading size="6">Members</Heading>
    <Button>Invite</Button>
  </Flex>
  <Grid columns="repeat(2, 1fr)" gap="4">{/* … */}</Grid>
</Stack>
```

## There are two layers of spacing

`--space-1` through `--space-12` is the raw scale. The small end goes up in small steps,
because 12, 16 and 24 pixels are visibly different and you use all three constantly. The large
end doubles, because past a certain size an eight-pixel difference stops being visible.

`--layout-space-1` through `--layout-space-12` sits on top of it, and that second layer is what
every layout distance actually reads: `gap` on Flex, Stack and Grid, `p` and `m` on any
primitive, and the padding inside a card.

When you write `gap="4"` you get step 4 of the current density, not a permanent alias for 12
pixels. Without that middle layer the number would be a unit conversion, and you might as well
write the pixels.

```css
/* the raw scale, which density never touches */
--space-4: calc(12px * var(--scale));

/* the layer that gap="4" and p="4" actually read */
--layout-space-4: var(--space-4);   /* normal density */
--layout-space-4: var(--space-3);   /* compact density */
```

The line between them is exact. The layer carries every distance *between* two things, and
every distance from a container's edge to its contents. The raw scale stays raw inside a
control, because a button's padding and the gap between its icon and its label already respond
to density through their own values. Sending them through the layer as well would shrink them
twice.

You can also pass a real length. `gap="13px"` goes straight through, and stays visible in the
file as the exception it is.

## Density changes which step you get, and nothing else

`density` is a Theme setting with three levels: `compact`, `default` and `comfortable`. It is
an app-level choice, not a per-component one.

Each level is a set of hand-picked numbers rather than a multiplier. It restates every control
height and padding directly, and it picks twelve steps out of the raw scale, which itself never
moves. Nothing lands on 26.78 pixels, and any single value can be corrected without dragging
the others with it. A multiplier could only move a whole level at once, which would make every
small correction global. That is a judgment.

Density leaves two things alone. It never touches the raw scale, so a compact app cannot
collapse the big gutters around a page: the small steps shift down by one and steps 9 to 12
stay where they are. It also never touches text size, which is the whole reason the setting
exists. Density buys you room without changing how big the words are. If you want the words to
change too, you want `size`.

```tsx
<Theme density="compact">
  <Stack gap="4">{/* every distance below tightens */}</Stack>
</Theme>
```

## Responsive values respond to the container

Any layout prop can take one value per size, written as an object. `initial` is the base, and
`sm`, `md` and `lg` layer on top.

Those sizes measure the nearest measurable ancestor rather than the window, so the same Grid
behaves correctly in a narrow sidebar and in a wide main column without you writing two
versions.

You opt into measuring, because CSS makes you trade for it. A box that can be measured can no
longer size itself around its contents. Put `container` on something the layout already gives a
width to, or set `width`, `flexGrow` or `flexBasis` yourself. A `container` Box left to
shrink-wrap renders zero pixels wide, and a development build warns you when that happens.

```tsx
<Box container>
  <Flex direction={{ initial: "column", md: "row" }} gap={{ initial: "3", md: "5" }}>
    {/* … */}
  </Flex>
</Box>
```

Window size is a different question with a separate answer. Container sizes ask how much room
this component has. `useWindowClass()` returns `narrow`, `regular` or `wide`, and it asks which
shape the whole interface should take: a bottom bar, a narrow rail, or a full sidebar. You
answer that once, at the top. It is a hook rather than a token because the answer changes which
components you render, not how they look.

## Let a picture reach the edge with bleed

A card owns its padding, so a picture that runs edge to edge has to cancel a distance it cannot
see. `bleed` is the one named value on the spacing scale: on any margin prop, it resolves to
the negative of the padding of whatever surface contains it.

It is a value rather than a prop, which means every per-side and per-size spelling you already
know still works. `mt="bleed" mx="bleed"` bleeds the top and the sides. The nearest surface
wins, so a card inside a dialog bleeds to the card. Outside any surface it resolves to zero.

Shell panes are surfaces too, so `bleed` is also how a canvas or an image reaches the edges of
a pane. A `ShellScroll` needs no help: a scroll area placed directly inside a surface already
reaches the edges and re-pads itself inside.

`bleed` works on margins only. Padding and `gap` cannot take a negative length, so the word
reaches CSS unchanged and CSS rejects it somewhere you can see.

```tsx
<Card size="3">
  <Stack gap="3">
    <Box mt="bleed" mx="bleed">
      <img src="/cover.jpg" alt="" />
    </Box>
    <Heading size="6">Northern route</Heading>
    <Text size="3">Two days, one pass, and a ferry at the end.</Text>
  </Stack>
</Card>
```

Every other system ships a component part for this: a card section, a media slot, a cover. This
one does not, because a component only gets fixed parts when something non-visual forces them,
such as wiring up a label or announcing a role. A picture forces nothing.
