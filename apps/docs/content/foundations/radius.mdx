One word on your Theme sets how round your whole app is. The setting has five values, and
`full` is the default. Each type of component calculates its own corner from that word. So a
button becomes a pill, and the card around it stays a card. No component takes a corner prop.

## One word, five sets of values

Set the radius one time, on the Theme:

```tsx
<Theme radius="medium">
  <App />
</Theme>
```

The values are `none`, `small`, `medium`, `large` and `full`. `full` is the default. In this
system, buttons are pills and rows are capsules by default.

Each setting is a set of hand-picked values. It isn't a multiplier of one number, and `full`
shows why. CSS limits a corner to half the shorter side of the box. So one very large number
makes a button a correct pill, and it also makes a dialog a lozenge. No single multiplier gives
both results. Hand-picked values can. At `full`, buttons are true capsules, and cards use the
values of `large`.

The distance between values increases as the values get larger. At larger values, it is more
difficult to see a difference in roundness. At the small end, you can see a difference of 2
pixels. At the large end, a card with 30 pixels and a card with 32 pixels look the same. This
curve is a judgment.

Why is it one word and not a prop on each component? If one card is rounder than the next card,
the corner tells you nothing. Roundness looks like a property of the product only when no
single screen can change it.

## Ask for the family, not the number

Each of five families has its own set of values.

```css
--radius-control-2   /* a size-2 button, field, or select trigger */
--radius-surface-3   /* a size-3 card */
--radius-overlay-3   /* a size-3 dialog */
--radius-row-2       /* a size-2 menu or select row */
--radius-mark-2      /* a size-2 checkbox */
```

In your own CSS, write `--radius-control-2`, not `--radius-2`. Today, the numbers are the same.
In the future, they will be different. If you use the wrong family, you get a wrong shape, and
you don't get a build error.

The families also use different indexes. Control corners change with density. At a fixed
corner, a control with more room inside it looks square. Card corners and dialog corners change
only with the size number. Density changes a card through its padding.

**A corner is always approximately the same fraction of its box.** So checkboxes and rows have
their own values. A checkbox isn't on the control height scale. The height of a row is its line
of text plus a small inset. If you give either of them the corner of another family, the value
is calculated for a box that it doesn't have. You get a circle where a square is necessary, or
a corner that the browser doesn't draw.

## A panel's corner comes from the rows inside it

A panel that contains rows calculates its corner from the corner of its rows:

**panel corner = row corner + panel padding**

Two curves with the same centre fit together cleanly. If the centres are different, the curves
cut into each other, or they leave a visible gap next to each row.

The system keeps this relationship at every size and every setting. You don't calculate it, and
you don't give an offset.

The same rule applies one level higher. A dialog uses the corner of a card that is one size
larger. So the dialog is rounder than the cards inside it. `Surface` uses the same values. A
container of panels must be rounder than the panels in it.

At zero, the calculation has no answer. So `none` means no curve. A square panel doesn't get a
curve from its padding.

## Four shapes that `none` doesn't square

`none` makes everything square, including pills. Four shapes keep their curve, because in each
of them, the shape carries the meaning.

- A **radio** is a circle. A square radio looks like a checkbox.
- The **slider handle** and the **switch thumb** are circles. A square handle looks like a
  bead that can't move. Every platform makes them round.
- The **switch track** is a capsule, because a circle fits only inside a curve. A round thumb
  in a square channel looks like a bead in a rail, and that is a slider.

The rule also works in the opposite direction. At `full`, a checkbox stops at the corner of
`large`, because a circular checkbox looks like a radio. Roundness stops at that point, and it
never decreases.

These four are the only exceptions.

## Change the corner for a region, not for one component

No component takes a `radius` prop. If one region really needs a different corner, put a nested
Theme on an element that your layout already has:

```tsx
<Theme radius="medium">
  <Stack gap="5">
    <Card size="3">
      <Stack gap="3">
        <Heading size="6">Billing</Heading>
        <TextField size="2" placeholder="Card number" />
        <Button emphasis="loud">Save card</Button>
      </Stack>
    </Card>

    <Theme radius="none" render={<section />}>
      <Card size="3">
        <Text size="3" emphasis="medium">Legacy invoices</Text>
      </Card>
    </Theme>
  </Stack>
</Theme>
```

The first card, its field and its button all use the `medium` values. Each uses the values of
its own family. The nested section makes everything inside it square. The radio, the handles and
the switch track keep their shapes.

One line sets the corner for a region, and each person who reads the file can see it. With a
prop on each card, one screen could have nine different decisions.
