One word on your Theme sets how round your whole app is. The setting has five values, and
`full` is the default. Each kind of component works out its own corner from that word, so a button
becomes a pill while the card holding it stays a card. No component takes a corner prop.

## One word, five sets of values

Set it once, on the Theme:

```tsx
<Theme radius="medium">
  <App />
</Theme>
```

The values are `none`, `small`, `medium`, `large`, and `full`, and `full` is what you get by
default. Pill-shaped buttons and capsule rows are this system's normal look.

Each setting is a set of hand-picked values rather than a multiplier over one number, and
`full` shows why. CSS caps a corner at half the shorter side of the box, so one very large
number gives a button a perfect pill and turns a dialog into a lozenge. No single factor
produces both results. Hand-picked values produce both: at `full`, buttons get a true capsule,
and cards hold at the values `large` uses.

The values get further apart as they get bigger, because differences in roundness are harder
to see at larger values. At the small end, 2 pixels is a visible difference. At the large end,
30 and 32 pixels on a card look identical. That curve is a judgment.

Why one word rather than a prop per component? In an app where one card is rounder than the
next, the corner tells you nothing. Roundness only looks like a property of the product when
no individual screen can change it.

## Ask for the family, not the number

Five families each have their own set of values.

```css
--radius-control-2   /* a size-2 button, field, or select trigger */
--radius-surface-3   /* a size-3 card */
--radius-overlay-3   /* a size-3 dialog */
--radius-row-2       /* a size-2 menu or select row */
--radius-mark-2      /* a size-2 checkbox */
```

In your own CSS, write `--radius-control-2` rather than `--radius-2`. The numbers happen to
agree today. They will stop agreeing, and using the wrong family gives you a wrong shape rather
than a build error.

The families are also indexed differently. Control corners follow density, because a control
with more room inside it looks square at a fixed corner. Card and dialog corners follow only
the size number, because density reaches a card through its padding instead.

**A corner is always roughly the same fraction of the box it's drawn on.** That's why
checkboxes and rows have their own values. A checkbox isn't on the control height scale, and a
row's height is its line of text plus a small inset. Give either of them another family's
corner and you get a value calculated against a box they don't have: a circle where a square
belongs, or a corner the browser refuses to draw.

## A panel's corner comes from the rows inside it

A panel that holds rows works out the row's corner from its own:

**panel corner = row corner + panel padding**

Two curves that share a centre nest cleanly. Two that don't either cut into each other or
leave a visible gap beside every row.

The system holds that relationship at every size and every setting. You never calculate it,
and there's no offset to pass.

The same idea applies one level up. A dialog takes the corner of a card one size larger, so
it's rounder than the cards inside it. `Surface` uses the same values, because anything holding
panels needs to be rounder than the panels it holds.

At zero the arithmetic has no answer, so `none` really means none. It doesn't round a square
panel by its own padding.

## Four shapes that `none` doesn't square

`none` squares everything, including pills. Four shapes keep their curve, because in each one
the shape carries the meaning.

- A **radio** is a circle. A square radio looks like a checkbox.
- The **slider handle** and the **switch thumb** are circles. A square handle looks like a
  bead that got stuck. Every platform ships them round.
- The **switch track** is a capsule, because a circle only nests inside a curve. A round thumb
  in a square channel looks like a bead in a rail, which is a slider.

The rule also works in the other direction. At `full`, a checkbox stops at the corner `large`
uses, because a circular checkbox looks like a radio. Roundness stops increasing, and it never
reverses.

Those four are the only exceptions.

## Change the corner for a region, not for one component

No component takes a `radius` prop. When one region genuinely needs a different corner, nest a
Theme on an element your layout already has:

```tsx
<Theme radius="medium">
  <Stack gap="5">
    <Card size="3">
      <Stack gap="3">
        <Heading size="6">Billing</Heading>
        <TextField size="2" placeholder="Card number" />
        <Button emphasis="loud">Save card</Button>
      </Stack>
    </Card>

    <Theme radius="none" render={<section />}>
      <Card size="3">
        <Text size="3" emphasis="medium">Legacy invoices</Text>
      </Card>
    </Theme>
  </Stack>
</Theme>
```

The first card, its field, and its button all use the `medium` values, each from its own
family. The nested section squares everything inside it, while the radio, the handles, and the
switch track keep their shapes.

One line decides for a region, and anyone reading the file can see it. A prop on every card
would allow nine decisions on one screen.
