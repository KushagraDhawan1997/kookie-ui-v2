One word on your Theme sets how round your whole app is. The setting takes five values, with
`full` as the default, and each category of component calculates its own corner from that word,
so a button becomes a pill while the card around it stays a card. No component accepts a corner
prop.

## One word, five sets of values

Set the radius one time, on the Theme:

```tsx
<Theme radius="medium">
  <App />
</Theme>
```

The setting takes `none`, `small`, `medium`, `large` and `full`, and `full` is the default,
which makes buttons pills and rows capsules unless you say otherwise.

Each setting holds a set of hand-picked values rather than a multiplier of one number, and
`full` shows why. CSS limits a corner to half the shorter side of the box, so a single very
large number turns a button into a correct pill and a dialog into a lozenge at the same time.
No multiplier produces both results, whereas hand-picked values do: at `full`, buttons become
true capsules while cards take the values of `large`.

The distance between values widens as the values grow, because a difference in roundness gets
harder to see at the large end. You can see a difference of 2 pixels at the small end, while a
card at 30 pixels and a card at 32 pixels look identical at the large end. This curve is a
judgment.

The setting is one word rather than a prop on each component because a corner tells you nothing
once one card is rounder than the next. Roundness reads as a property of the product only when
no single screen can change it.

## Ask for the family, not the number

Each of five families has its own set of values.

```css
--radius-control-2   /* a size-2 button, field, or select trigger */
--radius-surface-3   /* a size-3 card */
--radius-overlay-3   /* a size-3 dialog */
--radius-row-2       /* a size-2 menu or select row */
--radius-mark-2      /* a size-2 checkbox */
```

Write `--radius-control-2` in your own CSS rather than `--radius-2`. The numbers agree today and
will diverge later, and the wrong family gives you a wrong shape without a build error.

The families also read different indexes. Control corners change with density, because a control
with more room inside it looks square at a fixed corner. Card corners and dialog corners change
only with the size number, since density reaches a card through its padding.

**A corner always takes approximately the same fraction of its box**, which is why checkboxes and
rows carry their own values. A checkbox does not sit on the control height scale, and a row's
height is its line of text plus a small inset. Giving either of them another family's corner
applies a value calculated for a box it does not have, which produces a circle where a square
belongs, or a corner the browser never draws.

## A panel's corner comes from the rows inside it

A panel that contains rows calculates its corner from the corner of its rows:

**panel corner = row corner + panel padding**

Two curves that share a centre fit together cleanly, while curves with different centres cut
into each other or leave a visible gap beside each row.

The system holds this relationship at every size and every setting, so you neither calculate it
nor supply an offset.

The same rule applies one level higher. A dialog takes the corner of a card one size larger,
which makes it rounder than the cards inside it, and `Surface` reads the same values, because a
container of panels must stay rounder than the panels it holds.

At zero the calculation has no answer, so `none` means no curve, and a square panel never gains
one from its padding.

## Four shapes that `none` doesn't square

`none` squares everything, including pills, except for four shapes that keep their curve because
in each of them the shape carries the meaning.

- **A radio stays a circle**, because a square radio reads as a checkbox.
- **The slider handle and the switch thumb stay circles**, because a square handle reads as a
  bead that cannot move. Every platform draws them round.
- **The switch track stays a capsule**, because a circle fits only inside a curve. A round thumb
  in a square channel reads as a bead in a rail, which is a slider.

The rule also runs in the opposite direction. At `full` a checkbox stops at the corner of
`large`, because a circular checkbox reads as a radio, so roundness halts there and never
reverses.

These four are the only exceptions.

## Change the corner for a region, not for one component

No component accepts a `radius` prop. Put a nested Theme on an element your layout already has
when one region genuinely needs a different corner:

```tsx
<Theme radius="medium">
  <Stack gap="5">
    <Card size="3">
      <Stack gap="3">
        <Heading size="6">Billing</Heading>
        <TextField size="2" placeholder="Card number" />
        <Button emphasis="loud">Save card</Button>
      </Stack>
    </Card>

    <Theme radius="none" render={<section />}>
      <Card size="3">
        <Text size="3" emphasis="medium">Legacy invoices</Text>
      </Card>
    </Theme>
  </Stack>
</Theme>
```

The first card, its field and its button all take the `medium` values, each from its own family,
while the nested section squares everything inside it except the radio, the handles and the
switch track.

One line sets the corner for a region, and everybody who reads the file can see it. A prop on
each card would let one screen carry nine different decisions.
