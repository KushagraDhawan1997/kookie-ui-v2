Radius is a `Theme` axis. One word sets the corner for the whole application. There are five
levels, and `full` is the default. Each family derives its own corner from that word, so a
control becomes a pill while the card holding it stays a card. No component takes a corner prop.

## One word, five palettes

Set the level one time, on the `Theme`:

```tsx
<Theme radius="medium">
  <App />
</Theme>
```

The levels are `none`, `small`, `medium`, `large` and `full`. `full` is the default. Pill
controls and capsule rows are this system's resting appearance.

Each level is a designed palette that the generator emits at build time. A level is not a
multiplier over one scale.

A multiplier moves every step together, so you cannot correct one corner alone. `full` shows why
this matters. CSS limits `border-radius` to half the smaller dimension. A very large number
therefore gives a control a correct pill, and gives a dialog a lens shape. One factor cannot
produce both results. A designed palette can. At `full`, the control band states the capsule and
the surface band holds at the values of `large`.

The palette is geometric rather than even, because the eye reads radius non-linearly. The steps
are close together at the small end and far apart at the large end, where 30 pixels and 32
pixels on a card look the same. That curve is a judgment.

One word rather than one prop per component: in a system where one card is rounder than the
next, the corner states nothing. A corner reads as a property of the product only when nothing
local can change it.

## Reference the family, never the number

There are five families and five bands.

```css
--radius-control-2   /* a size-2 button, field or select trigger */
--radius-surface-3   /* a size-3 card */
--radius-overlay-3   /* a size-3 dialog */
--radius-row-2       /* a size-2 menu or select row */
--radius-mark-2      /* a size-2 checkbox */
```

Write `--radius-control-2` in a block you own. Do not write `--radius-2`. The numbers agree
today. They stop agreeing when a scale is renumbered, and the wrong-family value is a shape
error rather than a build error.

The bands use different indexes. Control radius belongs to the density set, because a control
with more room reads square at a fixed corner. Surface radius and overlay radius follow the size
index alone, because density reaches a card through its padding.

**A corner holds a near-constant fraction of the box it is drawn on.** That is why a mark and a
row have bands of their own. A mark is not on the control height ladder, and a row's box is its
text line plus one designed inset. A family that reads another family's band gets a corner
computed against a box it does not have. The result is a circle where a square belongs, or a
corner the browser refuses to paint.

## Curves nest

A pane that holds rows derives the row's corner from its own corner:

**panel corner = row corner + panel padding**

Two curves that share a centre nest correctly. Two curves that do not share a centre either cut
into each other or leave a gap at every row.

The system holds this relationship for each size and each level. You never calculate it, and
there is no offset to pass.

The same rule applies one band over. An overlay wears the corner of the card one size above it,
so a dialog out-rounds the cards inside it. `Surface` reads that band, because a pane that holds
panes must out-round its contents.

The arithmetic has no answer at zero, so `none` means none. It does not round a square panel by
its own padding.

## Four corners that `none` does not reach

`none` squares everything, including the pill. A switch with an exception is not a switch.

Four shapes survive `none`. Each one survives because the shape states the role.

- A **radio** is a circle. A square radio reads as a checkbox.
- The **slider grip** and the **switch thumb** are circles. A square handle reads as a bead that
  stopped moving. Every platform ships them round.
- The **switch track** is a capsule. A circle nests only in a curve. A round thumb in a square
  channel reads as a bead in a rail, which is a slider.

The system applies the same rule in the other direction. Under `full`, the checkbox stops at the
corner of `large`, because a circular checkbox reads as a radio. A corner stops getting rounder.
It never reverses.

There are four exceptions and there is no fifth. A shape that escapes `none` without a written
reason is a defect.

## Change the corner for a region, not for a component

No component takes a `radius` prop. When one region needs a different corner, nest a `Theme` on
an element the layout already has:

```tsx
<Theme radius="medium">
  <Stack gap="5">
    <Card size="3">
      <Stack gap="3">
        <Heading size="6">Billing</Heading>
        <TextField size="2" placeholder="Card number" />
        <Button emphasis="loud">Save card</Button>
      </Stack>
    </Card>

    <Theme radius="none" render={<section />}>
      <Card size="3">
        <Text size="3" emphasis="medium">Legacy invoices</Text>
      </Card>
    </Theme>
  </Stack>
</Theme>
```

The first card, its field and its button all take the `medium` palette, each from its own band.
The nested section squares every corner inside it, and the radio, the grips and the switch track
keep their shapes.

One line states a decision about a region, and the reader of that file can see it. A per-card
prop produces nine decisions on one screen, and no corner at all.
