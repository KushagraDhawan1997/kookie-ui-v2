Radius is a Theme axis: one word for the whole application, five designed levels, `full` by
default. Every family re-prices its own corner from that word, so a control pills while the card
holding it stays a card. No component takes a corner, and that is the point.

## One word, five palettes

Set it once, on the Theme:

```tsx
<Theme radius="medium">
  <App />
</Theme>
```

The levels are `none`, `small`, `medium`, `large` and `full`. `full` is the default: pill
controls and capsule rows are this system's resting identity, not an opt-in.

Each level is a **designed palette**, emitted at build time — not a multiplier over one scale. A
factor moves every step together, so no single corner stays correctable. The decisive case is
`full`: CSS clamps `border-radius` to half the smaller dimension, so a huge number gives a
perfect pill on a control for free and turns a dialog into a giant lens. One factor cannot do
both. A designed palette can, and at `full` the control band states the capsule while the
surface band holds at `large`'s values.

The palette is geometric rather than even, because radius is perceptually non-linear: fine steps
at the small end, spread out at the large end where 30 and 32 pixels on a card are the same
corner. That curve is taste, and it is named as taste.

Why one word rather than a prop per component: a system where one card is rounder than the next
has no corner at all. Corner reads as a property of the *product*, and it only reads that way
when nothing local can move it.

## Bands, because a fraction belongs to a box

Five families, five semantic bands. You reference the family, never the number:

```css
--radius-control-2   /* a size-2 button, field or select trigger */
--radius-surface-3   /* a size-3 card */
--radius-overlay-3   /* a size-3 dialog */
--radius-row-2       /* a size-2 menu or select row */
--radius-mark-2      /* a size-2 checkbox */
```

A Button reads `--radius-control-2`; it never reads `--radius-2`. Numeric coincidence — "size 2
uses radius 2" — holds exactly until something is renumbered.

The bands are indexed differently on purpose. Control radius belongs to the density set, because
a control given more room reads boxy at a fixed corner; surface and overlay radius follow the
size index alone, since density reaches a card through its padding.

The rule underneath all of it is that **a corner holds a near-constant fraction of the box it is
actually drawn on**. This system has broken that rule more than once, always the same way — a
family riding a ladder that belongs to a box the component does not have.

- The checkbox shipped on `--radius-control-N`. Those radii are designed against the control
  height ladder and a mark is not on it, so the corner ran from a quarter of the mark at size 1
  to nearly two fifths at size 4 — at comfortable size 4 it was a circle in all but name, which
  is the one thing a checkbox must never be.
- The menu row took the control band's capsule at `full`. A row's box is its text line plus one
  designed inset, not the height ladder, so the panel wrapped its rows at corners the browser
  could never paint — wrong in 21 of 24 cells by up to 9 pixels, wider than the panel's whole
  padding.

Both were caught by eye, then by a law reading the browser's resolved corner rather than the
declared number. That is why the mark family and the row family each own a band.

## Curves nest, they do not collide

A pane holding rows derives the row's corner from its own: **panel corner = row corner + panel
padding**. Two curves that share a centre nest; two that do not either cut into each other or
leave a crescent of dead space at every row.

The relationship holds by construction, per size and per level — you never compute it and there
is no offset to pass. The same sentence applies one band over: an overlay wears the corner of
the card one size up, so a dialog out-rounds the cards inside it, and `Surface` reads that band
because a pane containing panes has to out-round its contents.

Concentric arithmetic is undefined at zero, so `none` is guarded to mean none rather than
rounding a square panel by exactly its own padding.

## The four corners `none` never reaches

`none` squares everything, including the pill — a kill switch with an exception is not a kill
switch. Four shapes survive it anyway, and they survive as **role semantics** rather than taste:

- a **radio** is a circle, because a square radio reads as a checkbox;
- the **slider grip** and the **switch thumb** are circles, because a square handle reads as a
  bead that stuck, and every platform ships them round;
- the **switch track** is a capsule, because a circle only nests in a curve — a round thumb in a
  square channel reads as a bead in a rail, which is a slider.

Role legibility outranks theme uniformity in both directions. The checkbox is capped at
`large`'s corner under `full` for the mirrored reason, since a circular checkbox reads as a
radio: a corner stops getting rounder, it never retreats.

An exception has to be argued to be one. The slider's rail was once a silent fifth, escaping
`none` by arithmetic rather than by argument, and it was fixed rather than promoted. Treat a
fifth as a bug until someone has written the paragraph.

## What you cannot do

There is no `radius` prop on any component, and there will not be one. If a region genuinely
wants a different corner, that is a nested Theme on an element you already have:

```tsx
<Theme radius="small" render={<section />}>
  <Card>Settings</Card>
</Theme>
```

That is a statement about a region, and it is visible in review. A per-card knob is nine
opinions per screen and, at the end of them, no corner at all.
