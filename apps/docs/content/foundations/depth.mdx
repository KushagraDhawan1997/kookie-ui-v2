The `depth` setting in a Theme answers a single question: does this app contain light? No
component accepts a shadow prop, and no screen selects a shadow individually. Instead, each
component category determines its own shadow behaviour.

## Set depth once, at the root

```tsx
<Theme depth="elevated">
  <App />
</Theme>
```

The default `elevated` setting gives the app a light source, allowing cards to sit above the
page, main actions to catch light, and handles to lift. The `flat` setting removes this light
source, relying on lines and fills for separation.

Depth belongs to the Theme because light is perceived as a property of the environment, not a
single object. Having both a raised and a flat card on the same screen would suggest two
different environments. Therefore, Kookie does not provide `shadow`, `elevation`, or `raised`
props.

## What casts a shadow

These components cast a shadow:

- `Card` and card-like panels
- Loud buttons
- Handles on sliders and switches
- `Kbd`

These components do not:

- `Surface`
- Text fields and text areas
- Medium and quiet buttons
- Checkboxes
- Progress bars
- Separators
- Tab bars

Only two kinds of element receive a shadow: the object you pick up, and the element that floats
above everything else. This rule changes the code you write in three places:

- **Grounds cast nothing:** A `Surface` holds objects rather than being one. To elevate an
  element, place a `Card` inside the Surface.
- **Fields stay recessed:** To elevate a form, place it inside a Card. The fields remain
  recessed.
- **Medium buttons stay flat:** Rank buttons using `emphasis` rather than depth. A loud button
  catches light and casts a shadow, while a medium button does neither.

A checked checkbox catches light without casting a shadow, as checking it fills a recess rather
than lifting the element.

A disabled card loses its shadow. A shadow indicates that an element sits above the page and can
be picked up, which a disabled card cannot, so it returns to the page.

## Turn off the light for one region

You can nest a Theme to remove the light source from a specific region of an elevated app.

```tsx
<Theme depth="elevated">
  <Stack gap="5">
    <Card size="3">
      <Stack gap="3">
        <Heading size="6">Production</Heading>
        <Text size="3" emphasis="medium">Deployed 4 minutes ago.</Text>
        <Button emphasis="loud">Promote build</Button>
      </Stack>
    </Card>

    <Theme depth="flat" render={<section />}>
      <Card size="3">
        <Text size="3" emphasis="medium">Archived environments</Text>
      </Card>
    </Theme>
  </Stack>
</Theme>
```

The first card lifts and its loud button catches light, while the second card defines its edge
with a thin line. Nothing inside the nested Theme casts a shadow, including a menu opened from
it.

## Bigger boxes get longer shadows

Kookie provides five shadow values: one recess and four drops.

Each drop repeats the same structure at a different height. A tight contact line keeps the
shadow sharp, while softer layers move inward so the depth falls under the element rather than
spreading outward.

Larger elements cast larger shadows, and a smaller element that borrows a larger shadow looks
swollen. A card uses a shadow with a longer reach than a floating panel. This relationship is
based on observation, while the exact values remain a design judgment.

Kookie publishes `--shadow-1` through `--shadow-5` as a resource. Components access these
through the theme rather than directly. Use `style` for custom implementations:

```tsx
<Box style={{ boxShadow: "var(--shadow-3)" }}>Custom pane</Box>
```

`Box` lacks a shadow prop because it is a layout component, and shadows are paint.

## Popups must show their edges

A popup covers the content beneath it, so its edge must remain visible. An elevated app shows
this edge with a shadow, while a flat app casts nothing at all, including menus and dialogs, and
draws a thin line instead.

A `Dialog` casts no shadow of its own in either setting because the dimmed background provides
the necessary separation. The panel retains the standard card shadow for the current depth
setting.

## Handles cast a shadow even in a flat app

These elements cast a shadow regardless of the app's depth setting:

- Slider handles
- Switch thumbs
- Selected segments of a segmented control
- `Kbd`

These are the same four shapes that keep their form at `radius="none"`, because their appearance
conveys their function. A handle that does not sit above its track stops looking like a handle,
and since a handle's position is the value it sets, the control stops working.

`Kbd` is an exception, as it represents a key pressing into a surface, making its depth a recess
rather than a lift.

A disabled handle loses its shadow and dims while retaining its colour, since a grey handle in a
grey track is hard to see.
