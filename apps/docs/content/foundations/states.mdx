Every control shares one set of states: resting, hover, press, focus, disabled and invalid. The
system defines how each state looks, once, for every control. When you build with a component,
you choose its settings, such as `tone` and `emphasis`, and the states follow from them.

Each change is instant. A hovered or pressed control doesn't move or animate, and only its
colours change. CSS handles every state, so no JavaScript runs when you point at, press or
focus a control.

This matters because the numbers multiply. Dozens of components, three levels of loudness and six
states produce more combinations than anyone can keep consistent by hand.

## Hover and press move one step at a time

Hover moves a control's fill one step along the colour scale, and press moves it one step
further. Every level of loudness uses the same size of step:

- **Loud:** rests on the family's strong fill, then moves one step on hover and another on press.
- **Medium:** rests on a light grey fill, then moves one step darker on hover and another on
  press. In dark mode the steps go lighter.
- **Quiet:** has no fill at rest. On hover it takes the medium button's resting fill, and on
  press the medium button's hover fill.

The colours differ at each level, but the amount of change is the same, so two controls at the
same loudness respond in the same way. The colour scale has perceptually even steps, which
means one step looks like the same amount of change on blue as it does on yellow.

Hover and press always move the fill away from the label colour. If a label is readable at
rest, it stays readable under the pointer and while you press.

## Hover only on devices that can hover

Hover styles apply only when the device has a pointer that can hover, through the
`(hover: hover)` media query. A touch screen reports a hover when you tap and keeps it until
your next tap, so without the query a button you tapped would stay in its hover colour.

Press has no such condition, because press is the only feedback a touch screen gives.

## The focus ring

One focus ring shows keyboard focus everywhere. It is an outline two pixels wide with a
two-pixel gap around the control. An outline follows the control's corners, including a fully
round pill, and it never changes the layout.

The ring uses the accent colour whatever tone the control has, so a destructive button gets the
same ring as any other. The ring only says where focus is, and that information is the same on
every control. With the default grey accent, the ring is near-black in light mode and a light
grey in dark mode.

WCAG 2.4.7 and 2.4.13 set the measured limits: at least two pixels wide, with a gap, and 3:1
contrast against the colour beside it. The ring meets them in both modes, using a different
shade in each.

The one exception is an invalid field, which shows its ring in the error colour.

## A field shows its ring while you type in it

You enter a field rather than press it, so a field shows its ring whenever the text cursor is in
it, not only when you arrive by keyboard. Every native text input behaves this way.

The ring goes on the field as a whole. A button inside the field, such as a clear button, gets
its own ring when it has focus, so you only ever see one ring at a time.

## Which state wins

Some states can apply at the same time, and the order between them is fixed:

- **Disabled wins over invalid.** A disabled field shows the disabled colours even when its value
  is invalid.
- **Invalid wins over checked.** A ticked checkbox that is also invalid shows the error colours.

## Disabled

A disabled control does four things:

- Its text, fill and border change to the disabled colours.
- It stops responding to hover and press.
- The cursor is an ordinary arrow, not `not-allowed`, because no native platform uses that
  cursor on a disabled control.
- It loses its shadow.

Disabled never uses opacity. On a tinted surface, opacity lets the colour underneath show
through and breaks the contrast the theme calculated. Separate disabled colours keep the control
readable while showing clearly that it is off.

A `loading` Button is different. It blocks presses, but it keeps its normal colours and shows a
busy cursor, because it is still the control you pressed.

## Cards you can press

A `Card` that you render as a button or a link behaves like a control. Its fill changes on hover
and press, and it shows the same focus ring as a button.

A disabled card looks like a disabled button. The fill lightens, the text dims, the cursor is an
ordinary arrow and the shadow goes, because a shadow suggests that you can pick the card up.

## Cards you can select

There's no `selected` prop. To let people choose one of several cards, make each card the label
of a real `Radio`:

```tsx
<RadioGroup defaultValue="pro" aria-label="Plan">
  <Grid columns="repeat(3, minmax(0, 1fr))" gap="5">
    <Card size="3" render={<label />}>
      <Stack gap="3">
        <Flex justify="space-between" align="center">
          <Text size="3" weight="medium">Pro</Text>
          <Radio value="pro" />
        </Flex>
        <Text size="5">$20</Text>
      </Stack>
    </Card>
    {/* the other cards, each with its own Radio */}
  </Grid>
</RadioGroup>
```

Because the card is a label, clicking anywhere on it chooses the radio. The keyboard, the form
value and what a screen reader announces all come from the radio, and the chosen card's border
changes colour. A `selected` prop would be a second way to say what the radio already says, and
the two could disagree.

For a board where people choose several cards, use a `Checkbox` in the same way. Place the radio
or checkbox wherever the layout needs it. The chosen state and the focus ring use different
colours, so a card can show both at once.

## Invalid fields

There's no `invalid` prop. Your validation code decides whether a value is invalid, and you say
so with `aria-invalid`. Inside a `Field`, Base UI sets the matching `data-invalid` attribute for
you, and the system responds to either.

```tsx
<Stack gap="4">
  <Flex render={<label />} direction="column" gap="2">
    <Text size="2" weight="medium">Work email</Text>
    <TextField
      type="email"
      value={email}
      onChange={(event) => setEmail(event.target.value)}
      aria-invalid={emailError ? true : undefined}
      aria-describedby={emailError ? "email-error" : undefined}
    />
    {emailError ? (
      <Text id="email-error" size="2" tone="destructive">{emailError}</Text>
    ) : null}
  </Flex>
  <Button emphasis="loud" disabled={!email}>Send invite</Button>
</Stack>
```

An invalid field shows its border and its focus ring in the error colour. The text that the
person typed stays fully readable, because it is their content.

WCAG 1.4.1 says that colour alone must not carry information, so the red border is not enough.
Always write an error message beside the field, as in the example.

## States are attributes on the element

Every setting is written on the element as a data attribute, and the stylesheet reads those
attributes. You can see every decision in the browser's inspector:

```html
<button type="button" class="kui-control kui-button"
        data-size="2" data-tone="destructive" data-emphasis="quiet">Delete</button>
```

None of these values is a colour. The element carries the meaning and the loudness, and the
theme turns them into colours.

## Tone and emphasis

A button answers two separate questions, so it has two separate props. `tone` says what the
action means. `emphasis` says how loud it is compared with the actions near it: `loud`,
`medium` or `quiet`.

A single appearance prop such as `variant` mixes the two questions. That is how systems end up
with names like `secondary-outline-destructive`, where every new combination needs a new name.
A `primary | secondary | danger` prop also can't say "quiet and destructive", and a quiet delete
action is one of the most common things an interface shows.

```tsx
<Button emphasis="loud">Save changes</Button>
<Button tone="destructive" emphasis="quiet">Delete</Button>
```

`bordered` adds one more step between quiet and medium: quiet, then quiet with a border, then
medium. Use it to rank an action, not as decoration.
