`size` picks a step, not a measurement. When you write `size="2"` you are asking for the second
step on a scale, and the theme decides what that step is worth today.

The same number means different things on different components, because the components are
measuring different things. On a Button, size sets how tall the box is. On Text, size sets how
large the words are.

## A step, not a number of pixels

`size="2"` on a Button gives you a control 32 pixels tall right now, on a normal-density theme
with a mouse. It is 44 pixels on a touch screen. You did not ask for either number, and you do
not have to change your code when they change. You asked for the second step.

The values are fixed lists. Controls take `"1"` to `"4"`. Text and Heading take `"1"` to `"9"`.
There is no `size="2.5"` and there is no way to pass a length. If one screen could invent a
value in between, the scale would stop holding across the app. That is a judgment, not a
measured limit.

Three different scales share these numbers:

- Button, TextField and Select use a **height** scale.
- Card and Surface use a **padding and corner** scale.
- Checkbox, Radio, Switch and Slider use a **mark** scale.

`size="3"` on a Card and `size="3"` on a Button are therefore not the same size as each other.
They are the third step of two different things. Pick the number that looks right for each
component rather than matching numbers across them.

## One number sets everything about a control

Set `size` once and the component takes a group of values that were designed to go together:
its height, its side padding, its corner, its icon size, the gap between the icon and the
label, and the size of the label text.

None of those come from multiplying a base number. Every combination of density and pointer has
its own written-out values:

```css
/* normal density, mouse */
--control-height-2: calc(32px * var(--scale));
--control-px-2: calc(10px * var(--scale));
--icon-size-2: calc(16px * var(--scale));

/* touch screens get their own numbers, not a multiplied version of the ones above */
--control-height-2: calc(44px * var(--scale));
--control-px-2: calc(13px * var(--scale));
--icon-size-2: calc(20px * var(--scale));
```

They are written out so that one of them can be corrected without moving the other three. If a
single multiplier produced all four heights, nudging one would drag the rest with it.

Controls set a minimum height rather than a fixed one. If someone turns their text up to 200%,
or a label wraps onto a second line, the control grows instead of clipping the text. WCAG 2.2
Success Criterion 1.4.4 requires that, so this one is a measured limit.

## Checkboxes and switches use their own scale

A checkbox, a radio, a switch and a slider handle all sit *beside* a label rather than
containing one. They have no text inside them, so the control height scale does not apply. They
use a scale of their own, and a switch is one step larger than a checkbox at the same size,
which is the relationship most design systems arrive at by hand.

A checkbox is exactly as tall as one line of the text beside it. It therefore aligns with its
label without any adjustment, and it gets bigger on a phone because the text gets bigger there.

### Leave 12 pixels between stacked checkboxes

A checkbox is small, so its tappable area reaches past the box you can see, out to the size a
Button of the same size would occupy.

Stacked checkboxes therefore need room. Put at least 12 real pixels between them. Any closer
and the lower checkbox's invisible tappable area covers the one above it and wins the tap, so
clicking one checkbox toggles its neighbour.

`gap="4"` gives you 12 pixels at normal density. Use `gap="5"` if you want it to stay safe at
every density, because compact density pulls step 4 down to 8 pixels.

```tsx
<Stack gap="5">
  <Flex render={<label />} align="center" gap="3">
    <Checkbox size="2" />
    <Text size="3">Notify me when it ships</Text>
  </Flex>
  <Flex render={<label />} align="center" gap="3">
    <Checkbox size="2" />
    <Text size="3">Send the weekly digest</Text>
  </Flex>
</Stack>
```

## Touch screens get bigger controls

`pointer` has two settings, `fine` for a mouse and `coarse` for a touch screen. They are two
complete sets of measurements, in the same way light and dark are two complete sets of colours.
The components, the size numbers and the rules are identical. Only the values differ.

What is touching the screen decides it, not how wide the window is. A narrow browser window on
a laptop is still a mouse.

On a touch screen, seven things get new values: control heights, side padding, icon size, the
gap between icon and label, control corners, the checkbox scale, and reading text. Spacing
between components does not change. A phone needs more content per inch, not less.

### 24 pixels is the floor, 44 is the normal size

WCAG 2.2 Success Criterion 2.5.8 sets a minimum tappable area of 24 by 24 pixels at Level AA.
Nothing in this system falls below it: the smallest control you can build is a size 1 control
at compact density with a mouse, and it measures exactly 24. That is a measured limit.

You normally get 44 pixels, which is a higher bar than the minimum. Success Criterion 2.5.5
sets 44 at Level AAA, and Apple uses the same number. A fingertip is about 10 millimetres
across. A size 2 control on a touch screen measures exactly 44. You only go below that by
choosing size 1 or by setting a denser theme, and both are deliberate.

Set `pointer` on the Theme. It takes `fine`, `coarse` or `auto`, and `auto` follows the device.
Setting `coarse` yourself switches everything together, including reading text, which is useful
for testing a phone layout on your laptop.

```tsx
<Theme pointer="coarse">
  <Button size="2">Continue</Button>
</Theme>
```

## A control inside another control sizes itself

Put a Button inside a TextField and you do not give it a size. The field calculates it, so that
the button has even space on all four sides.

You could not calculate it yourself in any reliable way. The control heights are only four to
eight pixels apart, so no size number leaves a button sitting neatly inside a field.

Its tappable area matches the field's box rather than growing to 44 pixels. A 44-pixel target
inside a 36-pixel field would be larger than the thing containing it, and WCAG counts that
against you.

```tsx
<TextField
  size="3"
  type="password"
  trailing={<Button emphasis="quiet">Show</Button>}
/>
```

## Some components have no size at all

Before adding a `size` prop to a component, check whether any of the three scales suits it.
Sometimes none does, and then the component ships without one.

Progress has no size. The closest scale is the slider's track, which is drawn as a fraction of
the slider's handle. A progress bar has no handle, so sizing it that way would measure it
against something it does not have. It works like Separator instead: one thickness, the width
of whatever contains it, and no size prop.

Code does the opposite. Its `size` is optional, and if you leave it out it takes the size of
the line it is sitting in. A word inside a sentence should not have a size of its own.

```tsx
{/* A progress bar has no size. */}
<Box width="240px">
  <Progress value={62} aria-label="Uploading" />
</Box>

{/* Code takes the size of the text around it. */}
<Text size="2">
  Run <Code>pnpm build</Code> before publishing.
</Text>
```

If you are unsure, ship without a size. Adding one later does not break anyone's code. Removing
one does.
