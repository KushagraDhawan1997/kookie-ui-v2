`size` picks a step rather than a measurement, so `size="2"` asks for the second step on a
scale and the theme decides what that step is worth today.

The same number means different things on different components, because the components measure
different things. On a Button, size sets the height of the box, while on Text it sets how large
the words are.

## A step, not a number of pixels

Today `size="2"` on a Button gives you a control 32 pixels tall at normal density with a mouse,
and 44 pixels on a touch screen. You asked for neither number, and your code does not change
when the numbers do.

The values come from fixed lists: controls accept `"1"` to `"4"`, while Text and Heading accept
`"1"` to `"9"`. There's no `size="2.5"` and no way to pass a length, because a screen that could
invent a value between two steps would break the scale across the app.

Three different scales use these numbers:

- Button, TextField and Select use a **height** scale.
- Card and Surface use a **padding and corner** scale.
- Checkbox, Radio, Switch and Slider use a **mark** scale.

`size="3"` on a Card and `size="3"` on a Button therefore describe different sizes, since each
names the third step of a different scale. Pick the number that looks correct for each
component, rather than matching numbers across components.

## One number sets everything about a control

Set `size` one time, and the component gets a group of values that were designed together:

- its height
- its side padding
- its corner
- its icon size
- the gap between the icon and the label
- the size of the label text.

The system doesn't calculate these values from a base number. Each combination of density and
pointer has its own values, written out in full:

```css
/* normal density, mouse */
--control-height-2: calc(32px * var(--scale));
--control-px-2: calc(10px * var(--scale));
--icon-size-2: calc(16px * var(--scale));

/* touch screens get their own numbers, not a multiplied version of the ones above */
--control-height-2: calc(44px * var(--scale));
--control-px-2: calc(13px * var(--scale));
--icon-size-2: calc(20px * var(--scale));
```

Each value is written out separately, so correcting one leaves the other three where they are,
whereas a single multiplier behind all four heights would move them together.

Controls set a minimum height rather than a fixed one, so a control grows and never cuts off its
text when a person enlarges their text by 200% or a label wraps onto a second line. WCAG 2.2
Success Criterion 1.4.4 requires this, which makes it a measured limit.

## Checkboxes and switches use their own scale

A checkbox, a radio, a switch and a slider handle sit *next to* a label rather than containing
one. They hold no text, so the control height scale does not apply and they read a scale of
their own, on which a switch is one step larger than a checkbox at the same size. Most design
systems reach that relationship by hand.

A checkbox is exactly as tall as one line of the text beside it, which aligns it with its label
without an adjustment and makes it grow on a phone, where the text grows too.

### Leave 12 pixels between stacked checkboxes

A checkbox is small, so its tappable area extends past the box you can see, out to the size of a
Button at the same size.

Stacked checkboxes therefore need at least 12 real pixels between them. Any closer and the lower
checkbox's tappable area covers the upper checkbox and takes the tap, so a click on one checkbox
changes the one beside it.

`gap="4"` gives you 12 pixels at normal density, while compact density reduces step 4 to 8
pixels. Use `gap="5"` to stay safe at every density.

```tsx
<Stack gap="5">
  <Flex render={<label />} align="center" gap="3">
    <Checkbox size="2" />
    <Text size="3">Notify me when it ships</Text>
  </Flex>
  <Flex render={<label />} align="center" gap="3">
    <Checkbox size="2" />
    <Text size="3">Send the weekly digest</Text>
  </Flex>
</Stack>
```

## Touch screens get bigger controls

`pointer` takes two settings: `fine` for a mouse and `coarse` for a touch screen. Each setting
holds a full set of measurements, in the way that light and dark hold two full sets of colours.
The components, the size numbers and the rules stay the same, and only the values differ.

The setting follows what touches the screen rather than the width of the window, so a narrow
browser window on a laptop still reports a mouse.

On a touch screen, seven things get new values:

- control heights
- side padding
- icon size
- the gap between the icon and the label
- control corners
- the checkbox scale
- reading text.

The spacing between components stays where it is, because a phone needs more content per inch
rather than less.

### The 24-pixel floor and the 44-pixel default

WCAG 2.2 Success Criterion 2.5.8 sets a minimum tappable area of 24 by 24 pixels at Level AA,
and nothing in this system falls below it. The smallest control is size 1 at compact density
with a mouse, which measures exactly 24 pixels.

The usual result is 44 pixels, well above that minimum. Success Criterion 2.5.5 sets 44 pixels
at Level AAA, Apple uses the same number, and a fingertip measures approximately 10 millimetres
across. A size 2 control on a touch screen measures exactly 44 pixels, and a control drops below
that only when you choose size 1 or a denser theme, which are both deliberate choices.

Set `pointer` on the Theme, where it accepts `fine`, `coarse` or `auto`, and `auto` follows the
device. Setting `coarse` moves everything together, including reading text, which makes it
useful for testing a phone layout on your laptop.

```tsx
<Theme pointer="coarse">
  <Button size="2">Continue</Button>
</Theme>
```

## A control inside another control sizes itself

Leave the size off a Button that you put inside a TextField, because the field calculates it so
that the Button keeps equal space on all four sides.

You cannot pick that size correctly yourself, since the control heights sit only four to eight
pixels apart and no size number places a button neatly inside a field.

The Button's tappable area matches the field's own box rather than growing to 44 pixels, because
a 44-pixel target inside a 36-pixel field would exceed the field, which WCAG treats as a
failure.

```tsx
<TextField
  size="3"
  type="password"
  trailing={<Button emphasis="quiet">Show</Button>}
/>
```

## Some components have no size

Check whether one of the three scales applies before you add a `size` prop to a component,
because sometimes none of them does and the component then has no `size` prop at all.

Progress is one such component. The nearest scale belongs to the slider track, which is a
fraction of the slider handle, and a progress bar has no handle, so that scale would measure the
bar against a part it does not have. Progress therefore works like Separator: one thickness, as
wide as its container, and no size prop.

Code refuses from the other direction, because its `size` is optional and falls back to the size
of the line around it. A word inside a sentence must not carry a different size.

```tsx
{/* A progress bar has no size. */}
<Box width="240px">
  <Progress value={62} aria-label="Uploading" />
</Box>

{/* Code takes the size of the text around it. */}
<Text size="2">
  Run <Code>pnpm build</Code> before publishing.
</Text>
```

Leave the size off when you are unsure, because adding one later breaks no code, whereas
removing one does.
