Motion covers two things: a colour changing, and something moving. Two separate clocks drive
them. No component sets a duration, and CSS handles every transition, so nothing runs in
JavaScript while someone is pressing a control.

## Colour and movement run on separate clocks

A colour or opacity change eases, and it's short. It uses `--motion-duration` and
`--motion-easing`.

Something that moves follows a spring. The configuration states the physics, and the generator
samples that model and bakes the result into a CSS `linear()` curve. The finished curve costs
the browser exactly what a `cubic-bezier` costs.

If both changes share one clock, the colour waits for the movement, and the control
responds late.

```css
/* Wrong: one clock for everything. */
.thing {
  transition: all 200ms ease;
}

/* Right: the colour eases, the movement springs. */
.thing {
  transition:
    background-color var(--motion-duration) var(--motion-easing),
    translate var(--motion-press) var(--motion-spring-stiff);
}
```

## A press changes colour immediately

A tap lasts about 60 milliseconds. An eased fill never reaches its colour in that time, so
someone tapping on a phone gets no colour response at all. You only see this on a real
phone, not in desktop touch emulation.

So a press sets its colour clock to zero. The fill lands on the first frame, and the
movement springs underneath it. Any motion added later has to keep the press immediate.

The hover state arrives in 80 milliseconds and leaves in 220. It arrives quickly because a
hover is something the person did. It leaves slowly because moving away needs no response.

## Each kind of component moves its own distance

A button sinks when pressed. It moves down and gets slightly smaller at the same time. If it
only moved down, it would look like a slide. If it only shrank, it would look like it was
backing away.

A pressable card sinks by its own smaller distances. Scale is relative, so a big card shrinking
by a button's factor would move each edge several pixels, and that looks like the page
flexing.

A checkbox squashes instead, because it has no depth to sink into. A text field doesn't move
at all. You read inside the box, so the box has to stay still.

None of them sets a duration. The system sets the clocks, and a component sets only its
distances, so two controls of the same size move at the same speed.

Nothing in the example below sets a duration, a distance, or an
easing.

```tsx
<Card size="3">
  <Stack gap="4">
    <Heading size="6">Deploy to production</Heading>

    <Flex render={<label />} align="center" gap="3">
      <Switch size="2" />
      <Text size="3">Run the migration first</Text>
    </Flex>

    <Slider defaultValue={[25]} aria-label="Rollout percentage" />

    <Flex gap="3" justify="flex-end">
      <Button emphasis="quiet" bordered>Cancel</Button>
      <Button emphasis="loud">Deploy</Button>
    </Flex>
  </Stack>
</Card>
```

The buttons sink. The switch thumb springs across its track. The slider handle follows your
pointer.

There's no duration prop, no easing prop, and nothing called `animate`. Components can't
write a duration either. Every part of every transition has to resolve to a motion token, so a
hand-typed `150ms` fails the build.

## Movement overshoots once, at most

Both springs pass their target at most once. A control that crosses its target twice wobbles,
and a wobbling control looks mechanical.

To make a movement more noticeable, move it further. Don't loosen the spring. A looser curve
over a short distance looks like a bounce effect. The physics is fixed, and distance is the
only part a component sets.

## A focus ring can't animate a short distance

A focus ring needs about four pixels of travel to be worth animating. Chrome rounds
`outline-offset` to whole pixels, so a ring with two pixels of room animates in three frames,
and three frames look like a stutter rather than a movement. A field's ring has two pixels of
room, so it appears instantly.

## Spinners slow down instead of stopping

A Spinner, and a Progress bar with no value, are a different category. Their movement isn't
a transition between two states. It says that work is still happening.

When someone has asked their operating system for reduced motion, both slow down, and the
spinner slows to three seconds. Neither stops, because a busy indicator that stops looks
finished.

## Reduced motion stops everything else

Every other movement stops when someone asks for reduced motion. A panel appears in place
instead of travelling, and the system skips the measurements that only fed animations.

The stylesheet that starts a movement is the same one that switches it off, on the same
selector, so a new animation can't arrive without its own off switch.

## Nothing runs in JavaScript while you interact

Hover, press, focus, and the validity states are all stylesheet rules reading data
attributes off the element. No handler measures anything while you're pointing at a control,
and the package ships no runtime animation library.

There are three exceptions, and none of them happens while you're interacting. A floating panel
measures where it's going once, when it opens. A tab bar re-measures its underline when the
selection changes. The glass effect is built when a panel mounts and when the window resizes.
