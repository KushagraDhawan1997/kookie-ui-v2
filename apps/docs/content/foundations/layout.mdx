On a KookieUI screen, every distance belongs to a container rather than to the thing inside it.
Four components place things on the screen, one scale supplies the distances, and one theme
setting moves that scale for the whole app.

## Components don't set their own outer spacing

The `gap` on a container sets the distance between the things inside it, and no control accepts
a margin prop.

A margin describes a relationship between two things rather than a property of one. The correct
distance below a button depends on the next component, on the density of your theme, and on the
job of the group, none of which the button can know, so a component carrying its own margin can
only guess and every layout that uses it must cancel the guess first.

Wrap the component in a Box when you need a one-off distance, because a wrapper is visible in the
file while a margin inside a control is not.

```tsx
// Does not compile. A control has no margin prop.
<Button mt="4">Save</Button>

// The distance belongs to the container.
<Stack gap="4">
  <TextField placeholder="Project name" />
  <Button>Save</Button>
</Stack>

// A one-off distance is a wrapper you can see.
<Box mt="6">
  <Button>Save</Button>
</Box>
```

## Box does the work

`Box` accepts the full set of layout props: spacing, width and height, a few structural keywords,
and the props for a flex or grid child. `Flex`, `Grid` and `Stack` are each a Box with a fixed
display and a shorter list of props, and none of the three adds CSS.

The shorter list is deliberate. Plain CSS lets you put any property on any element and silently
ignores the ones that do not apply, whereas `columns` on a `Flex` does not compile here.

Use `Stack` when things run down the page, `Flex` when you must choose the direction or the
alignment, `Grid` for a two-dimensional arrangement, and `Box` when you need a prop the narrower
components refuse. Reach for `style` for a property outside the prop list, which applies last and
therefore wins.

```tsx
<Stack gap="4">
  <Flex align="center" justify="space-between" gap="3">
    <Heading size="6">Members</Heading>
    <Button>Invite</Button>
  </Flex>
  <Grid columns="repeat(2, 1fr)" gap="4">{/* … */}</Grid>
</Stack>
```

## Two layers of spacing

`--space-1` to `--space-12` is the raw scale. The steps stay small at the small end, where you
can see the difference between 12, 16 and 24 pixels and use all three often, while each step
doubles at the large end, where a difference of eight pixels is invisible.

`--layout-space-1` to `--layout-space-12` is a second layer on top of that raw scale, and every
layout distance reads it: `gap` on Flex, Stack and Grid, `p` and `m` on any layout component, and
the padding inside a card.

`gap="4"` therefore gives you step 4 of the current density rather than a permanent name for 12
pixels. Without the second layer it would be one more way to write 12 pixels.

```css
/* the raw scale, which density never touches */
--space-4: calc(12px * var(--scale));

/* the layer that gap="4" and p="4" actually read */
--layout-space-4: var(--space-4);   /* normal density */
--layout-space-4: var(--space-3);   /* compact density */
```

The layout layer carries every distance between two things, and every distance from the edge of
a container to its contents. Inside a control the raw scale stays raw, because a button's padding
and the gap between its icon and its label already answer to density through their own values,
and reading the layout layer as well would shrink them twice.

You can also pass a real length, and `gap="13px"` goes through unchanged, where it stays visible
in the file as an exception.

## What density changes

`density` is a Theme setting with three levels, `compact`, `default` and `comfortable`, and you
choose it for the whole app rather than for one component.

Each level holds a set of hand-picked numbers rather than a multiplier. A level sets every
control height and every control padding directly, and it picks twelve steps from the raw scale
while the raw scale itself stays put, so no value arrives at 26.78 pixels and correcting one
value leaves the others where they are. A multiplier would only let you move a whole level, which
would turn every small correction into an app-wide change.

Two things stay outside density. It never moves the raw scale, so a compact app cannot shrink the
large gutters around a page: the small steps move down by one while steps 9 to 12 hold. It also
never changes the size of text, because it gives you more room and leaves the words alone. Use
`size` to change the words.

```tsx
<Theme density="compact">
  <Stack gap="4">{/* every distance below tightens */}</Stack>
</Theme>
```

## Responsive values respond to the container

Any layout prop accepts one value per size, written as an object, where `initial` is the base
value and `sm`, `md` and `lg` apply on top of it.

These sizes measure the nearest ancestor you can measure rather than the window, which lets one
Grid work correctly in a narrow sidebar and in a wide main column without two versions.

Measurement has a cost, so you turn it on deliberately. A box you can measure no longer sizes
itself around its contents, so put `container` on a box the layout already gives a width to, or
set `width`, `flexGrow` or `flexBasis` yourself. A `container` Box left to size itself around its
contents comes out zero pixels wide, and a development build warns you when that happens.

```tsx
<Box container>
  <Flex direction={{ initial: "column", md: "row" }} gap={{ initial: "3", md: "5" }}>
    {/* … */}
  </Flex>
</Box>
```

The size of the window is a different question with a different answer. A container size tells
you how much room one component has, whereas `useWindowClass()` returns `narrow`, `regular` or
`wide` and tells you which shape the whole interface must take: a bottom bar, a narrow rail or a
full sidebar. You answer that once, at the top of the app. It's a hook rather than a token,
because the answer changes which components you render rather than how they look.

## Let a picture reach the edge with bleed

A card has padding, so a picture running from edge to edge must cancel it. `bleed` is the only
named value on the spacing scale, and on any margin prop it resolves to the negative of the
padding of the nearest surface around it.

`bleed` is a value rather than a prop, which keeps every per-side and per-size form you already
know: `mt="bleed" mx="bleed"` bleeds the top and the two sides. The nearest surface wins, so a
card inside a dialog bleeds to the edge of the card, and outside a surface `bleed` is zero.

Shell panes are surfaces too, so `bleed` also lets a canvas or an image reach the edges of a
pane. A `ShellScroll` needs no `bleed`, because a scroll area directly inside a surface already
reaches the edges and re-applies the padding inside itself.

`bleed` works on margins only, since padding and `gap` reject a negative length. CSS receives the
word `bleed` unchanged and refuses it.

```tsx
<Card size="3">
  <Stack gap="3">
    <Box mt="bleed" mx="bleed">
      <img src="/cover.jpg" alt="" />
    </Box>
    <Heading size="6">Northern route</Heading>
    <Text size="3">Two days, one pass, and a ferry at the end.</Text>
  </Stack>
</Card>
```

Most systems ship a component part for this, such as a card section, a media slot or a cover.
Kookie ships none, because a component receives fixed parts only when something non-visual
demands them, such as connecting a label to its control or announcing a role. A picture demands
neither.
