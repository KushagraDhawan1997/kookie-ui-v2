On a KookieUI screen, every distance belongs to a container. It never belongs to the thing
inside the container. Four components place things on the screen. One scale supplies the
distances, and one theme setting changes that scale for the whole app.

## Components don't set their own outer spacing

The `gap` on a container sets the distance between the things inside it. No control takes a
margin prop.

A margin describes a relationship between two things. It isn't a property of one thing. The
correct distance below a button depends on the next component, on the density of your theme,
and on the job of the group. The button can't know any of that. So a component with its own
margin can only guess. Then every layout that uses it must first cancel the guess.

If you need a one-off distance, wrap the component in a Box. You can see a wrapper in the file.
You can't see a margin inside a control.

```tsx
// Does not compile. A control has no margin prop.
<Button mt="4">Save</Button>

// The distance belongs to the container.
<Stack gap="4">
  <TextField placeholder="Project name" />
  <Button>Save</Button>
</Stack>

// A one-off distance is a wrapper you can see.
<Box mt="6">
  <Button>Save</Button>
</Box>
```

## Box does the work

`Box` takes the full set of layout props. These are spacing, width and height, some structural
keywords, and the props for a flex or grid child. `Flex`, `Grid` and `Stack` are each a Box
with a fixed display and a shorter list of props. None of the three adds CSS.

The shorter list is intentional. In plain CSS, you can put any property on any element. CSS
ignores the properties that don't apply, and it doesn't tell you. Here, `columns` on a `Flex`
doesn't compile.

Use `Stack` when things go down the page. Use `Flex` when you must choose the direction or the
alignment. Use `Grid` for a two-dimensional arrangement. Use `Box` when you need a prop that the
narrower components don't accept. For a property outside the prop list, use `style`. Your
`style` is applied last, so it wins.

```tsx
<Stack gap="4">
  <Flex align="center" justify="space-between" gap="3">
    <Heading size="6">Members</Heading>
    <Button>Invite</Button>
  </Flex>
  <Grid columns="repeat(2, 1fr)" gap="4">{/* … */}</Grid>
</Stack>
```

## Two layers of spacing

`--space-1` to `--space-12` is the raw scale. At the small end, the steps are small. You can
see the difference between 12, 16 and 24 pixels, and you use all three often. At the large
end, each step doubles. At large sizes, a difference of eight pixels isn't visible.

`--layout-space-1` to `--layout-space-12` is a second layer on top of the raw scale. Every
layout distance reads this second layer. That includes `gap` on Flex, Stack and Grid, `p` and
`m` on any layout component, and the padding inside a card.

So `gap="4"` gives you step 4 of the current density. It isn't a permanent name for 12 pixels.
Without the second layer, `gap="4"` would only be a different way to write 12 pixels.

```css
/* the raw scale, which density never touches */
--space-4: calc(12px * var(--scale));

/* the layer that gap="4" and p="4" actually read */
--layout-space-4: var(--space-4);   /* normal density */
--layout-space-4: var(--space-3);   /* compact density */
```

The layout layer carries every distance between two things. It also carries every distance
from the edge of a container to its contents. Inside a control, the raw scale stays raw. The
padding of a button and the gap between its icon and its label already change with density,
through their own values. If they also used the layout layer, density would shrink them two
times.

You can also give a real length. `gap="13px"` goes through without change. You can see it in
the file as an exception.

## What density changes

`density` is a Theme setting with three levels: `compact`, `default` and `comfortable`. You
choose it for the whole app. You don't choose it for one component.

Each level is a set of hand-picked numbers. It isn't a multiplier. Each level sets every
control height and every control padding directly. Each level also picks twelve steps from the
raw scale, and the raw scale itself never moves. So no value comes out at 26.78 pixels. You can
also correct one value, and the other values don't move. With a multiplier, you could only move
a whole level. Then every small correction would change the whole app.

Density doesn't change two things. First, it never changes the raw scale. So a compact app
can't make the large gutters around a page smaller. The small steps move down by one, and steps
9 to 12 don't move. Second, density never changes the size of text. It gives you more room, and
the words stay the same size. To change the size of the words, use `size`.

```tsx
<Theme density="compact">
  <Stack gap="4">{/* every distance below tightens */}</Stack>
</Theme>
```

## Responsive values respond to the container

Any layout prop can take one value for each size, as an object. `initial` is the base value.
The `sm`, `md` and `lg` values apply on top of it.

These sizes measure the nearest ancestor that you can measure. They don't measure the window.
So the same Grid works correctly in a narrow sidebar and in a wide main column. You don't write
two versions.

You must turn on measurement, because it has a cost. A box that you can measure doesn't size
itself around its contents. Put `container` on a box that the layout already gives a width to.
Alternatively, set `width`, `flexGrow` or `flexBasis` yourself. If a `container` Box sizes itself
around its contents, it is zero pixels wide. A development build shows a warning when this
occurs.

```tsx
<Box container>
  <Flex direction={{ initial: "column", md: "row" }} gap={{ initial: "3", md: "5" }}>
    {/* … */}
  </Flex>
</Box>
```

The size of the window is a different question, with a different answer. A container size tells
you how much room one component has. `useWindowClass()` returns `narrow`, `regular` or `wide`.
It tells you which shape the whole interface must have: a bottom bar, a narrow rail or a full
sidebar. You answer that question one time, at the top of the app. It's a hook and not a token,
because the answer changes which components you render. It doesn't change how they look.

## Let a picture reach the edge with bleed

A card has padding. So a picture that goes from edge to edge must cancel that padding. `bleed`
is the only named value on the spacing scale. On any margin prop, `bleed` gives the negative of
the padding of the nearest surface around it.

`bleed` is a value, not a prop. So every form for one side and for one size that you already
know still works. For example, `mt="bleed" mx="bleed"` bleeds the top and the two sides. The
nearest surface wins, so a card inside a dialog bleeds to the edge of the card. Outside a
surface, `bleed` is zero.

Shell panes are also surfaces. So you also use `bleed` to let a canvas or an image reach the
edges of a pane. A `ShellScroll` doesn't need `bleed`. A scroll area directly inside a surface
already reaches the edges, and it adds the padding again inside itself.

`bleed` works on margins only. Padding and `gap` can't take a negative length. So CSS gets the
word `bleed` without change, and CSS rejects it.

```tsx
<Card size="3">
  <Stack gap="3">
    <Box mt="bleed" mx="bleed">
      <img src="/cover.jpg" alt="" />
    </Box>
    <Heading size="6">Northern route</Heading>
    <Text size="3">Two days, one pass, and a ferry at the end.</Text>
  </Stack>
</Card>
```

Most systems have a component part for this: a card section, a media slot or a cover. Kookie
doesn't. A component only gets fixed parts when something that isn't visual needs them. Two
examples are the connection of a label to its control and the announcement of a role. A picture
doesn't need either.
