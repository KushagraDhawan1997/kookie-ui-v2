Most design systems give you a flat list of components. This one sorts them into families,
and the family a component belongs to decides which props it takes.

You can tell a `Card` what material it is made of. You cannot tell a `Checkbox`, because a
checkbox has no material to be made of. You can rank a `Button` against the button beside it.
You cannot rank a `MenuItem`, because every item in a menu is equal.

So when a component does not have the prop you were expecting, find its family below. The
family is usually the reason.

## Pages, grounds and cards

There are three levels underneath any screen, and the last two are the ones people mix up.

The **page** is the bottom. The library does not paint it, because a Theme that painted a
background would repaint it again every time you nested another Theme. Paint it yourself with
`--color-page`.

A **ground** is a region that holds other things. `Surface` is a ground. It is barely a
different colour from the page, and it casts no shadow, because it sits *in* the page rather
than above it.

A **card** is an object with its own surface. `Card` is opaque, so anything behind it stops at
its edge, and in a raised theme it casts a shadow.

```tsx
<Surface size="3">
  <Stack gap="3">
    <Card size="2">
      <Stack gap="2">
        <Heading size="6">api-gateway</Heading>
        <Text size="2" emphasis="medium">Deployed 4 minutes ago</Text>
      </Stack>
    </Card>
    <Card size="2">
      <Stack gap="2">
        <Heading size="6">worker-queue</Heading>
        <Text size="2" emphasis="medium">Deployed 2 hours ago</Text>
      </Stack>
    </Card>
  </Stack>
</Surface>
```

The Surface is the tray. The two cards are the things sitting on it, and each one lifts. If you
find yourself nesting a Card inside a Card to get a quieter region, reach for a Surface
instead. Neither one is a quieter version of the other.

A Card is also the one surface that can become a control. Render it as a button and it
presses. Render it as the label of a radio and it can be selected. There is no prop for
either, because the element you gave it already says which one it is.

## Controls

A control is something people operate. Every control shares the same states, the same size
steps and the same loudness setting. There are four kinds.

**Buttons** do something, and they rank against each other. `emphasis` is how loud this action
is compared to the ones beside it; `tone` is what the action means. Use one loud button per
screen.

**Fields** hold something people type. They do not rank, so `TextField` and `TextArea` take no
`emphasis` and no `tone`. A form where one field shouts louder than the next is telling you
nothing. A field is also a recess rather than a raised object, so it never casts a shadow.

**Marks** are the controls that *are* their own mark: `Checkbox`, `Radio`, the `Switch` track
and the `Slider` handle. They sit beside a label instead of containing one, so they do not use
the control height. A mark is exactly as tall as one line of the text next to it.

**Instruments** show or set a value along a length: `Slider` and `Progress`. An instrument has
no panel and no border of its own, so material and surface styling do not apply to it.

## A checkbox sits beside its label

The checkbox and the label are two things in a row, and the row sets the distance between them.

```tsx
<Flex align="center" gap="2">
  <Checkbox id="terms" />
  <Text render={<label htmlFor="terms" />}>Email me about releases</Text>
</Flex>
```

No mark takes a `label` prop. A label is text, and `Text` already handles every size, weight
and colour text needs. A `label` prop would mean building a second, smaller text system inside
a checkbox.

## Rows

A row is one interactive line in a list. A menu item is a row. A sidebar item is a row.

A row looks like a small button but is a different thing, for one reason: **rows are equal.**
No option in a list is louder than the ones around it, so rows take no `emphasis` at all.

The row you are currently on is not a louder row. It changes colour instead, which is what
leaves it somewhere to go when you hover it.

A row also does not use the control height. Its height is its line of text plus a small fixed
inset, which is what makes a column of rows read as a list rather than a stack of buttons.

## Type, layout and the frame

**Type** components take their colour from whatever surface they are sitting on. `Text`,
`Heading`, `Blockquote`, `Code` and `Kbd` have no fill of their own, so on type `emphasis`
picks a text colour rather than a background.

`Link` is the one type component that responds to a pointer, and it is still type rather than
a control. A control is a box with a height, a padding, a corner and a tap target. A link is a
run of words inside a sentence: it has to stay selectable, wrap across lines, and sit on the
same line as the paragraph around it. So it takes the hover and focus states and none of the
box.

**Layout** components paint nothing at all. `Box` does the work, and `Flex`, `Stack` and `Grid`
are Box with a fixed display and a shorter prop list.

**The frame** is `Shell`, and Shell is a pattern rather than a component. A component contains
the things it owns. A pattern arranges things it does not own. If a child ever has to reach
upward and configure its parent, you have built a pattern as a component.

## Five pairs that look alike

These render almost identically and belong to different families. Rather than comparing how
they look, ask whether you could want one without the other.

- **Tabs or SegmentedControl.** A tab bar changes what is below it. A segmented control sets a
  value where it stands. You can change a view without setting a value, and set a value
  without changing a view, so these are two operations. That is why one is a radio group and
  the other is not.
- **Dialog or AlertDialog.** A dialog holds work you asked for. An alert stops you to ask one
  question, and its contents are fixed, because the system lays them out.
- **Menu or Select.** A menu picks an action. A select picks a value and submits it with a
  form.
- **Link or Button.** A link goes somewhere; a button does something. Ask what happens when
  you press it: a new address, or a change to what you are looking at. Accent-coloured words
  that submit a form are a quiet Button, and a Link that runs a handler has broken the one
  promise a link makes.
- **Card or Surface.** An object, or the thing it is sitting on.

The test that works for all five: ask what each one does when the other is not there. If the
answers differ, they are different things, and one component with two variants would teach
everyone who read your code that the difference was only cosmetic.
