Every design system ships guidelines. Almost all of them are advice: a document beside the
code, describing what the code would do if everyone remembered. The gap between the two opens
immediately and never closes, because nothing measures it.

The rules in these pages are not advice. Most of them are unexpressible to violate, and the
rest are checked by something that fails a build. This chapter is about which is which — and
about the parts that are genuinely taste, said plainly, because dressing a preference as a law
is the same error as dressing a law as a preference.

## Refusals are types, not warnings

What the system forbids is usually not available to write.

```tsx
// Not "don't do this". There is no such prop.
<Button margin="4">Save</Button>
```

`ButtonProps` has no margin, no `variant`, no `color`, and no shadow. A component owns no outer
spacing, so the type does not offer any; loudness and meaning are separate axes, so there is no
prop that conflates them. Every scale is a closed union — `size` is `"1" | "2" | "3" | "4"`,
not a number — so a value between the rungs cannot be typed.

This is stronger than a lint rule and much stronger than a paragraph. A lint rule can be
disabled; a paragraph can be unread. A prop that does not exist produces a red squiggle in the
editor before anyone has run anything.

The corollary is that **an absence is information**. When a component does not take a prop you
expected, that is usually a decision with a reason, and the reason is written down: every
component's page has a section listing what it refuses and why. If you find an absence with no
entry, that is a gap in the documentation rather than a permission.

## The escapes are real, and they are loud

A refusal without an escape is policing. Every component forwards `className` and `style`, and
consumer `style` merges last — so an escape always wins, and it wins *visibly*.

```tsx
// The sanctioned way to place something. Not a margin on the button.
<Box m="4">
  <Button>Save</Button>
</Box>

// The escape, when the system genuinely has no answer.
<Card style={{ maxInlineSize: "42rem" }}>…</Card>
```

That visibility is the point. An escape hatch is a signal: one is fine, a file full of them
means the system is missing something, and what it is missing is usually a token or a family
rather than a prop.

## The laws

The system's claims about itself are executable. They are not snapshot tests — a snapshot
asserts nothing anyone decided — but statements about invariants, and the suite is written so
that a claim which stops being true fails a build.

- Every size-2 control resolves the identical height, padding and radius tokens.
- Every recipe's hover is exactly one step up and its press exactly two.
- Every generated solid fill passes its contrast target against its own computed label colour.
- The gzipped CSS is measured on every commit and a regression is a hard failure.
- Margin and position props do not exist on control types, asserted at the type level.

One rule governs how those laws are written, and it was learned the expensive way. **A law
reads the browser's computed value, through a mounted component, in both appearances.** An
audit once found that every broken axis in the system was one where no law read a computed
value: the tests asserted attribute strings, token *names*, and in-memory objects — each one
indirection short of the thing that could be wrong, and in each case that thing was wrong.

## The reviewer

Some rules are about composition rather than about a component, and those cannot live in a
type. One focal action per surface. Differentiated rhythm. Tone used as vocabulary rather than
decoration. A heading ladder that descends.

Those are checked too, in the [builder](/builder): the house style runs as live rules over a
document, each finding citing the system's own sentence and carrying a fix. The templates it
ships are held to zero findings by a law, which is what keeps the rules honest — a rule nobody
can satisfy gets found the moment it is written.

## What is not enforced

Taste. Deliberately, and it is most of what makes an interface good.

The system has objective floors and it is immovable about them: target sizes come from touch
anthropometry, contrast from measured models, grouping from documented perceptual behaviour.
Above the floors, the exact radius, the material's saturation, the specific accent, and the
rhythm of a particular screen are judgment. They are stated as judgment, they are tuned by eye,
and no law asserts them.

Being clear about the boundary is the discipline. Asserting false precision is the same error as
asserting false sameness, inverted — and a system that claimed its taste was measured would be
lying in the direction that is hardest to catch.

## Drift is treated as a bug

A last mechanism, and it is the one holding this site together. When code forces a decision to
change, the document changes in the same commit. The pages you are reading are checked against
the specification they publish: every chapter names the sections it re-voices and a law resolves
every one of those references against the real document, so a chapter about a decision that was
never specified fails before it reaches you.

The generated half of the component reference is read out of the package's own types, and a law
regenerates and compares — so it cannot describe a prop that no longer exists. That failure has
happened here: a documented prop that had never existed shipped once and was caught only because
the page happened to be type-checked. The mechanism exists because the mistake did.
