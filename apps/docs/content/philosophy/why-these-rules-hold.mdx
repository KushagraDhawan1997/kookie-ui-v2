Most design systems ship their guidelines as advice. The document sits next to the code and
describes what the code would do if everyone remembered every rule. Over time the two drift
apart, and nothing tells you how far.

The rules on this site work differently. Most of them you cannot get wrong, because the types
will not let you. Some are checked automatically. The rest are judgments, and this chapter
tells you which is which — because dressing a judgment up as a measured rule is how a system
stops being trustworthy.

## Most refusals live in the types

You cannot write the code the system refuses.

```tsx
// This prop does not exist.
<Button margin="4">Save</Button>
```

`ButtonProps` has no `margin`, no `variant`, no `color` and no shadow prop. A component does
not set its own outer spacing, so there is no margin to set. `tone` and `emphasis` are
separate, so there is no prop that combines them.

Every scale is a fixed list. `size` is `"1" | "2" | "3" | "4"` — not a number, so you cannot
type a value in between.

A type is stronger than a lint rule and much stronger than a paragraph. You can turn a lint
rule off and you can skip a paragraph. A prop that does not exist shows up as an error in your
editor before you run anything.

**When a prop is missing, that usually means something.** If a component does not take a prop
you expected, it is normally a refusal rather than an oversight, and every component page
lists its refusals with the reason for each. If you find one with no entry, that is a gap in
these pages.

## The ways out are meant to be visible

A refusal with no way around it is not a design, it is an obstruction.

Every component forwards `className` and `style`, and your `style` is applied last, so your
value wins.

```tsx
// There is no token for a reading column width, so state it directly.
<Box style={{ maxInlineSize: "42rem" }}>
  <Card size="3">
    <Stack gap="4">
      <Heading size="6">Workspace name</Heading>
      <TextField id="workspace" defaultValue="Kookie Studio" />

      {/* One control, spaced by a wrapper you can see. */}
      <Box mt="2">
        <Button emphasis="loud">Rename</Button>
      </Box>
    </Stack>
  </Card>
</Box>
```

The point is that an escape shows up in a diff. One is normal. A file full of them means the
system is missing something, and what it is missing is usually a token or a tone rather than a
prop.

## What the tests actually check

There are no snapshot tests here, because a snapshot only tells you that something changed,
not that anything was ever decided.

- A Button, a TextField and a Select at size 2 resolve to the same height, padding and corner. A
  checkbox, a menu row, a tab and a segment are sized by their own rules, and each of those is
  checked against the rule it follows.
- Every control moves one step on hover and two on press.
- Every generated colour meets its contrast target against the text that sits on it.
- The gzipped CSS is measured on every commit, and the build fails if it grows.
- Margin and position props do not exist on control types, and a type-level test proves it.

One rule governs how all of these are written. **A test reads the value the browser actually
computed, from a real mounted component, in both light and dark.**

A test that reads an attribute, a token name or an object in memory stops one step short of the
thing that can be wrong, and it will happily pass while the rendered result is broken.

## Some rules are about a whole screen

A few rules describe a screen rather than a component, so no type can hold them.

- Use one loud control per screen.
- Use different gaps for different relationships.
- Use a tone because of what it means.
- Step each heading down from the one above it.

The [builder](/builder) runs these over a live document. Every finding quotes the rule it comes
from and offers a fix. All the templates that ship with the builder are held to zero findings,
which also keeps the rules honest: a rule nobody could satisfy would break those templates the
day it was added.

## What is not checked, on purpose

Nothing here checks taste, and taste is most of what makes an interface good.

What the system does hold, and will not move, are the measured limits: tap target sizes come
from how big fingertips are, contrast comes from measured models of vision, and grouping comes
from documented research on perception.

Above those, the exact corner radius, how saturated a glass panel is, which hue the accent takes,
and the rhythm of any one screen are judgments. These pages say so, and each of those values
lives in one configuration file rather than being buried in a component. No test asserts any of
them.

Saying which is which matters. A system that called its judgments measurements would be making
a claim nobody could check.

## These pages cannot quietly go stale

When a change to the code forces a decision to change, the documentation changes in the same
commit.

Every chapter names the parts of the specification it comes from, and a test resolves each of
those references against the real document. A chapter describing a decision the specification
does not contain fails before anybody reads it.

The props table on each component page is generated from the package's own types, and a test
regenerates it and compares. It cannot describe a prop that no longer exists, and it cannot
leave out one that does.
