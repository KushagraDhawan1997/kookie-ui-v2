Most design systems ship guidelines as advice. The document sits beside the code and describes
what the code would do if every developer remembered every rule. The two separate, and nothing
measures the gap.

The rules on this site work differently. You cannot express most of them incorrectly. A test
checks the rest. This chapter states which rule is which. It also states which parts are
judgment, because presenting a judgment as a measured rule is a fault.

## The types state the refusals

You cannot write most forbidden code.

```tsx
// This prop does not exist.
<Button margin="4">Save</Button>
```

`ButtonProps` has no `margin`, no `variant`, no `color` and no shadow prop. A component does
not set outer spacing, so the type offers no margin. `tone` and `emphasis` are separate axes,
so no prop combines them.

Every scale is a closed union. `size` is `"1" | "2" | "3" | "4"`. It is not a number. You
cannot type a value between two steps.

A type is stronger than a lint rule, and much stronger than a paragraph. You can disable a
lint rule. You can skip a paragraph. A prop that does not exist produces an editor error
before you run anything.

**A missing prop carries information.** When a component does not take a prop you expect, the
system usually refuses it for a reason. Each component page lists its refusals and the reason
for each one. If you find a refusal with no entry, the documentation has a gap.

## The escapes work, and they are visible

A refusal with no escape is not a design. It is an obstruction.

Every component forwards `className` and `style`. Your `style` merges last, so your value
always wins.

```tsx
// The reading column has no token, so state it with style. Everything inside it does.
<Box style={{ maxInlineSize: "42rem" }}>
  <Card size="3">
    <Stack gap="4">
      <Heading size="6">Workspace name</Heading>
      <TextField id="workspace" defaultValue="Kookie Studio" />

      {/* One control, placed by the layout that owns the relationship. */}
      <Box mt="2">
        <Button emphasis="loud">Rename</Button>
      </Box>
    </Stack>
  </Card>
</Box>
```

An escape is visible in a diff. One escape is normal. A file full of escapes means the system
lacks something. That missing thing is usually a token or a tone family, not a prop.

## The tests state the invariants

The test suite asserts invariants. It contains no snapshot tests, because a snapshot asserts
nothing that anyone decided.

- Every size-2 control resolves the same height, padding and radius tokens.
- Every recipe moves one step on hover and two steps on press.
- Every generated fill meets its contrast target against its own label colour.
- CI measures the gzipped CSS on every commit and fails the build when it grows.
- Margin and position props do not exist on control types. A type-level test asserts this.

One rule governs how the suite writes these tests. **A test reads the value the browser
computes, from a mounted component, in both appearances.**

A test that reads an attribute string, a token name or an object in memory stops one step short
of the value that can be wrong. It passes while the rendered result is incorrect.

## The reviewer checks the composition

Some rules describe a whole screen, not one component. A type cannot hold them.

- Use one loud control on each screen.
- Use different gap values for different relationships.
- Use a tone for its meaning.
- Step each heading down from the heading above it.

The [builder](/builder) runs these rules over a live document. Each finding cites the rule and
carries a fix. A test holds the shipped templates to zero findings. That test also checks the
rules: a rule that nobody can satisfy fails on the day someone writes it.

## What the system does not check

The system does not check taste. This is deliberate, and taste decides most of the quality of
an interface.

The system holds measured limits and does not move them. Target sizes come from touch
anthropometry. Contrast comes from measured models. Grouping comes from documented perceptual
behaviour.

Above those limits, the exact radius, the saturation of a material, the accent colour and the
rhythm of one screen are judgments. The documentation states them as judgments, and every one of
them is a value in the colour configuration rather than a number in a component. No test asserts
them.

State the boundary clearly. A system that claimed its judgments were measurements would make a
claim that nobody can check.

## The documentation cannot drift

When code forces a decision to change, the document changes in the same commit.

These pages are checked against the specification they publish. Each chapter names the sections
it states, and a test resolves every one of those references against the real document. A
chapter about a decision that the specification does not contain fails before you read it.

A script generates the props table on each component page from the package types. A test
regenerates the table and compares it. The table cannot describe a prop that no longer exists,
and it cannot omit one that does.
