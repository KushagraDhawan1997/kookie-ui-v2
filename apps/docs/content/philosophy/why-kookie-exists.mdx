KookieUI is built to be correct rather than to be easy to adopt. Those two goals pull apart
more often than you would think, because the things that make a system spread are not the
things that make it right.

There are two questions worth asking about a system like this. Does it agree with what we
actually know about how people use interfaces? Do the products built on it work better? How
many people have starred it is not one of them.

## Find the pattern before you name the component

A **pattern** is a structure that keeps turning up: a context, a problem, and the shape of the
solution. You find patterns in the world rather than inventing them.

A **component** is a pattern packaged so you can reuse it. A **name** is just the label on the
package.

Work in that order — pattern, then component, then name. Most teams go the other way. They
start with a name and a picture of how it should look, and work out what it does last. Almost
every fault below comes from that reversal.

## Two things that look alike can still be two things

Tabs and SegmentedControl look nearly identical. Both draw a row of segments. They do
completely different jobs.

Tabs moves you between views, and the panel underneath changes. SegmentedControl sets a value
where you are standing, and the chart underneath stays put.

It is tempting to make them one component with two variants. The problem is not that it would
look bad. It is that putting two things in one box teaches everyone who reads your code that
they are the same thing.

```tsx
// Switching between views. The panel below changes.
<Tabs defaultValue="usage">
  <TabsList>
    <TabsTab value="usage">Usage</TabsTab>
    <TabsTab value="invoices">Invoices</TabsTab>
  </TabsList>
  <TabsPanel value="usage">{usage}</TabsPanel>
  <TabsPanel value="invoices">{invoices}</TabsPanel>
</Tabs>

// Setting a value in place. The chart below stays where it is.
<SegmentedControl
  value={range}
  onValueChange={(value) => setRange(String(value))}
  aria-label="Date range"
>
  <SegmentedItem value="7d">7 days</SegmentedItem>
  <SegmentedItem value="30d">30 days</SegmentedItem>
  <SegmentedItem value="90d">90 days</SegmentedItem>
</SegmentedControl>
```

The difference is not only visual. Tabs announces itself as a tab list and gives each panel a
name. SegmentedControl announces itself as a radio group, so a screen reader says "3 of 3
selected" and the arrow keys change the value. You cannot get either behaviour out of the
other component.

## Some design questions already have answers

Not everything in design is taste. Some of it has been measured.

- Fitts's law, from 1954, predicts how long it takes to move a pointer to a target, from the
  distance and the size of the target.
- A fingertip is about 10 millimetres across. That measurement is where every platform's
  44-point minimum tap target comes from.
- The Gestalt principles, from 1923, describe how your eye groups things before you read them.
- WCAG and APCA both measure whether text is readable against its background.

Above those limits, it really is judgment: the exact corner radius, how saturated a glass
panel should be, which blue is your blue.

The important part is knowing which kind of answer you are holding. Where something is
measured, cite it and leave it alone. Where it is a judgment, say so and own it. Dressing a
judgment up as a measurement is how a system stops being trustworthy.

## Being consistent is cheaper than being inconsistent

Shipping the same button twice costs less than deciding, a second time, how heavy that button
should be.

An inconsistent system does not actually save you time. It just makes you decide the same
things again, one screen at a time, with no way to see what the earlier screens decided. The
bill arrives around the twentieth screen.

## Why so much of the field works the other way

This is about incentives rather than skill.

- **The popular tools have no middle.** shadcn/ui gives you source code to copy into your
  project, and once you copy it, it is yours and nothing updates it. Tailwind puts every style
  choice on the element that uses it. Both are fast to start with. Neither gives you one place
  to change a rule.
- **Teams build patterns as though they were components.** A component contains things. A
  sidebar coordinates things it does not contain: the header, the content, the width of the
  window. You can spot the mistake when a child component has to reach upward and configure
  its parent.
- **Public work rewards a single screenshot.** Most careful systematic design happens inside
  companies, on systems nobody outside ever sees. What gets shared publicly is judged one
  component at a time, and consistency does not show up in one component. It shows up across
  twenty screens.
- **The research stopped being read.** A missed tap on a website costs almost nothing, so
  nothing punishes the mistake. That is how "responsive" changed meaning: it used to mean
  "adapt to the person holding this device", and now it mostly means "reflow without a
  sideways scrollbar". The easy measurement replaced the goal.
- **AI produces more of it, faster.** A model writes each component on its own, and each one
  looks fine. The set is inconsistent, and nothing tells you.

## What this costs you

A system built for correctness is harder to adopt than one built for adoption. That is a real
trade and you should know it before you start.

There is no `variant` prop to reach for when a design does not quite fit. Instead there are
refusals, and every refusal comes with a reason and an alternative. There are fewer escape
hatches, and this documentation tells you where the ones that exist are.

What you get in return is one thing: your twentieth screen costs about what your second screen
cost.
