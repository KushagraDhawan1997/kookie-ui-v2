KookieUI is built to be correct rather than easy to adopt. Those two goals pull apart often,
because what makes a system spread is not what makes it right.

Two questions are worth asking about a system like this one. Does it agree with what research
shows about how people use interfaces? Do the products built on it work better? The number of
stars it has is not one of those questions.

## Find the pattern before you name the component

A pattern is a recurring structure: a context, a problem and the shape of the solution. You
discover patterns in the world rather than inventing them.

A component is a pattern packaged for reuse, and a name is the label on that package.

Work in this order: first the pattern, then the component, then the name. Most teams reverse
it. They start with a name and a picture of how it should look, and they decide what it does
last. Almost every fault below comes from that reversal.

## Tell two components apart by what they do

Tabs and SegmentedControl look almost identical, and both draw a row of segments. They do
different jobs.

Tabs moves you between views, so the panel underneath changes. SegmentedControl sets a value in
place, so the chart underneath stays where it is.

Combining the two into one component with two variants is tempting. The result would look fine.
The cost is that one name teaches everyone who reads your code that these are the same thing.

```tsx
// Switching between views. The panel below changes.
<Tabs defaultValue="usage">
  <TabsList>
    <TabsTab value="usage">Usage</TabsTab>
    <TabsTab value="invoices">Invoices</TabsTab>
  </TabsList>
  <TabsPanel value="usage">{usage}</TabsPanel>
  <TabsPanel value="invoices">{invoices}</TabsPanel>
</Tabs>

// Setting a value in place. The chart below stays where it is.
<SegmentedControl
  value={range}
  onValueChange={(value) => setRange(String(value))}
  aria-label="Date range"
>
  <SegmentedItem value="7d">7 days</SegmentedItem>
  <SegmentedItem value="30d">30 days</SegmentedItem>
  <SegmentedItem value="90d">90 days</SegmentedItem>
</SegmentedControl>
```

The difference is not only visual. Tabs announces itself as a tab list and gives each panel a
name. SegmentedControl announces itself as a radio group, so a screen reader says "3 of 3
selected" and the arrow keys change the value. Neither behaviour is available from the other
component.

One test settles cases like this. Ask what each component does when the other is absent. You
can switch views without setting a value, and you can set a value without switching views.
These are two operations rather than one operation with two appearances.

## Some design questions already have answers

Not everything in design is a matter of taste. Some of it has been measured.

- Fitts's law, from 1954, predicts how long it takes to move a pointer to a target, from the
  distance and the size of that target.
- A fingertip is about 10 millimetres across. That is where every platform's 44-point minimum
  tap target comes from.
- The Gestalt principles, from 1923, explain how your eye groups things before you read them.
- WCAG and APCA both measure whether text is readable against its background.

Beyond those measured limits a design decision is a judgment, such as the exact corner radius,
how saturated a glass panel should be and which hue your accent takes.

Know which kind of answer you are holding. Where something is measured, cite it and do not
change it. Where it is a judgment, say so and own it. A system that presents a judgment as a
measurement makes a claim nobody can check.

## Why consistency saves time

Shipping the same button twice is cheaper than deciding a second time how heavy that button
should be.

An inconsistent system does not save you time. It makes you decide the same things again, one
screen at a time, with no way to see what the earlier screens decided. That cost does not
appear on the first screen or the fifth. It appears around the twentieth.

## Why so much of the field works the other way

The cause is incentives rather than skill.

- **The popular tools have no middle ground.** shadcn/ui gives you source code to copy into your
  project, and once you copy it, it is yours and nothing updates it. Tailwind puts every style
  choice on the element that uses it. Both are quick to start with, but neither provides a
  single place to change a rule.
- **Teams build patterns as though they were components.** A component contains the things it
  owns. A sidebar coordinates things it does not contain, such as the header, content and
  window width. You can spot the mistake when a child component has to reach upward
  and configure its parent.
- **Public work rewards a single screenshot.** Most careful, systematic design happens inside
  companies, on systems nobody outside ever sees. Public work is judged one component at a
  time, and consistency does not appear in one component. It appears across twenty screens.
- **The research stopped being read.** A missed tap on a website costs almost nothing, so
  nothing punishes the mistake, and "responsive" changed meaning as a result. It used to mean
  "adapt to the person holding this device", but now it mostly means "reflow without a sideways
  scrollbar". The easy measurement replaced the goal.
- **AI produces more of it, faster.** A model writes each component on its own, and each one
  looks fine. The set is inconsistent, and nothing reports it.

## What this costs you

A system built for correctness is harder to adopt than one built for adoption. That is a real
trade, and you should know it before you start.

There is no `variant` prop to reach for when a design does not quite fit. Instead there are
refusals, and each one comes with a reason and an alternative. There are fewer ways out than
you are used to, and these pages name every one that exists.

Your twentieth screen takes about as long to build as your second.
