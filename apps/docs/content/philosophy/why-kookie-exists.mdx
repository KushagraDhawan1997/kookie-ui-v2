KookieUI optimizes for correctness, not for adoption. The two separate often, because the
market cannot measure correctness.

Two tests judge this system. Does it match the published research on how people use
interfaces? Do products built on it work better? GitHub stars are not a test.

## Patterns, not components

A **pattern** is a functional structure that repeats. It has a context, a problem and a
solution. You find a pattern in the world. You do not invent it.

A **component** is a pattern packaged for reuse. A **name** is a label for a component.

Work in this order: find the pattern, then package it, then name it. Most teams work in the
opposite order. They start with a name and an appearance, and they decide the function last.
That order causes the faults below.

## Split by function, not by appearance

Tabs and SegmentedControl look almost the same. Both draw a horizontal row of segments. They
do different jobs.

Tabs switches between views, and the panel below it changes. SegmentedControl sets a value in
place, and the chart below it stays where it is.

Do not merge them into one component with two variants. The merge is not ugly. It is wrong.
When you put two things in one category, readers treat them as the same thing.

```tsx
// Switching between views. The panel below changes.
<Tabs defaultValue="usage">
  <TabsList>
    <TabsTab value="usage">Usage</TabsTab>
    <TabsTab value="invoices">Invoices</TabsTab>
  </TabsList>
  <TabsPanel value="usage">{usage}</TabsPanel>
  <TabsPanel value="invoices">{invoices}</TabsPanel>
</Tabs>

// Setting a value in place. The chart below stays where it is.
<SegmentedControl
  value={range}
  onValueChange={(value) => setRange(String(value))}
  aria-label="Date range"
>
  <SegmentedItem value="7d">7 days</SegmentedItem>
  <SegmentedItem value="30d">30 days</SegmentedItem>
  <SegmentedItem value="90d">90 days</SegmentedItem>
</SegmentedControl>
```

`Tabs` announces a tab list, and each panel gets a name. `SegmentedControl` announces a radio
group, so a screen reader says "3 of 3 selected" and the arrow keys change the value. Neither
behaviour is available from the other component.

## Design has measured limits

Some design questions have measured answers.

- Fitts's law (1954) predicts how long a pointer movement takes, from the distance and the
  target width.
- Touch anthropometry measures a fingerpad at about 10mm. Every platform sets a 44-point
  minimum from this measurement.
- The Gestalt principles (1923) document how the visual system groups objects.
- WCAG and APCA measure contrast.

Above these limits, the work is judgment: the exact radius, the saturation of a material, the
specific accent colour.

Know which kind of answer you have. Cite the measurement and do not move it. Own the judgment
and call it a judgment. Calling a judgment a measurement is a fault. So is calling two
different things one thing.

## Consistency costs less than inconsistency

Shipping the same button twice costs less than deciding its weight a second time.

An inconsistent system does not save time. It repeats decisions without memory. Each screen
decides alone, and it cannot see what the earlier screens decided. You pay for that on the
twentieth screen.

## Why the field works this way

The cause is incentives, not skill.

- **The popular tools have no centre.** shadcn/ui gives you source code to copy into your
  project. Once you copy it, it is your code, and nothing updates it. Tailwind puts each style
  choice on the element that uses it. Both are quick to adopt. Neither can hold a rule in one
  place.
- **Teams build patterns as if they were components.** A component contains things. A sidebar
  coordinates things it does not contain: the header, the content, the width of the window.
  You can see the mistake when a child component has to reach up and configure its parent.
- **Public work rewards the single screenshot.** Most systematic design happens inside
  companies, on private systems nobody sees. Public work is judged one component at a time.
  Consistency does not show up in one component. It shows up when you assemble twenty screens.
- **Teams stopped reading the research.** A missed tap on a website costs little, so nothing
  punishes the error. "Responsive" changed meaning because of this. It used to mean "adapt to
  the person holding this device". It now means "reflow without a horizontal scrollbar". The
  easy measurement replaced the goal.
- **AI makes more of it, faster.** A model writes each component on its own. Each one looks
  correct. The set is inconsistent, and nothing reports it.

## What this costs you

A system built for correctness is harder to adopt than one built for adoption.

There is no `variant` prop to reach for when a design does not fit. There are refusals, and
each refusal gives a reason. There are fewer escape routes, and this document names the ones
that exist.

You get one thing for that cost. The twentieth screen costs what the second screen cost.
